# Rubric: 採点とフィードバック

ルーブリック式の **3軸 × 0.0-1.0** で部分点を付け、Hattie & Timperley (2007) の **3層フィードバック構造** で返す。フィードバックは学習科学において最大級の効果サイズ（*d* ≈ 0.7-1.0）を持つので、ここの設計を妥協しない。

## 採点の前のプロトコル: Self-Explanation

採点する前に、**「なぜそう答えたか」をユーザーに短く述べてもらう**（Stage 2 以降で必須）。

- Bisra et al. (2018) のメタ分析で *g* = 0.55
- ユーザーの説明と模範解答の **差分** が後の Feed-back の精度を決める
- Stage 1（Foundation / 完全初学者）では prior knowledge 不足のためスキップ可

例:
```
ありがとうございます。採点する前に1つだけ:
このコードでなぜ x を使ったか、一言で説明していただけますか？（思いつかなければ「パス」でOK）
```

## 3軸の定義

### 1. 正確性 (accuracy)
**質問が問うている内容に対する答えの正しさ**

| Score | 状態 |
|---|---|
| 1.0 | 完全に正しい。間違いなし |
| 0.7-0.9 | 主旨は正しいが些細な誤り（用語のブレ、軽微な不正確さ） |
| 0.4-0.6 | 部分的に正しいが核心の誤解あり、または一部のみ正解 |
| 0.1-0.3 | 関連はあるが本質的に誤り |
| 0.0 | 完全に誤り（ただし「わからない」回答は **後述の規定で 0.1-0.3**） |

### 2. 根拠 (reasoning)
**答えに至る理由・思考過程・裏付けが示されているか**

| Score | 状態 |
|---|---|
| 1.0 | 論理的・段階的で、なぜその答えに至るかが明瞭 |
| 0.7-0.9 | 大筋の根拠は示されているが説明に飛躍あり |
| 0.4-0.6 | 部分的に根拠を示すが、推測や暗黙の前提が多い |
| 0.1-0.3 | 「なんとなく」「直感で」レベル、根拠ほぼなし |
| 0.0 | 根拠が完全に不在、または論理破綻 |

### 3. 網羅性 (completeness)
**問われた要素を漏れなく扱っているか、エッジケース・例外への目配りがあるか**

| Score | 状態 |
|---|---|
| 1.0 | 主要観点をすべて押さえ、エッジケースにも言及 |
| 0.7-0.9 | 主要観点はカバー、エッジケースは一部のみ |
| 0.4-0.6 | 主要観点の半分程度、抜けが目立つ |
| 0.1-0.3 | 主要観点の一部のみ、大きな抜け |
| 0.0 | 触れていない |

## 重み付け

問題タイプにより 3軸の重みを変える:

| 問題タイプ | accuracy | reasoning | completeness |
|---|---|---|---|
| 短答・選択 (recall, mcq) | 0.7 | 0.2 | 0.1 |
| 出力予測 (predict-output) | 0.5 | 0.4 | 0.1 |
| 空欄補充 (fill-blank) | 0.7 | 0.2 | 0.1 |
| コード書き (code-write, hands-on) | 0.4 | 0.3 | 0.3 |
| バグ探し (find-bug, debug) | 0.4 | 0.4 | 0.2 |
| 説明問題 (explain, read-and-explain) | 0.3 | 0.4 | 0.3 |
| 比較・評価 (compare, critique) | 0.3 | 0.4 | 0.3 |
| 設計問題 (design-mini) | 0.3 | 0.3 | 0.4 |
| リファクタ (refactor) | 0.4 | 0.3 | 0.3 |
| 拡張 (extend) | 0.4 | 0.3 | 0.3 |

最終 `score = accuracy * w_a + reasoning * w_r + completeness * w_c`

## 「わからない」「空欄」回答のスコアリング

ユーザーが以下を回答した場合の規定:

| 回答状態 | accuracy | reasoning | completeness | 備考 |
|---|---|---|---|---|
| 完全空欄 | 0.0 | 0.0 | 0.0 | ただし採点後の対応は **必須**（後述） |
| 「わかりません」 | 0.1 | 0.1 | 0.1 | 取り組んだ姿勢を最低評価 |
| 「途中まで考えた + わからない」 | 0.2-0.3 | 0.2-0.3 | 0.1 | 部分的な思考プロセスを評価 |
| 「適当に」当てずっぽう | 0.0-0.2 | 0.0 | 0.0 | 推測当たりは評価しない |

**重要**: スコアが低くても、**必ず模範回答 + 解説を提示する**。次の問題に進まない。詳細は `references/explanation-guide.md` の「『わからない』『空欄』回答への対応」プロトコル参照。

## 採点の心構え

- **0.7 を「合格ライン」の感覚で使う**。0.95 も 0.55 もちゃんと使い分ける
- **同情で点を上げない**。実際の理解度を歪めるとレベル推定が壊れる
- **意地悪で点を下げない**。学習者の挑戦を奪う
- **採点理由を明示**。スコアだけでなく「なぜその点数か」が後で読み返せる形に

## フィードバック構造（Hattie の3層）

採点と一緒に、必ず以下の **3層** を提示する。Hattie & Timperley (2007) で最も効果的とされるパターン:

### 1. Feed-up（目標）
**この問題が問うていた本質を1行で再確認**

「この問題のねらい: <一文>」

### 2. Feed-back（差分）
**ユーザーの回答と模範解答のどこに差があるか、なぜ**

ユーザーの回答に **固有** の指摘をする（汎用的な解説で済ませない）。

### 3. Feed-forward（次の一手）
**次回同じ概念に出会った時の指針**

具体的なヒューリスティック1つ。「気をつけてください」では不十分。

## md エントリ形式

採点結果は問題ファイル末尾の `## 採点` / `## 解説` / `## 模範回答` セクションに Edit で書き込む。

```markdown
## 採点

**Score**: 0.72 (acc: 0.8 / reas: 0.7 / comp: 0.6)

**Tags**: weak: [edge-cases, null-handling], strong: [], hints_used: 0

## 解説

**この問題のねらい**: 配列処理で境界条件を漏らさないこと（Feed-up）

**差分の説明**:
ユーザーの回答は主要なケースの判定は正しいですが、空配列のときに `arr[0]` で undefined を返すパスが残っています（Feed-back）。

**次に意識してほしいこと**:
配列を扱うときは「空 / 1要素 / 多要素」の3パターンを最初に書き出す習慣をつけると同じ漏れを防げます（Feed-forward）。

（アナロジー、`explanation-guide.md` 参照）
</details>

## 模範回答

<details><summary>展開して見る</summary>

```typescript
function head<T>(arr: T[]): T | undefined {
  if (arr.length === 0) return undefined;
  return arr[0];
}
```

</details>
```

詳細な解説の書き方（例え話の作り方、self-explanation の引き出し方、ビジュアル化）は `references/explanation-guide.md` 参照。

## アンチパターン（避ける）

- **「すばらしい！」「がんばりました！」だけ** — 中身ない praise は *d* < 0.20、効果ほぼゼロ（Wisniewski et al. 2020）
- **「正解です」「不正解です」だけ** — 学習機会を捨てている。Feed-back と Feed-forward が必須
- **長文の講義** — Cognitive Load オーバー。1問 8-15行が目安、長いものは `<details>` で折りたたむ
- **「もっと頑張りましょう」** — 抽象的な promise。具体ヒューリスティックを1つ書く
- **採点だけして模範回答を出さない** — 「わからない」回答に対しては絶対禁止
- **同情採点** — 「次回頑張ろう」の意で 0.5 を 0.7 にしない。スコアの一貫性が崩れる

## タグ蓄積（弱点・強点）

採点時に `weak_tags` / `strong_tags` を Q エントリ末尾の `**Tags**:` 行に書く:

```markdown
**Tags**: weak: [edge-cases, null-handling], strong: [], hints_used: 0
```

- **検索可能なキーワード形式**（例: `generic-constraints`, `null-safety`, `side-effects-handling`, `passive-voice`, `derivative-chain-rule`）
- 自由記述だが、同一セッション内で **同じ概念には同じタグ** を使うこと
- 1問あたり 0-2個まで。多すぎると蓄積の意味が薄れる

採点後、`README.md` の `## Profile` セクションの `### Strong` / `### Weak` リストに **重複なくマージ** する（既存タグを Read で確認してから Edit）。

## 蓄積タグの活用

- 連続して同タグが Weak に出る → 次の lesson でそのサブトピックを優先
- Strong に何度も出るタグ → 出題頻度を下げて他分野に時間配分
- 5 lesson 連続で同じ Weak タグが出たら → カリキュラム再生成（基礎強化セクションを挟む）
- セッション終了時のサマリに反映、次回セッション開始時にも参照される
