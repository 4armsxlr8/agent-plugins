# 上流工程の価値を測る実験の計画 (分割払いケース)

実行前に固定する文書。実行後に変えた箇所は末尾の「変更履歴」に理由と一緒に書く。

## 測りたいこと

upstream-partial-refund では draft, spec, crystallize がすべて満点で、差があっても測れなかった。依頼者役が意図をすべて知っていて、草案に無いものも指摘できた点も有利に働いた。このケースでは次を分けて測る。

| 問い | 比べるもの | 主な指標 |
|---|---|---|
| H1 聞き出す力: ラウンドは短い草案より多くの判断を引き出すか | ask, draft, spec | 捕捉 (12 件)、潜在 5 件のうち開発者が尋ねた数 (ASKED) と決めて書いた数 (STATED)、依頼者が読む量 |
| H2 plan の工程は何を足すか | 同じ spec から枝分かれした spec, crystallize | 捕捉、性質テスト、費用 |
| H3 plan-implement は何を足すか | 同じ plan から枝分かれした crystallize, full | 性質テスト、捕捉、費用 |
| H4 文書は安い実装者を助けるか | draft, spec, crystallize の pre-impl を sonnet / medium で実装し直し、同じ文書の xhigh の実装と、文書なしの guess の sonnet / medium と比べる | 捕捉、性質テスト |
| H5 文書は後の変更を助けるか | 同じ実装で、文書あり / 文書なしで追加の依頼 | Basics と CarriedOver のテスト、DocumentedOnly の可否、元の判断の維持 |

## ケース

`billing` (midsize の fixture) に分割払いを足す。依頼文は `case.json` の `request`。

採点は 3 つで、どれも実行前に書いて固定する。
- `intents/hidden/test_intent.py`: 判断 12 件。クラス名が判断の名前
- `properties/hidden/test_properties.py`: 判断によらない性質 (合計の保存、保存と読み込み、既存処理との整合、監査、原子性、明細書、督促の土台)。依頼者役には見せない
- `followup/hidden/test_followup.py`: H5 の追加の依頼。3 クラスを分けて数える。DocumentedOnly (支払い済みを含めて 12 回) は意図の文書に書いてあってコードには現れにくい判断なので、作りとして文書あり側に有利に働く

### 判断 12 件

依頼文に無く、コードからも決まらないものを選んだ。「既定」は実行前の予想で、結果を見て変えない。

| 名前 | 区分 | 内容 | 既定の予想 |
|---|---|---|---|
| CountLimit | 明示 | 回数は 2〜12 | 上限は無いことが多い |
| RemainderLast | 明示 | 端数は最後の回 | 既存の allocate を使うと最初の回に寄る |
| Grace | 明示 | 督促は期日の 7 日後まで猶予 | 猶予なし |
| PartialAllowed | 明示・対照 | 一部入金済みも分割できる | 合う |
| FirstDueWindow | 明示 | 1 回目の期日は翌日〜60 日以内 | 上限は無いことが多い |
| PaymentOldest | 明示・対照 | 入金は古い回から | 合う |
| DueOnKept | 明示 | invoice.due_on は変えない | 割れる |
| MonthEnd | 潜在 | 月末起点は常に月末 (6/30 → 7/31) | 7/30 になる |
| VoidBlocked | 潜在 | 分割中は取り消せない | 割れる |
| PaidCancelBlocked | 潜在 | 分割後の入金があれば取りやめ不可 | 取りやめられることが多い |
| TinyRejected | 潜在 | 0 円の回ができる分割は拒否 | 通ることが多い |
| WeekendShift | 潜在 | 土日の期日は翌月曜 | ずらさない |

対照の 2 件は既定で合うと予想したもので、聞き出す力の差を見るときは除いた 10 件でも数える。

### 依頼者役

- モデルは Opus に固定する (`--oracle-model opus`)。前のケースの Sonnet は 7 回で 3 回、指示から外れた
- 明示の 7 件は最初から知っている。聞かれれば答え、一覧や草案が食い違えば指摘する
- 潜在の 5 件は、開発者のメッセージか添付が話題に具体的に触れるまで、返信を書く役に渡さない。判定は別の呼び出しで行い、`exchanges.jsonl` の `raised` に残す。依頼者が考えていなかった論点を、開発者が持ち出せるかを測るためである
- 走行後に、別コンテキストのレビューで全返信を意図と照合し、誤った返信と `raised` の誤判定を条件ごとに数えて報告する。誤りが捕捉に効いた回はその旨を示す

## 条件と回数

実装者はどの条件も `--effort xhigh` で、モデルはアカウントの既定に揃える。依頼者役の費用は cost に入れない。

| 条件 | 回数 | 見込み (1 回) |
|---|---|---|
| 校正 (guess 2, ask 1) | 3 | $4 |
| guess | 3 | $4 |
| ask | 5 | $4 |
| draft | 5 | $8 |
| spec | 3 | $20 |
| crystallize (spec の各回から枝分かれ。plan の工程と実装) | 3 | $20 |
| full (crystallize の各回の plan から枝分かれ) | 3 | $40 |
| 同じ文書の 2 回目の実装 (spec, crystallize の文書 6 件 × xhigh) | 各 1 | $3 |
| H4 実装し直し (文書 11 件 × sonnet / medium) | 各 1 | $1 |
| H4 文書なしの基準 (guess × sonnet / medium) | 2 | $1 |
| H5 追加の依頼 (実装 3 つ × 2 arm × 3 回) | 18 | $3 |

見込みの合計は約 $420 で、$800 を超えそうなら止めて報告する。順序は次のとおりで、途中で止めても使える順にしてある。

1. 校正 (下記)
2. guess, ask, draft。ここで止める判定をする (校正の節)
3. spec を 3 回
4. spec の各回から `--branch` で crystallize、その各回から `--branch` で full。文書のばらつきを比較から除くため、同じ文書どうしで比べる
5. `--replay` で同じ文書の 2 回目の実装。文書の差が同じ文書の実装のばらつきより大きいかを見る
6. H4 と H5

どの条件も `-j` は 3 まで。秒は比べない (回ごとに TMPDIR を分けたので plugin の条件も並行できる)。

H5 の実装は、draft, spec, crystallize のそれぞれで捕捉が最も多い回を選ぶ (同点は性質テストの通過率、さらに同点なら回の番号が小さいほう)。

## 校正

guess 2 回と ask 1 回を先に走らせる。結果は本番に数えない。目的は次の確認に限る。

- テストの名前が依頼文の名前で動くこと (全滅しないこと)
- 依頼者役の仕組みが動くこと
- 満点に当たらないこと
- trace に共有の TMPDIR (`/tmp/claude-501`) が出ないこと

ここで変えてよいのは採点の不具合 (参照解や妥当な実装を理由なく落とす) だけで、判断の入れ替えはしない。例外として、guess が 2 回とも対照を除く 10 件中 8 件以上を取り、性質テストも 100% だった場合は、ケースが目的に合わないので作り直し、そのことを変更履歴に書く。

校正のあとの止めどころ:
- 手順 2 のあと、draft の捕捉の中央値が 11 件以上で性質テストの中央値が 97% 以上なら、差が出る余地が無いので手順 3 以降に費用をかけず報告する
- guess の性質テストがすべて 100% なら、H3 は性質テストで差を示せないので full を走らせない

実行前の検査: 参照解 (`results/upstream-installments-reference`) は判断と性質のテストに通る。参照解に `reschedule` は入れていない。追加の依頼のテストは、一時的に足した実装が 13 件すべて通ることを確かめた。判断を 1 つずつ裏返すと、その判断のテストだけが落ちる (PaymentOldest と DueOnKept の裏返しは性質テストも一部落ちる。入金の充て方と取りやめ後の期日に依存するため)。

## 読み方

- 捕捉: テストが通った判断。出どころは `exchanges.jsonl` の順に、質問、一覧の訂正、ラウンド、草案の照合、のどれかを確かめる。文書に書かれず既定で通ったものは「既定」と分けて書く
- 差があると言うのは、回ごとの値の範囲が重ならず、かつ中央値の差が捕捉で 2 件以上、潜在 5 件に触れた数で 2 件以上、性質テストで 5 ポイント以上のときだけ。それ以外は「差を示せなかった」と書く
- 枝分かれの H2, H3 は同じ文書どうしの差で読む。3 組とも同じ向きで、差の中央値が上の幅以上で、かつ同じ文書の 2 回の実装の差より大きいときだけ差があると言う。効果が無くても 3 組が揃う確率は 25% あるので、幅とばらつきの条件を外さない
- H1 の言い切りには量の注記を付ける。依頼者が読む量は ask より spec が大きく、明示の 7 件は文書が長いほど照合で拾える。聞き出す力は潜在 5 件の ASKED と、文書が無くても出た質問で読む
- H4 は同じ文書の xhigh との差と、文書なしの sonnet / medium との差の両方を書く
- H5 は Basics と CarriedOver (12 件) を率で、DocumentedOnly を可否で別に書く。実装 3 つのうち 2 つ以上で範囲が重ならず、差の中央値が 2 件以上で向きが揃うときだけ差があると言う。文書あり側が文書に触れたか (`touched_docs`) と、その spec に支払い済みを含む 12 回の決まりが書いてあるかも書く
- 回数が少ないので検定はしない。判断ごとの数は記述として出す
- 費用は全体の cost で比べる。`-j 3` の条件の秒は比べられない
- 依頼者が読む量 (メッセージ、レポート、最終版の spec の文字数) は表に出すが、人が読んだときの見落としはこの実験では測れない
- 1 ケースの結論としてだけ書く。別の種類のケースを足すかは結果を見て旦那様に諮る

## ERROR と取り直し

- 上限に当たった回は、仕組みが待って同じセッションで続ける
- ERROR の回と汚染の疑いがある回は数えず、同じ条件で 1 回足す。足した数と理由を報告する
- 実装を書いた工程の前に `billing/` を変更した回、plan を作った spec の回、ask で実装しないまま終わった回は ERROR にする
- H4, H5 の入力は ERROR でない回だけにする

## 汚染の確認

- 回ごとに `CLAUDE_CODE_TMPDIR` で別の TMPDIR を渡し (短いパスなら効くことを 1 回確かめた)、回の終わりに消す
- どの回も、採点の材料、共有の `/tmp/claude-501`、他の回の TMPDIR に触れた形跡があれば ERROR にする (実装し直しと追加の依頼も同じ)
- 実行前に、過去の検証が `/private/tmp/claude-501` に残した `gen`, `g`, `b`, `hr` を消した

## 第 2 段階: 問いにだけ答える依頼者役

### 変える理由

第 1 段階 (上の依頼者役、`--oracle-rule review-all`) では ask が 11 件、draft が 11〜12 件で上限に当たり、止めどころに当たった。ask の捕捉 55 件のうち 25 件は一覧の訂正で、一覧をすべて読んで直す依頼者役がラウンドの価値を測る余地を消していた。そこで一覧や草案を読まない依頼者役で測り直す。実際の人は、すべて直す上限 (第 1 段階) と、問われたことにしか答えない下限 (第 2 段階) の間にいる。

### 依頼者役の規則 (`--oracle-rule question-only`)

規則の本文は `upstream.py` の `REVIEW_RULES["question-only"]` に固定する。要点は次のとおり。

- 1 つの論点を名指しして判断を求めている文にだけ答える。選択肢の有無は問わない。チャットでもラウンドレポートでも同じ。「他に要望はありますか」のような広い問いには、第 1 段階と同じく 1 つだけ答える
- 問いが意図の 1 行に触れたら、その行の決まりをまとめて答え、別の行には触れない
- 一覧、表、草案、前提のまとめは読まない。意図と食い違っていても指摘しない
- 一覧や前提のまとめを確認するよう求める文は問いではない。ほかに問いがなければ「はい、それで結構です」とだけ答える
- 書き終えた仕様書の確認や確定を求める文も問いではない。ほかに問いがなければ DONE と答える (「はい」と答えると spec が plan に進むおそれがあるため)
- ラウンドレポートの推奨の無い問いで意図に書かれていなければ、先頭の選択肢を選ぶ
- 報告と次の工程の案内には、これまでどおり DONE と答える

指示だけに頼らず、次は仕組みで防ぐ。

- spec の草案は依頼者役に渡さない
- 潜在の判断は、ASKED と判定されるまで返信を書く役に渡さない。STATED のままなら依頼者は知らない
- 明示の 7 件は最初から知っているので、一覧を読まないことは指示に頼る。走行後の監査で違反を数える

判定の指示に「一覧全体にまとめて確認を求めているだけの項目」と「問いの説明、表、選択肢の得失に出てくるだけのもの」は STATED と足し、印の無い行も STATED にした。第 1 段階の `raised` はこの追記の前のものなので、両段階を比べるなら ASKED だけを使い、STATED は question-only では草案を判定に渡さない分だけ少なくなる点も書く。`read_chars` はタグを除いて数えるようにした。第 1 段階の値はタグ込みである。

走らせる前に、規則の最終版を保存済みのメッセージで確かめる (chat の質問と一覧、「特に確認してほしい」の境界、ラウンド 1、仕様書の確認、確定の案内)。走らせる直前の `upstream.py`、`compare.py`、`post.py`、この文書、テストを `results/upstream-installments-phase2-fixed/` に写して固定の証拠にする (コミットしていないため)。

### 条件と順序

実装者と採点は第 1 段階と同じ。テストと `case.json` は変えない。guess は依頼者役を使わないので、第 1 段階の 3 回を基準として使う。CLI の版とモデルが第 1 段階と変わっていれば報告に書く。

| 順 | 条件 | 回数 | 見込み (1 回) |
|---|---|---|---|
| A | ask | 5 | $2.2 |
| A | draft | 5 | $3.7 |
| B | spec | 3 | $20 |

見込みの合計は約 $90 で、$120 を超えそうなら止めて報告する。`-j` は 3 まで。spec の 1 回目は仕組みの確認を兼ねて 1 回だけ先に走らせ、ERROR でなければ本番に数える。plugin の条件を回ごとの TMPDIR で走らせるのは初めてなので、1 回目の trace に `/tmp/claude-501/` が出ていないかも見る。ERROR の足し直しは上の節に従うが、同じ理由が 1 条件で 2 回出たら足さずに止めて報告する。

### 監査

別コンテキストの監査役に、全返信を規則と照合させる。監査役には捕捉の結果を渡さない。数えるのは次の 3 つで、問いは走らせる前にここで固定する。

- 違反 a: 問われていない論点について、意図に沿って指摘したか、決まりを伝えたか
- 違反 b: 1 つの論点を名指しした問いに、「はい」で済ませたか、答えなかったか、答えが意図と食い違ったか
- 判定の誤り: `raised` の ASKED と STATED が、開発者のメッセージと規則の定義に照らして誤っていないか

捕捉に効いたかは、監査の報告と捕捉の結果を突き合わせて別に数える。

### A のあとの判定

- 違反で捕捉が変わった回が、ask か draft のどちらかで 2 回以上あれば、規則を直して ask と draft の両方を取り直す。直して取り直すのは 1 度だけで、直す前の結果も報告する。変更履歴に書く
- ask の捕捉の中央値が 10 件以上なら、一覧を読み飛ばしていない疑いがあるので `exchanges.jsonl` を確かめる。違反が無ければ次の条件で判断する
- draft の捕捉の中央値が 11 件以上なら、捕捉で spec との差は示せない。ASKED だけで読むために B を走らせるかを旦那様に諮る
- それ以外は B に進む
- 第 1 段階の止めどころ (draft の中央値 11 件以上で止める) は、上の諮る手順に置き換える

B のあとも同じ監査をする。B で上の基準に当たっても取り直さず、報告して諮る。

### 実行前の予想

第 1 段階の出どころから、質問への回答と既定だけを残した値を予想とする。結果を見て変えない。

- ask は 1 回あたり約 6 件 (質問 14 件と既定 16 件を 5 回で割る)
- draft は 1 回あたり約 7 件 (質問 22 件と既定 13 件を 5 回で割る)。草案の照合が無くなるので、残る差は質問の数だけになる
- spec は予想を置かない
- 性質テストは第 1 段階の guess、ask、draft がすべて 100% なので、この指標で差は出ない見込みである
- 予想が外れたら原因を書くが、読み方の基準は変えない

### 読み方

- 差があると言う基準は上の「読み方」と同じ。捕捉 (主は 12 件で、対照を除く 10 件は併記) は範囲が重ならず中央値の差が 2 件以上、潜在 5 件の ASKED も同じく 2 件以上、性質テストは 5 ポイント以上
- 主な比較は question-only の ask、draft、spec で、基準は guess。差があると言うのは、全回の値と違反の回を除いた値の両方が基準を満たすときだけにする。ASKED は判定の生の値と監査後の値の両方で同じにする
- 第 1 段階の ask、draft とは依頼者役の規則だけが違う別の走行で、同じ走行の繰り返しではない。両段階の差は「一覧や草案を読む依頼者がいる場合の上乗せ」の幅として記述し、原因の断定はしない
- 依頼者が読む量は、メッセージと、タグを除いたラウンドレポートの文字数を書く。question-only では草案を読まないので読む量に入らず、最終版の文書の長さは別に書く
- 捕捉はテストで数え、出どころは第 1 段階の分類に「開発者の既定」(開発者が文書や一覧に書き、依頼者が答えていない判断) を足して書く。一覧の訂正と草案の照合が残っていれば違反として別に数える
- この段階で答えられるのは「読まない依頼者のもとで、どの工程がどれだけ判断を引き出すか」だけで、H2 から H5 (plan、plan-implement、安い実装者、後の変更) は測らない。実際の人の注意力も測らない

## 第 3 段階: 一覧と草案を読む依頼者役のもとでの spec

### 測ること

第 2 段階では、spec を問いにだけ答える依頼者役 (question-only) のもとでしか走らせていない。ask と draft は両方の依頼者役で走らせたので、依頼者役の規則による差は分かる (ask は 11 件対 6 件)。spec は片方だけなので、「一覧を読んで直す依頼者がいれば ask で足りるか」に答えられない。そこで spec を review-all で 3 回走らせ、第 1 段階の ask と draft と比べる。

### 走らせる前に直したもの (第 2 段階の監査で見つかった不備)

- question-only の規則に「選択肢の説明や得失も読まない。前提が違うを選ぶのは、問いの文が求める論点について意図が選択肢と食い違うときだけ」を足した。共通の規則とのぶつかりを解くためで、この段階 (review-all) には効かない
- 判定の指示に「次のラウンドで聞く予定のような予告は STATED」を足した。一度 ASKED と判定された判断は判定し直さない。依頼者役が一度知った意図は忘れさせられないためで、この作りは変えない
- 返信の最後の行が DONE でも、やり取りを終える。説明文が開発者に届かないようにするため

保存済みのメッセージで確かめた。DONE の前に説明文が付いた返信は終わりと読まれた。予告は STATED と判定された。第 2 段階の spec の 1 回目で違反になった問いには、question-only で先頭の選択肢を選び、問われていない決まりを書かなかった。

第 1 段階の ask と draft は、この 3 つを直す前に走らせた。判定の指示の追記で「触れていない」が STATED に変わると、review-all では依頼者役が潜在の意図を知る時点が早まり、捕捉と先漏れの両方に効きうる。DONE を最後の行でも認めると、答えのあとに DONE を付けた返信では答えも開発者に届かない。その返信は `exchanges.jsonl` に `trailing_done` として残し、監査で本文を読む。

実行前のレビューを受けて、STATED の判断も review-all で判定し直すようにした (ASKED は「一度でも ASKED と判定された」の意味になる)。

### 走らせていない理由

実行前のレビューで、この段階は問いに答えられない作りだと分かった。第 1 段階の ask は全回 11 件で、判断は 12 件しかないので、spec が全回 12 件を取っても中央値の差は 1 件にしかならず、「差あり」の基準 (2 件以上) に届かない。結果は「示せなかった」か「spec が ask より少ない」のどちらかになる。潜在の判断に触れた数も、ask が 4 件なので同じである。この段階で分かるのは費用、読む量、捕捉の出どころ、ASKED だけで、約 $55 に見合わないと判断し、走らせる前に止めて旦那様に諮った。

## 第 4 段階: plan と plan-implement の価値

### 測ること

- H2 (plan の工程): 同じ spec から plan を作って実装したとき、spec だけから実装したときより捕捉や性質テストが増えるか
- H3 (plan-implement): 同じ plan を plan-implement で実装したとき、プラグインなしで実装したときより性質テストや捕捉が増えるか

### 天井の問題と、測り方の選び方

Opus 5.5 xhigh の実装は、文書の無い guess でも性質テストが全回 100% だった。上の止めどころ (「guess の性質テストがすべて 100% なら full を走らせない」) により、xhigh の full は走らせない。捕捉も、spec の取りこぼし 2 件 (PaidCancelBlocked, WeekendShift) は仕様書に意図と逆の決まりとして書かれているので、plan や plan-implement が覆す見込みは低い。差が出る余地は次の 2 つにしか無い。

1. 実装者を弱くする (sonnet / medium、だめなら haiku / medium)。「仕組みが安いモデルに足りないものを補うか」を測ることになる
2. 既存の plan-implement-* ケース (spec と plan が揃っている小さな機能) で、プラグインなしの Opus xhigh が落ちるもの

どちらにも余地が無ければ、そこで止めて「このケースと実装者では差を示せる余地が無い」と書く。

### 手順

1. 走査 (校正と同じく本番に数えない。約 $25)
   - a. `compare.py --arms plain` (Opus xhigh) を、まだ 3 回以上走らせていない plan-implement-* の 8 ケース (basic, boundary, e2e-cli, external, glossary, mixed, review-fix, split) で各 3 回。table-gap は grader が plan-implement の手順を採点するので除く (compare.py の既定)
   - b. 分割払いの guess を sonnet / medium で 2 回、haiku / medium で 2 回
   - c. 第 2 段階の spec 3 回の pre-impl を、`--replay` で sonnet / medium で 1 回ずつ実装し直す
2. 走査のあとの分かれ道
   - a のうち、隠しテストか結果を見る grader (asks-go, no-deadline など。tool_used は compare.py が使わない) で 3 回中 1 回でも落ちたケースがあれば、そのケースで `--arms crystallize` を 3 回走らせる
   - 分割払いの実装者の強さ L は、sonnet / medium の 5 回 (b の 2 回と c の 3 回) のどれかの性質テストが 95% 以下なら sonnet / medium にする。そうでなく haiku / medium の 2 回のどちらかが 95% 以下なら haiku / medium にする。どちらも無ければ分割払いの H2, H3 は 3 以降を走らせない
3. H2 の文書: 第 2 段階の spec 3 回から `--branch` で crystallize を 3 回 (`--oracle-rule question-only`、Opus xhigh)。plan の工程の依頼者役は第 2 段階と同じ規則で、元の回が知った潜在の判断を引き継ぐ。実装は Opus xhigh のプラグインなしで、xhigh での H2 (捕捉と性質) になる
4. L での比較 (3 の plan を使う)
   - H3: 3 の各回から `--branch` で full を L で 1 回ずつ。比べる相手は、同じ plan を `--replay` で L のプラグインなしが実装したもの (各 2 回)
   - H2 (L): 3 の plan を L で実装したもの (上の各 2 回) と、元の spec を L で実装したもの (c の 1 回に 1 回足して各 2 回)
   - 同じ文書の 2 回の差を、実装のばらつきとして書く

### 費用

見込みは走査 $25、3 が $60、4 が L = sonnet で約 $50 (full は 1 回 $10〜15 と見込む)。合計約 $135 で、$150 を超えそうなら止めて報告する。`-j 3` まで。

### 交絡として書くもの (直さない)

- plan-implement の code-generator は frontmatter で sonnet に固定されている。xhigh の比較なら「plan-implement はスライスの実装を sonnet に書かせ、フェーズ 3・4 の修正は統括役 (Opus) 自身が書く」形になる。L = sonnet なら揃う。L = haiku なら full のコードは sonnet が書くので、full の側だけ強いモデルが混ざる。このときは差があっても仕組みの効果とモデルの差を分けられないと書く

- full が go / no-go より前に止まった回 (差し戻しの上限、変更前から落ちるテストなど) は ERROR にせず、その時点の作業ツリーを採点し、止まった理由を書く

### 実行前の予想

- a はどのケースもプラグインなしで通る (前回の midsize, judgment, conflict と同じ)

## 第 5 段階: 問いだけの短いラウンドレポート

### 測ること

第 2 段階の spec が依頼者役に見せた文字数は約 3 万字で、ask の約 15 倍だった。依頼者役は前提欄も選択肢の説明も読まない規則で、それでも 10, 8, 10 件取れた。そこで、ラウンドレポートを問いだけ (問いの文 1 文、選択肢の label 1 行、推奨の理由 1 行、「前提が違う」) にしても捕捉が落ちないかを測る。

この依頼者役は元のレポートでも説明を読まないので、測れるのは開発者側の変化 (前提や得失を書けなくなったとき、同じ判断を問いとして出すか、黙って決めるか) と、見せる量と費用である。人間が説明なしで答えられるかは測れない。

### 版

`variants/short-report/` に、plugin のファイルを差し替える 3 つを置いた (`skills/spec/SKILL.md`、`skills/html-report/SKILL.md`、`skills/html-report/references/templates.md`)。
- spec: 問いの素材は `id` / `title` / `question` / `recommended` / `reason` / `options[{id, label}]` と range の項目だけ。`frame`・`premise`・`gain`・`loss`・`exhibit` は書かない。試問は項目 1, 3, 4, 5, 7 だけ。ラウンドレポートから選ばれた答えには復唱をしない (元の版も、得失が選択肢の直下にあれば復唱しないので、往復の数を揃えるため)
- html-report: round の型を問いだけにする。素材に前提や得失があっても出さない
- 仕様書 (Step 4) と、チャットに書くメッセージは変えない

`upstream.py --variant short-report` は plugin を `/private/tmp` に写し、上の 3 つを差し替えて読み込む。結果の行に `variant` を残す。
