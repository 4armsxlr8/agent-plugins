# コミット粒度の作法

1 コミットに論理的な変更を 1 つだけ入れるための基準。plan-commit が「1 plan = 1 コミット」の原則から外れて分割コミットを選ぶときに、この基準で切り分ける。

## 論理単位の分類基準

差分に含まれる変更をファイル単位ではなく「変更の意図」単位でグルーピングする。1 つの意図に複数ファイルがまたがるのは自然だが、1 ファイルの中に複数の意図が混在している場合は、その差分自体を分けて考える。グルーピングの妥当性は次の 3 つで判定する。

- **機能的独立**: その変更だけを他の変更なしに適用しても動くか。動かない (別の変更が前提になる) なら同じグループ
- **レビュー容易性**: できあがった diff だけを見て、変更の意図がすぐわかるか。わからないなら、意図が異なる変更が紛れ込んでいる
- **追跡可能性**: 後から `git log` や `git blame` でこの変更だけを探し出せるか。無関係な変更と一緒くたになっていると、狙った変更だけを追えない

## コミットメッセージの形式

Conventional Commits に従う。

```
<type>(<scope>): <説明>
```

- `type` は `feat` / `fix` / `refactor` / `docs` / `test` / `chore` / `style` / `perf` / `ci` / `build` のいずれか
- `scope` は変更が触る領域 (省略可)
- 説明は 1 行で、そのコミットが「何を」変えたかを言い切る

## 適正粒度の判定サイン

切り分けが適切かどうかは、次の 4 つのサインで確認する。どれか 1 つでも引っかかったら、その粒度を見直す。

1. **要約行を書くのに「と」「ほか」のような接続語が要るなら分割サイン**: 1 コミット 1 意図が原則。要約が素直な一文で書けない差分は、まだ複数の論理変更を抱えている
2. **1 画面のスクロールで意図を追えるかどうか**: 追えないほど大きい差分は、たいてい「準備のための整理」と「本体の変更」のような段階に分けられる。段階ごとに分けると、それぞれが読める大きさに戻ることが多い
3. **同じファイルでも意図が違えば別コミット**: 逆に、1 つの意図の変更が多数のファイルに散らばること自体は分割の理由にならない。意図が 1 つなら、ファイル数が多くても 1 コミットでよい
4. **そのコミットだけを単独で revert できるか**: できないなら、論理単位の境界の引き方を間違えている。この revert 可能性が独立性の一番実地に近いテストになる
