# spec

実装に着手する前に、作成する対象の要件をユーザーと合意し、仕様書 (`docs/crystallize/specs/<slug>.md`) にまとめるためのスキルです。
仕様書 (spec) は実装手順ではなく要件を記述する文書であり、リポジトリに保存されて改訂履歴を持ちます。実装手順は後続の `/plan-create` が別の文書として作成します。

要件は一度作成して終わりではなく、開発の進捗に応じて更新していくものです。事前の確認をどれほど綿密に行っても、UI は実際に操作して初めて気づく点があり、リリース後の利用者の意見によって変更されることも一般的です。仕様の遵守とは、無断で仕様から逸脱しないことであり、一切の変更を拒むことではありません。

この前提のもと、本スキルの目的は「変更されない仕様書」を作成することではなく、「現時点で判明している要件に漏れがなく、変更が生じた際に基準として立ち返ることができる文書」を作成することにあります。すべての事象を過剰に網羅することよりも、判断の理由と、その判断によって除外された挙動を追跡できる状態を目指します。

## Input / Output

- **Input**: `$ARGUMENTS` = タスクの説明。省略された場合は直前の会話内容から推定し、1行で確認を取ります。既存 spec のパスが渡された場合は **改訂モード** として動作します (Step 0 参照)。**複数のタスクを同時に指定することも可能ですが、3件を上限とします** (それ以上指定するとセッションが長文化し、各論点が本来の目的から逸れやすくなります)。複数の場合も各タスクに対して Step 0〜4 をすべて実行し、仕様書を1件ずつ作成します。集約するのは対話の機会であり、要件検討の深さは省略しません。`$ARGUMENTS` に `audit: on` が含まれる場合は、その文字列を除外した残りをタスクの説明として扱い、Step 2 の質問監査を有効にします (除外しない場合、slug やタスク要約に混入します)。slug は目的を表す1文から英小文字とハイフンを用いて3〜5語で作成します (例: `share-card-link`)。後続の plan、plan-implement、plan-commit、diff-review でもこの slug を継続して使用します。
- **Output**: `{projroot}/docs/crystallize/specs/<slug>.md` (spec 本体。成果物として残ります)。作業用ファイルは `{projroot}/docs/crystallize/specs/<slug>/` 配下に作成します。

| ファイル | 寿命 | 中身 |
|---|---|---|
| `docs/crystallize/specs/<slug>.md` | 残る | **最終成果物**: spec 本体 (改訂履歴つき) |
| `docs/crystallize/specs/<slug>/ledger.md` | 残る | design tree (検討事項と依存関係) / 確定事項 / 監査記録 |
| `docs/crystallize/specs/<slug>/mock.html` | 残る | **ラウンドシート**兼確認用モック (1タスクにつき1ファイル。同一ファイル内で各案を切り替え、質問と回答パネルも同じ画面に配置します。検討ラウンドを通じて同一ファイルを更新します) |
| `docs/crystallize/specs/<slug>/question-round-<n>.md` | 残る | 質問監査を行った場合のみ作成する監査用入力ファイル (Step 2)。シートの QUESTIONS 宣言から生成します |
| `docs/crystallize/specs/<slug>/eval-context.json`, `eval-question-round-<n>.json` | 残る | 質問監査を行った場合のみ作成する監査の context と eval JSON (Step 2)。監査件数の正式な記録は ledger に記載されるため、再参照する必要はありません |
| `docs/crystallize/CONTEXT.md` (配置場所の判定は Step 0) | 残る | **用語集**: プロジェクト全体で単一の正本として管理する用語集。複数の spec にわたって継続的に更新されるため `<slug>/` の外に配置します。**更新を行うのは `spec` のみ**です。例外は `plan-implement` の仕様改訂フローのみであり、その際の plan-implement は spec の編集処理を代行しています (更新者を増やすと、同一用語の定義が複数箇所で個別に追記され、表記や定義の揺れが生じるためです)。 |

## 最重要禁則

1. **プロダクトコードの作成および編集を行わないこと**。書き込みを許可する対象は、`docs/crystallize/specs/<slug>.md`、`docs/crystallize/specs/<slug>/` 配下のファイル、および用語集 (Step 0 で特定した `docs/crystallize/CONTEXT.md` またはリポジトリ直下の `CONTEXT.md`) のみです。
   理由: コードの記述を始めた時点で、作成済みのコードを正当化するバイアス (サンクコスト効果) が生じ、客観的な要件の検討が阻害されるためです。実装作業は、spec と plan の合意が完了した後の別セッションで実施します。例外: `html-report` が生成する `docs/crystallize/reports/` 配下の HTML ファイル (報告用の一時的な表示形式であり、成果物ではないため)。hook による制御へ移行する場合も、このパスおよび用語集はブロック対象から除外します。
2. **会話のテキストのみで合意を確定させないこと**。前提とされている認識や細かな選好は、言語的な質問だけでは表面化しないことがあります。各 Step では必ず具体的に確認可能な成果物 (モック、代替データ、spec の草案) を提示し、それに対する確認結果をもって合意とします。

## Step 0: 既存文書との突き合わせ

初めに**用語集の内容を確認します**。ファイルの配置場所は以下の優先順位で特定し、以降の全 Step において特定された単一のファイルを用語集として参照・更新します。

1. リポジトリ直下に `CONTEXT.md` が存在し、その中に `## 用語` または `## Language` の見出しが存在する場合は、**それを正本とします**。この場合、`docs/crystallize/CONTEXT.md` は作成しません (リポジトリ直下の `CONTEXT.md` を利用する他の運用と共通のファイルを参照するためです。用語集が複数存在すると、参照すべき基準が判断できなくなります)。
2. 上記に該当しない場合は、`docs/crystallize/CONTEXT.md` を正本とします (リポジトリ直下に `CONTEXT.md` が存在していても用語の見出しを持たない場合は用語集ではないため、異なる目的のファイルに用語を追記してはいけません)。
3. いずれも存在しない場合は、現時点で用語集は存在しません。この時点では新規作成を行いません (Step 2 において最初の用語が確定した段階で `docs/crystallize/CONTEXT.md` に新規作成します)。

続いて `docs/crystallize/specs/` 配下の既存 spec を確認し、**今回のタスクと同じ画面、モジュール、またはデータを扱う仕様書**を読み込みます。**用語集が存在しない場合、または用語集を本 spec で初めて利用する場合 (Step 2 における既存用語の移行のため) に限り**、それらの仕様書の「用語」節も確認します。すでに用語集が存在する場合、用語の正本は用語集側にあるため、spec 側の用語節はその spec で決定・変更された用語の記録に過ぎません (spec の件数が増えるほど各 spec の用語節を確認する負荷が増加し、同一用語に対する定義の不一致が発生しやすくなります)。

- 既存 spec の記述と今回の依頼内容に齟齬がある場合は、**最初のラウンドにおける質問事項として提示します** (例: 「既存 spec では X を Y と定義していますが、今回は Z に変更しますか」)。この段階で確認しなかった矛盾は、実装段階で手戻りが発生する原因となります。
- **用語集の語、ソースコード内の識別子、および今回の依頼で使用されている語の間に生じている齟齬**についても同様に質問として確認します (例: 「用語集では X を Y と定義していますが、今回の文脈では Z を意味していますか」「コード内では X を Y と命名していますが、用語集の Z と同一の概念ですか」)。用語の修正は合意を得た後に実施し、どちらが正しいかを独自に判断してはいけません。不一致の検出は用語集を基準に行います。**各用語およびその用語の「使わない語」に指定されている同義語を識別子として `grep -rin` で検索し、コード内でどのように命名されているかを確認します** (依頼文の語句から逆引きした場合、用語集にのみ残っている不要な用語やコードとの乖離を検出できません)。用語集が空または存在しない場合、この検索手順は不要です。
- コードの実装とユーザーの説明に食い違いがある場合も、同様に質問として確認します。
- 既存 spec および用語集の双方が存在しない場合は、本 Step を1行の記録 (「既存 spec・用語集なし」) で終了します。

**改訂モード** (`$ARGUMENTS` に既存 spec のパスが指定された場合): 仕様書全文の再作成は行いません。

1. 既存の spec を読み込み、**仕様書の記述と現在のコードベースに乖離がないか**を事前に確認します (仕様書を保持・管理し続ける場合、実装との乖離が発生しやすいため、改訂時には必ず確認します)。乖離が確認された場合は、改訂履歴に「リリース後」の変更として1行記録します。**用語集の語とコード内の識別子との齟齬**についても、同様にこの確認対象に含めます。用語集も保持される文書であるため、確認を怠ると spec と同様にコードの実態と乖離します。用語の修正は質問を通じて合意を得た後に行い、独自に判断して変更してはいけません。
2. 今回の変更対象となる要件のみを design tree として構造化し、差分となる論点のみを Step 2 の質問ラウンドで扱います。
3. 変更した項目を改訂履歴に追記します。変更のない節は修正しません。

## Step 1: design tree の初期化と blindspot

タスクの内容を1行で要約し、`docs/crystallize/specs/<slug>/ledger.md` を作成します。この管理台帳は以下の3つの節で構成します。

| 節 | 中身 |
|---|---|
| design tree | 検討事項 (論点) と、その論点が前提としている別の論点 (依存関係)。決定済みの論点には完了の印を付けます |
| 確定事項 | 決定した事項と、その決定理由および採用を見送った代替案による影響 |
| 監査記録 | 質問総数 / 監査実施数 / 不合格数 / 不合格の理由 (Step 2) |

Explore subagent を実行してコードベースの調査を行い、その結果を「ユーザー側でまだ想定されていない可能性がある論点」として整理し、tree に追加します。

- 調査対象: タスクに関連する既存の実装、命名規則や設計構造の慣習、過去の設計判断、変更によって影響を受けやすい箇所。
- **コードベース調査の完了を待たずに Step 2 へ進みます**。調査の完了を待機すると確認の開始が遅れ、質問の質も向上しません。具体的には、(a) バックグラウンド実行が可能な環境では Explore をバックグラウンドで起動し、即座に第1ラウンドの確認事項を提示します。(b) バックグラウンド実行ができない環境では、依存関係のない論点のみで第1ラウンドを提示し、**ユーザーが回答している間に** Explore を実行します。いずれの場合も、調査結果に依存する質問は次のラウンドに回します。
- 親エージェントは調査結果の要約のみを受け取ります (調査の詳細なログを親コンテキストに直接取り込みません)。
- 一般論としての注意点は論点として扱いません。対象のコードベースの実態に即した具体的な論点のみを扱います。

**各ラウンドの開始時に ledger 冒頭のタスク要約を再確認します**。確認プロセスが長期化すると、個別の論点が本来の目的から逸脱しやすくなります。要約に照らし合わせて不要と判断できる論点は深追いせずに除外します。

## Step 2: grilling ラウンド

design tree の **frontier** (前提となる論点がすべて解決済みの未決定事項) を抽出し、**1つのラウンドにまとめて番号付きで提示します**。未確定の論点の回答に依存する質問は、次のラウンドに回します (依存関係に基づいて段階的に整理されるため、1問ずつ順に質問する必要はありません)。

**事実に関する確認と、方針の決定に関する確認を明確に区別します**。コードベースの実装状況、API の仕様、ライブラリの機能の有無、プラットフォームの制約などは客観的な事実であり、ユーザーの好みの問題ではありません。これらは Explore、WebSearch、WebFetch、公式ドキュメントなどを用いて自ら調査して確認します。ユーザーに確認するのは方針、選好、および優先順位のみです。客観的事実をユーザーに質問すると、不確かな推測による回答が確定事項として記録される原因になります。

### 出し方 — ラウンドシート (HTML) と貼り戻し

各ラウンドの質問は、**ラウンドシート** `docs/crystallize/specs/<slug>/mock.html` に反映してブラウザで提示します。回答は、ユーザーがシート上の [貼り付ける文章を作る] 機能で生成した定型テキストをターミナルに貼り付ける形で受け取ります (書式は `references/reply-format.md` に準拠)。シートの実体はモックキット (`references/mock-kit.md`) であり、案 (variant)、調整パネル、回答パネルが同一画面に統合されています。**画面表示の確認場所と回答の入力場所を分離させない構成とします**。ターミナルの対話式プロンプトで回答させると、選択時に画面を確認できず、案の採否や理由が自由文となってエージェントの解釈の差異が生じやすくなります。

- **1 ラウンド = 1 回の確認往復**とします。質問内容と、そのラウンドで確認する表示内容 (各案、調整パネル、代替データ) を同一シート上に配置します。質問はシート内の `QUESTIONS` 定義に記述します (`id` / `title` / `question` / `premise` / `recommended` / `reason` / `options[{id, label, gain, loss, variant?, rejected?}]`)。後述の質問フォーマットの4要素を反映させます (`question` = 質問文、`premise` = 前提条件、`gain` / `loss` = 各選択肢で得られる挙動および失われる挙動、`recommended` + `reason` = 推奨する回答とその理由)。**`QUESTIONS` および `ROUND` の定義は親エージェントが記述します** (モック案の生成自体は Step 3 でサブエージェントに委任しますが、質問の構成は親エージェントの責務です)。案を選択させる質問には選択肢に `variant` を指定します。これにより、選択した瞬間に表示がその案に切り替わり、画面を確認しながら選択できます。各案の `data-variant` および `data-variant-name` は親エージェントが委任前に決定して指定します (命名が不一致の場合、選択しても表示が切り替わらず、不具合に気づきにくくなります)。案が存在しないシート (画面表示の作成前である第1ラウンドなど) では、親エージェントがキットを複製し、`QUESTIONS` のみを作成します。
- **同一の値を質問と調整パネルの双方に重複して配置しないこと**。`TWEAKS` にキーが存在する数値や程度の項目 (余白、件数、色、アニメーション速度、閾値など) は `QUESTIONS` として扱いません。これらの決定値は、回答テキストの `調整パネル:` 行から取得します (値の基準は調整パネル側にあるためです)。両方に配置すると回答テキストに同一項目の値が重複して出力され、整合性を手動で合わせる必要が生じます。調整を依頼したい項目は個別の質問にせず、シートを開く際の案内文で調整対象として明記します。
- **推奨案はあらかじめ選択された状態で提示します。無回答 (未選択) の項目は、推奨案を採用したものとして確定します。** ユーザーは推奨案と異なる方針を希望する項目のみを変更すれば完了します。「選ばない (お任せに戻す)」の選択も同様に推奨案への委任として扱います。
- **1 ラウンドあたりの質問数は 3±1 問とし、5問以上を同時に提示しないこと**。回答者の判断負荷を抑えることが重要です。frontier に該当する論点がそれ以上存在する場合は、設計全体への影響が大きい順に選定し、残りは次回以降のラウンドに回します (ラウンド数が増加することは問題ありません。1回の確認負荷が大きいと、合意形成プロセス全体が停滞します)。
- **同一のファイルを複数のラウンドにわたって更新します**。`ROUND.round` の値を更新し、前回のラウンドで決定した質問は削除します。**前回のラウンドで不採用となった案は、取り消し線を付与して保持します** (`.cz-variant` に `data-rejected` を指定し、`data-variant-name` の先頭に「(不採用)」を付与)。解決済みの論点をさらに詳細化して再度質問する場合は、除外された選択肢を削除せず、`rejected: true` を指定して取り消し線の状態で残します。いずれも、過去の検討経緯を記憶に依存せず確認できるようにするためです。
- 質問数が0件 (モックの確認のみを求める場合) や、案が0件 (画面表示を伴わないラウンド) の場合であってもシートを出力します。案が存在しない場合、回答パネルが表示領域に直接配置されます。画面表示を伴わないタスクの代替確認物 (API レスポンスの例、CLI の出力例など) は、フレーム内に静的テキストとして配置します。
- **回答テキストがターミナルに入力される前に、次のラウンドや Step 4 に進んではいけません**。確認工程を設ける目的が失われます。待機中は、Explore の調査結果の整理など、回答内容に依存しない作業を進めます。
- 回答テキストは `references/reply-format.md` の規則に従って解析します。`(未選択 = お任せ)` となっている項目は推奨案で確定します。「見ていた案」および「調整パネル」の行には、ユーザーが最後に表示していた案と設定値が記録されているため、案の採否に関する回答と矛盾がある場合は再度確認します。「全体へのコメント」に設計変更を伴う指摘が含まれている場合は、design tree に論点として追加します。
- **フォールバック**: ブラウザを開くことができない環境 (SSH 接続、コンテナ環境、`open` コマンドが利用できない場合など) では、絶対パスおよび `file://` 形式の URL を提示してユーザー側で開くよう案内します。それも不可能な場合に限り AskUserQuestion による対話に切り替えます。この場合も前述の4要素を質問文と選択肢の説明に反映し、1回あたり4問までとします。focus mode では AskUserQuestion の呼び出しで終了するターンの通常出力が表示されないため、同一ターン内で通常の質問文と混在させないようにします。この代替手順を用いた場合でも、決定事項の確認の復唱は省略しません。

### 試問 — シートを見せる前の検査

シートを提示する前に、**事前文脈を持たない subagent** (Agent ツール、general-purpose を使用。fork は既存のコンテキストを引き継ぐため不可) に対し、シートの絶対パスと読者設定の1行 (対象読者 + 前提知識なしで使用してよい用語) のみを渡し、**同期処理で検証結果を待ちます**。作業の背景、コードベース、これまでの対話内容は渡しません。仕様の作成者はすべての背景情報を把握しているため、第三者に正確に伝わるかどうかを客観的に自己評価することが難しいためです。質問が1問以上存在するラウンドでは必ずこの検査を実施します。検査項目は以下の5点です。

1. **弁別性** — 各質問において、選択肢ごとの表示や動作の違いが、シートの記載のみから理解できるか。`variant` が設定された選択肢については、対応する `data-variant` の HTML 構造を比較し、各案の設計が実際に異なっていると判断できるか (ブラウザ表示ツールがある環境では表示を切り替えて確認してよいですが、ツールがない環境でも HTML を直接確認して判定できる必要があります)。明確に区別できない質問を指摘します。
2. **実質的な選択肢の有無** — 推奨案以外の選択肢を選ぶ客観的な利点 (`gain`) が明記されているか。利点が不明瞭な質問を指摘します (そのような質問は実質的に選択を求めていません)。また、単に `TWEAKS` の設定値を並べ替えただけの質問も指摘します (調整パネルと機能が重複しているためです)。
3. **可読性** — 読み上げた際に不自然な表現や、意味が通じない箇所を原文のまま指摘し、内容の要約を3文以内で記述できるか確認します。
4. **専門用語・非標準語** — 読者設定で許可された語句以外で、説明なしに使用されている専門用語や独自の造語を列挙します。
5. **足す方向への偏り** — 選択肢がすべて何かを追加する方向で、現状のまま・何かを削る・対象を狭めるといった選択肢が1つも無い質問を指摘します。質問は実装案の分岐点から作られるため、作成側は「どう作るか」の選択肢しか思いつかず、「作らない」「既にあるものを外す」で論点が消える可能性を見落としやすいためです。前提行に削れない理由が書かれている質問は指摘しません。

検証で問題が指摘された質問は修正します。弁別性が不十分な場合はモックの追加や各案の構造の見直しを行い、`gain` が成立しない場合は実質1択であるため質問を取り下げて推奨案で確定し、調整パネルと重複する質問は取り下げて値の指定を `調整パネル:` 行から受け取るようにし、独自の用語は注記の追加ではなく一般的な用語へと書き換えます。足す方向への偏りを指摘された質問は、削る選択肢に `gain` が成立するならそれを選択肢に加え (論点ごと消えるなら質問を取り下げて「削る」を確定事項にします)、成立しないならその理由を前提行に1文で書きます (「削る選択肢が無い」ことをユーザーにも見せるためです。`gain` の無い選択肢を形だけ足すことは検査項目2に反します)。再試問は同一の subagent に対し変更差分のみを渡して1回実施し、**合計2回で完了とします**。2回目の検証で残った指摘が軽微な表現に関するものであればそのまま提示します。重大な問題 (選択肢の違いが判断できない、文章の意味が通じないなど) が残っている場合は、3回目の試問には進まず、読者設定から見直してラウンド全体を再構築します。修正を重ねても改善しない場合は、論点の整理自体に問題があるためです。試問は後述の質問監査を代替するものではありません。質問監査が前提と二者択一の論理的整合性を検証するのに対し、試問は読者への伝わりやすさを検証します (文面のみで判定可能な可読性と専門用語の有無については、質問監査においても `legibility` として評価されます)。

### 質問フォーマット

```
Q<n> <題>
前提: <この質問が前提にしていること。違っていたら前提側を撃ってください>
質問: <挙動の選択肢として書く。技術の選択肢にしない>
選択肢: 各選択肢に「選ぶと得られる挙動」と「選ぶと失われる挙動 (否定形)」を1行ずつ
推奨: <推奨する答えと理由1文>
```

この書式は、4つの規則 (1 前提の検証 / 2 二者択一の成立理由の提示 / 3 前提条件の明示 / 4 採用しなかった場合の制約の明示) のうち、3つを構造的に担保するためのものです。**規則 1 前提の検証** (明文化できない不確かな前提は事前に調査してから記載する)、**規則 3 前提条件の明示** (前提行への記載)、**規則 4 採用しなかった場合の制約の明示** (選択肢における否定形での挙動記述)。自由記述の形式にすると記載が省略されやすいため、必須の行として固定します。

残る **規則 2 二者択一の成立理由の提示** は書式のみでは担保できないため、以下の手順を守ります。「A と B のどちらを優先するか」を問う質問は、**それらを同時に成立させることができない技術的・論理的理由を1文で説明できる場合にのみ提示します**。説明できない場合は成立しない二者択一であるため、双方を両立する設計を先に検討します。両立案と並んで、**既存の何かを外す・何も足さずに現状のままにすることで A も B も不要になる引き算案**も同じ扱いです。成立するなら二者択一ではなく、引き算案を選択肢に加えるか、論点ごと取り下げます。

「推奨」の行は恣意的な誘導ではなく、効率的な合意形成のための設計です。推奨案の提示がない質問はユーザーに設計を委ねる形になり、判断を保留する回答につながりやすくなります。推奨案に対する明確な合意や反対の意見を得ることが重要な判断材料となります。

### 選択の確定 (失われる体験の復唱確認)

複数の案の中からユーザーが1つを選択した際は、不採用となった案によって**提供されなくなる挙動を否定形の1文**で再度確認し、明確な同意を得てから確定事項として記録します。例: 「この選択肢を採用した場合、共有リンクを受け取ったユーザーは作品の一覧ページを閲覧できず、該当画像のみの表示となります。この方針で確定してよろしいですか」

- 選択を行う際、ユーザーは採用する案の表示に注目しているため、選択肢に制約事項が記載されていても、確定の直前に否定形で再確認しなければ制約の影響が十分に認識されないまま進行する恐れがあります (実例: 「画像のみ表示」という選択肢で確定したにもかかわらず、後続の確認において「リンク先で一覧も表示される想定だった」という認識の齟齬が判明した事例があります)。
- **確認を省略できる条件**: シートの回答パネルから選択され、その選択肢の `loss` 行 (提供されなくなる挙動の否定形) が選択肢の直下に明記されていた場合。この場合はすでに制約を確認した上で選択されているため、再確認を行うと同一内容の重複確認となり往復が増加するだけとなります。`loss` が空欄であった質問、代替手段である AskUserQuestion を経由した場合、および会話で直接指示された場合は省略できません。
- **「案 A を先行してリリースし、反応を見てから案 B を検討する」といった段階的な導入方針をとる場合は、上記の省略条件を満たしていても再確認を必須とします**。ユーザーの想定内に後続の案の挙動が残ったまま合意されるケースが多いためです。
- 再確認に対して合意が得られなかった場合は、不採用への差し戻しとして扱います。ledger の該当する確定事項を未解決の状態に戻し、再度要件を確認します。

### 語の確定 (用語集への書き込み)

検討の過程で用語に関する決定が行われた場合 (新規用語の定義、既存用語の意味の変更、同義語の統一など)、**その場で用語集に反映します**。具体的には、**回答を受け取った同一ターン内で、次のラウンドの質問を作成する前に用語集ファイルを更新します** (次の質問を作成した後に更新しようとすると記載漏れが発生しやすく、次のラウンドで用語の不一致を確認する基準も失われます)。用語を記述する際の5つの原則は Gotchas に記載されています。

用語集が存在しない場合は、**最初の1語が決定した段階でファイルを新規作成します**。空の用語集ファイルを事前に作成してはいけません。内容のないファイルは参照されず、利用されないファイルは標準として機能しなくなります。**本仕様書において既存の用語集を初めて利用する際は、既存の各 spec の「用語」節に記載されているプロジェクト固有の用語をこの段階で用語集へ移行します**。これは用語集ファイルを新規作成した場合だけでなく、リポジトリ直下の `CONTEXT.md` を用語集として初めて利用する場合も含みます (移行処理は「用語集ファイルが作成された時点」ではなく、「本仕様書の検討で用語集を初めて参照した時点」で実施します。用語集を参照し始めた後は各 spec の用語節を個別に確認しなくなるため、移行されなかった用語は参照対象から外れてしまいます)。すでに用語集内に同一の用語が定義されている場合は上書きしません。spec ごとに定義が食い違っている用語も直接移行せず、次のラウンドの確認事項として扱います。書式は以下の通りです。

```markdown
# <プロジェクト名 (またはコンテキスト名)>

1〜2 文で、この用語集が扱う範囲。

## 用語

- **<語>**: 何であるかを 1〜2 文で。 _使わない語_: <同義語 1>, <同義語 2>
- **<語>**: …

### <自然なまとまりがあれば小見出し>
- …
```

### 質問監査 (任意)

`$ARGUMENTS` に `audit: on` が指定されているか、またはユーザーから質問監査の指示があった場合に限り、**ラウンドごとに1回** `question-evaluator` (Skill ツール、fork 実行) による監査を実施します。

- 当該ラウンドのすべての質問を、前述のフォーマットを維持したまま `docs/crystallize/specs/<slug>/question-round-<n>.md` に書き出します (先頭にタスクの1行要約を記載)。**シートの `QUESTIONS` 定義から直接変換して生成します** (`question` → 質問行、`premise` → 前提行、`options` の `gain` / `loss` → 選択肢行、`recommended` + `reason` → 推奨行)。同一の質問内容を複数の場所で手作業で記述すると、監査対象の文章とユーザーに提示した文章との間に差異が生じます。先頭にはタスク要約に加え、試問と同様の読者設定の1行を記述します (監査における `legibility` の評価と、試問における用語判定の基準を一致させるためです)。実行時は context JSON を `docs/crystallize/specs/<slug>/eval-context.json` に作成して渡します (`project_dir` / `plan` = 質問ファイルのパス / `output_contract.eval_file` = `docs/crystallize/specs/<slug>/eval-question-round-<n>.json`)。質問ファイルのパスのみを渡すと例外処理に入り、eval JSON がプロジェクト直下の `output/` に出力され、後続の `plan-commit` で誤って Git の管理対象に含まれる原因になります。具体的な実装案や ledger の内容は渡しません。実装案を含めると、監査側も同一の前提に影響を受け、客観的な評価が行えなくなります。
- `passed: false` が返された場合は、`feedback_structured` で指定された質問のみを前提の再検証からやり直し、そのラウンドの監査を再度実行します。指摘を受けていない質問は修正しません。
- **再監査は1回までとします**。2回連続で `passed: false` と判定された質問は、3回目の修正を行いません。残った指摘が軽微な表現上の問題であればそのまま提示し、重大な問題 (前提条件の誤りや、不当な二者択一など) である場合は、質問を取り下げて調査し直すか、前提条件自体に誤りがないかをユーザーに直接1行で確認します (`plan-create` における2回連続不合格時の停止基準と同様の扱いです。文面の推敲を繰り返しても、前提条件自体の誤りは解決しないためです)。
- **監査の実施有無にかかわらず、ledger の監査記録に実績件数を残します** (質問総数 / 監査実施数 / 不合格数 / 不合格理由)。任意としている監査機能を将来的に必須とするか廃止するかは、この実績データが一定数蓄積された後に判断します。記録がない状態では、監査機能の有効性を検証できません。

### 終了条件

frontier が空になり (仕様や挙動の変更を伴う未解決の論点が完全に解消され)、かつユーザーから「認識が揃った」旨の明確な同意が得られた段階で終了とします。いずれか一方のみでは終了しません。論点一覧が空であってもユーザーに懸念が残っていれば論点の漏れが存在し、ユーザーが合意を希望しても論点一覧に未解決事項が残っていれば実装時に問題として表面化するためです。

**Step 2 と Step 3 は交互に繰り返します**。モックの確認によって新たに浮上した論点は design tree に追加し、前提条件が解決した段階で次のラウンドの質問として扱います。終了条件の判定は、モックへのフィードバックによって追加された論点も含め、すべての frontier が解消された段階で行います。一方通行の処理にすると、モックを実際に確認して初めて判明した要件が spec に反映されないまま文書の書き出しに進んでしまいます。

## Step 3: モック (見て反応できる成果物)

「実際の表示を確認しなければ判断できない」要件について、実装前に具体的な成果物に対するフィードバックを得ることで仕様を明確化します。**モックに関する仕様の基準は `references/mock-kit.md` に定義されています**。端末フレーム、切り替えバー、表示状態の切り替え、調整パネル、比較表示の仕様はすべて該当ファイルに準拠します。本節では作成する案数の決定規則のみを定めます。

| 論点の種類 | 案数 |
|---|---|
| 値・程度の論点 (間隔・件数・色・速度・閾値) | **1案 + 調整パネル** |
| 構造の論点 (レイアウト・情報階層・主要操作) が1つ | **2案** (対立する2構造) |
| 構造の論点が複数、または方向性そのものが未定 | **3案** (上限) |

**理由なく3案を基本としないこと**。親エージェントは委任を行う前に「N 案。比較対象とする論点: …」を1行で指定します。比較すべき論点が明確でない案は作成しません。各案は構造上の明確な違いを持つ必要があり、配色や文言の違いのみにとどまるものは別案として扱いません。

- **1タスクにつき1ファイル** `docs/crystallize/specs/<slug>/mock.html` を使用します (Step 2 のラウンドシートと同一ファイルです)。各案は同一ファイル内に配置し、mock-kit の切り替えバーで切り替えます。案ごとに個別のファイルを作成してはいけません (ブラウザのタブが増加し、各案の比較作業が煩雑になるためです)。
- **既存画面を改修する場合は、現行画面を正確に再現したものを最初の案として配置します** (`data-variant="A" data-variant-name="現状"`)。現行画面の確認は**ユーザーに協力を依頼します**。第1ラウンドの案内時に該当画面のスクリーンショットの提供を依頼し、受け取った画像を data URI 形式にして案 A に埋め込みます (エージェント自身は画面を表示・撮影できないためです。対象がブラウザ環境で既存の HTML が利用可能な場合は、DOM による再現でも問題ありません)。変更内容はそれ以降の案に差分として反映し、変更箇所を赤系の色で強調します (現状案は無彩色とします)。現行画面の正確な再現が比較の基準となるため、実態と乖離したモックでは変更点に対する正確なフィードバックが得られません。スクリーンショットが得られない場合は現状案を配置せず、その旨をシート内に明記します (推測による再現画面は比較基準として不適切です)。新規作成の画面では、この現状再現案は不要です。
- **終了条件を満たした段階で、最終決定事項をシートに確定値として反映します** (親エージェントが実行します)。(1) 採用された案 (確定案) の `data-variant-name` の先頭に「(確定)」を付与します (キットは URL ハッシュの指定なしで開いた際に「(確定)」の案を最初に表示するため、`<section>` タグの並び順は動かしません。バーの並びは `data-variant` の ID 順にキットが揃えます)。(2) `TWEAKS` 内の各 `value` を、最終的な回答テキストの `調整パネル:` の値で更新します (初期設定値のまま放置すると、後からファイルを開いた際に最終的な設定値を確認できなくなります)。(3) 不採用となった案には `data-rejected` を付与し、`data-variant-name` の先頭に「(不採用)」を付与して保持します。(4) `QUESTIONS` の配列を `[]` に変更して空にします (終了したラウンドの質問が残っていると、後から開いた際に不要な回答テキストが生成可能になってしまいます。パネル自体は空でも表示されるため、選択案および調整パネルの値の取得機能は維持されます)。これにより `mock.html` 自体が最終決定の記録となり、Step 4 の「見た目の正本」として参照可能になります。後続のテスト判定 (`plan-implement`) および実装処理 (`code-generator`) ではこのシートを基準として参照するため、初期状態のまま残すと参照すべき確定案および設定値が特定できなくなります。
- 画面表示を伴わないタスクの場合は、代替となる成果物を提示して確認を行います。API のレスポンス例、データモデルの定義案、CLI の出力例、変換前後のサンプルデータなどをフレーム内に静的に配置します。
- モックの作成はサブエージェントに委任します。その際、`references/mock-kit.md` および `assets/mock-kit.html` の**絶対パス** (スキル実行時のプロンプト冒頭に設定される「Base directory for this skill」を基底としてパスを解決します。スキルの Bash 実行環境では `${CLAUDE_PLUGIN_ROOT}` は設定されていないため使用できません。サブエージェントは親エージェントのカレントディレクトリや base directory を把握していません) と、**親エージェントが定義した TWEAKS の設定キー一覧 (キー名、型、値の範囲、単位、初期値) および状態キー**を渡します。設定キーの定義を各サブエージェントに委ねると、各案ごとの設定パネルの整合性が失われ、案同士の客観的な比較が行えなくなります。
- フィードバックは Step 2 の回答テキスト (案の採否、確認時の選択案、調整パネルの最終値、全体へのコメント) を通じて受け取ります。フィードバックの内容 (採用、不採用、修正要望) は理由とともに ledger の確定事項に記録し、**モックによる確認で決定した要件には「(モック確定・実機で再確認)」の注記**を付与します。モックは実際の操作感と異なる場合があるため、ここで決定した事項は実機環境での動作確認時に変更される可能性があります。変更が生じた際に仕様改訂として適切に対応できるよう、決定の経緯を記録として残しておきます。

## Step 4: spec の書き出し

`docs/crystallize/specs/<slug>.md` を以下の形式で作成します。ファイルパスやコードの断片は記載しません (実装の変更に伴い陳腐化しやすいためです)。ただし例外として、モックやプロトタイプで合意された内容をコード形式で表現した方が正確な場合 (状態遷移の定義、スキーマ定義、型定義など) と、「見た目の正本」節における `mock.html` のパスおよび `TWEAKS` の最終設定値は記載を認めます (パスは `specs/<slug>/mock.html` として slug に固定されており、spec と同一の寿命を持つため陳腐化しません。また、フラットな key-value 設定は決定事項の記録であり、実装コードとは異なります。これを散文に要約すると細かなデザインの決定事項が失われ、実装者がモックを参照せずに UI を実装する原因となります)。

```markdown
# <ゴール 1 文>

## 課題
ユーザー視点の 1 段落。

## 解決
ユーザー視点の 1 段落。

## 要件
- <挙動の箇条書き>。挙動に関わる項目には否定形の帰結を併記 (「= その結果 X は起きない / 見えない」)
- モックの反応で決めた項目には末尾に「(モック確定・実機で再確認)」の印

## 非機能要件
- 性能・オフライン・アクセシビリティ・データ量の境界など。該当なしなら「該当なし」と書く

## 見た目の正本
- 確定案: docs/crystallize/specs/<slug>/mock.html#variant=<id> (確認した状態: many, empty / 端末: phone)  ← UI を含まない spec は「該当なし」の 1 行だけ
- 調整パネルの最終値: {"cardGap": 12, "accentColor": "#3f6ad8", ...}  ← 最後の貼り戻しの `調整パネル:` 行をそのまま

「確認した状態」は、確定案の `data-state` キーのうち、ラウンド中の貼り戻しの `見ていた案:` 行に実際に現れたもの (貼り戻しごとに 1 つずつ運ばれるので、各ラウンドの行から集める)。

## 受け入れ基準 (テストケース表)
| ID | seam | ケース | 期待結果 |
|---|---|---|---|
| AC-1 | <public な境界> | <代表 1 点 / 境界の両側 / 異常系を 1 行ずつ> | <観測可能な結果> |

ID は追番で、**一度振ったら再利用しない** — 改訂で行を消しても番号を詰めない (plan・テスト・改訂履歴が同じ行を指し続けられなくなる)。

テストしないと決めたもの:
- <対象> — <理由>

実機確認に委ねる基準 (UI・見た目など TDD 対象外で挙動ゲートに委ねるもの):
- <観測可能な基準>

## スコープ外
- …

## 用語
この spec で新しく決めた語・意味を変えた語だけ。無ければ「なし」と書く。
- **<語>**: 1〜2 文の定義。意味を変えた語には「<前の定義> から変更」を添える

## 改訂履歴
| 日付 | 項目 | 変更 | 理由 | 発見した場面 (認識合わせ / 実装 / 挙動ゲート / リリース後) |
```

**「受け入れ基準 (テストケース表)」は、後続の `test-generator` の入力データとして直接利用されます。** seam (検証境界)、ケース、テスト対象外の範囲の3要素は、従来 `plan-implement` が実装開始時にユーザーと合意していた内容そのものです。本スキルでこれらを事前に確定させるため、**plan-implement 側で seam に関する個別の合意は行わず、表の内容を直接 test-generator に引き渡します**。この表の記載が不十分であると実装セッションで再度要件の確認が発生するため、本節は spec の中で最も重要な箇所となります。

- seam は既存の境界を優先し、可能な限り上位の単一境界に集約します (seam を細かく増やしすぎると、テストが実装内部の構造と過度に密結合してしまいます)。
- テストケースには境界条件を必ず含めます (数量の 0 / 1 / 複数 / 上限値、日時の境界跨ぎ、処理の中断・再試行、空データ、重複データ、順序関係など、タスクに関連する項目)。境界条件の考慮漏れは、実装後の手戻りにつながる主な要因となります。
- テスト対象外とする範囲は、記載漏れと区別できるように理由を付記して明記します。

**「見た目の正本」節は、モックで合意したデザイン詳細 (色、余白、角丸、タイポグラフィ、影、動き、階層構造、情報密度) を実装担当者に伝達するための唯一の手段です**。「要件」節は挙動を言語化するものであり、視覚的な詳細を文章だけで表現することは困難です。本節にはモックのパスと確定値のみを記載し、外観の文章による説明は記載しません。外観の仕様は `mock.html` の確定案自体が担保します。`plan-create` は UI 実装を含むタスク項目にこの参照先を付与し、`plan-implement` は UI スライスの `code-generator` にこれを渡します。

**「用語」節は用語集の正本ではなく、差分変更の記録です**。用語の定義に関する正本は用語集ファイルであり、spec 側には**本 spec で新しく定義した語、または定義を変更した語のみ**を記載します。同一用語の定義を複数箇所に重複して保持すると、一方のみが更新されて不整合が生じ、どちらが正しい基準か判別できなくなります。ここに記載する用語は Step 2 で用語集に登録した内容を転記するのみとし、用語集に存在しない語を spec 側だけに記述してはいけません (用語集にない語は後続の別 spec から参照できなくなります)。

文書を作成したら要点のみをチャットに提示し (30行を超える場合は `html-report` を用いて HTML 化して提示します。spec の実体ファイルは Markdown 形式を維持します)、ユーザーの確認を得て完了します。**spec に対して plan-evaluator に類する機械的な監査は実施しません**。仕様の妥当性を評価するのはユーザー自身の確認であり、別コンテキストによる機械的なスコアリングではないためです。

## Step 5: 案内

同一セッション内で続けて `/plan-create` に進む旨を案内します。**作成されたすべての spec のパスを一覧として指定し、`/plan-create` を呼び出します** (複数タスクを扱った場合でも spec ごとに分割して呼び出す必要はありません。並列実行の可否の判断は `plan-create` 側の手順 6 で一括して行われます)。spec と plan は同一セッションで連続して作成可能です (plan は spec の内容を読み込んで計画を策定するのみであり、ユーザーとの新たな要件合意を必要としないためです)。実装作業は、plan が作成された後に新しいセッションを開始して着手します。

**`plan-create` スキルから改訂モードとして呼び出された場合は上記の案内を行わず、改訂された spec のパスと変更内容の1行要約を返し、呼び出し元の手順 4 (plan の書き出し) へ復帰します**。ただし、改訂によって受け入れ基準の項目数が増減した場合は、手順 3 (タスク分割の判定) からやり直します。`/plan-create` を再実行すると処理が重複するため行いません。

## Gotchas

- **モックに本番環境の接続処理やバックエンド処理を実装しないこと** — バックエンドや実際のデータに接続した時点で「実装を行わない」という原則が崩れ、作成したコードを破棄する心理的コストが生じて確認作業に歪みが生じます。単一の HTML ファイルとモックデータによる構成で十分です。調整パネル用のインライン JavaScript はモックデータを操作するための表示用処理であるため、ここでの禁止対象には該当しません (禁止対象はバックエンドや本番データへの接続です)。
- **明確な目的なく3案を作成しないこと** — 「どの論点を検証するための比較案か」を明示できない案は、選択肢を増やしているのではなく判断を曖昧にしているだけです。数値や程度の論点であれば、1つの案と調整パネルを組み合わせる方が迅速に合意を形成できます。
- **客観的事実をユーザーに質問しないこと** — 「このライブラリでこの処理は実現可能ですか」といった確認は、ユーザーへの質問事項ではなく事前の調査不足です。事実関係を質問されたユーザーは推測で回答する可能性があり、その推測が誤ったまま確定事項として記録される原因になります。
- **考慮漏れ事項として一般論を挙げないこと** — 「テストコードを書きましょう」「例外処理に注意してください」といった記述は具体的な検討事項ではなく不要な情報です。対象のコードベースで実際に確認された実装慣習や過去の設計判断に基づく具体的な課題のみを論点として扱います。
- **網羅性を過剰に追求しないこと** — 極端に長大で網羅的すぎる仕様書は十分に確認されず、確認されない仕様書は合意形成に寄与しません。要件は挙動の単位で簡潔に記述し、過度な説明文で文書を肥大化させないようにします。
- **シートを提示するのはラウンドごとに1回、試問が完了した後とすること** — 試問で問題が見つかった場合は、ユーザーに提示する前に修正します。提示後に修正を行った場合でも、再表示を指示してはいけません (ブラウザのタブが重複して開かれる原因になります。ユーザーは再読み込みを行うことで変更を確認できます)。修正を行った事実は案内文に1行明記します。
- **ラウンドを移行する際は必ず `ROUND.round` の値を更新すること** — 値を更新しない場合、前回のラウンドの一時保存データが復元され、過去の回答内容が混入する原因になります。
- **`QUESTIONS` の選択肢に「その他」を設けないこと** — 代替案がある場合は「全体へのコメント」欄に記入してもらいます。「その他」が選択された場合、その意図をエージェントが推測して解釈する必要が生じ、定型テキストとして回答を受け取る利点が失われます。
- **用語集を編集する際の5原則** (Step 2 における更新はこれらを遵守します):
  1. **用語定義の節のみを更新すること** — 仕様の詳細、実装方法、ファイルパス、作業用メモなどを記述してはいけません。それらは spec や plan に記述すべき内容であり、混在させるとライフサイクルの異なる情報が同一ファイルに蓄積され、参照基準が乱れる原因になります。**リポジトリ直下の `CONTEXT.md` を用語集として利用している場合は、`## 用語` (または `## Language`) 節の内部のみを編集し、他の節には触れてはいけません**。該当ファイルは他の運用の基準を共有しているためです。
  2. **定義は「何であるか」を2文以内で簡潔に記述し、「何を行うか」という振る舞いは記述しないこと** — 振る舞いを記述し始めると仕様が混入し、実装が変更されるたびに用語集の記述が実態と乖離する原因になります。
  3. **同義語は使用する1語を決定し、それ以外は「使わない語」に列挙すること** — 複数の表現を許容すると、コード、仕様書、会話で異なる用語が使われ続け、同一の概念を指しているかの確認コストが恒常的に発生します。
  4. **対象プロジェクト固有の用語のみを記載すること** — タイムアウトやリトライといった一般的な技術用語を登録し始めると、用語集が肥大化して実効的な参照が行われなくなります。
  5. **決定した段階で即座に反映すること** — ラウンドの終了時や仕様書の作成完了時にまとめて更新しようとすると記載漏れが発生しやすく、後続の質問作成時に用語の統一を図るための基準も不足します。
- **禁則 1 の制御昇格の判断基準**: コードの記述禁止ルールが遵守されない事例が再発した場合は、注意喚起にとどめず、hook (PreToolUse イベントで `docs/crystallize/specs/` および用語集の対象ファイル以外への Write / Edit 実行を拒否する制御) を設定して強制します。
