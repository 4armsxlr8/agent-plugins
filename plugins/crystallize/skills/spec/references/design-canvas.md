# デザインキャンバス — 絵を置く場所の使い方

画面のあるタスクの案 (モック) は、プロジェクトに 1 つの**デザインキャンバス** (claude.ai の Design 型 Artifact。アートボードを並べる面) に描く。問いはラウンドレポート (`docs/crystallize/specs/<slug>/round-<n>.html`) に置き、キャンバスには絵だけを置く。ここに書く名前 (`project/`・`.dc.html`・`canvas.json`・`support.js`・プロトタイプリンク・`{{…}}`・`<sc-for>`・`<dc-import>`) は 2026-10-18 に Design 型の指示で確認したもの。アートボードのファイルの書き方そのものはここに書かず、キャンバス作成時 (または `type_url` の `read`) に Design 型が返す指示に従う。**型の指示が変わっていたら型の指示が勝つ**。

## 1 プロジェクト 1 キャンバス

- `docs/crystallize/design-canvas.md` に URL・Design 型の `type_url`・題・使ったデザインシステム (無ければ「なし」)・作成日を書く。全 spec・全ラウンドで同じキャンバスを使い、spec ごとにページを 1 つ足す (「spec ごとのページ」)。キャンバスを spec ごと・ラウンドごとに作らない (絵の置き場が増えるほど、前に決めた画面との見比べができなくなる)
- `design-canvas.md` が無くても、すぐには作らない。この記録はリポジトリの中にあるので、記録が main に入る前に切った worktree や並行するセッションからは見えない。先に Artifact ツールの `action: "list"`, `type: "Design"`, `limit: 200` で題 `<プロジェクト名> design` のキャンバスを探し、見つかればそれを使う。そのときの `type_url` は `action: "quickstart"`, `intent: "design"`, `design_systems: false` で得て、URL とともに `design-canvas.md` に記録する。同じ題が複数あればユーザーにどれを使うか聞く
- 見つからなければ親が作る。Artifact ツールの `action: "quickstart"`, `intent: "design"` で Design 型の `type_url` とデザインシステムの一覧を得る → プロジェクトのデザインシステムが一覧にあればそれを使う → `type_url` と題 (`<プロジェクト名> design`) で publish → 返ってきた Design 型の指示 (ファイルの形、公開の仕方、先に読むページ) を読み、URL と `type_url` を `design-canvas.md` に記録する
- **セッションの最初に 2 回 `read` する**。(1) `action: "read"` + `url` = キャンバス: そのセッションで read も publish もしていない Artifact への publish は拒否されるため。これはページしか返さない。(2) `action: "read"` + `type_url` (url は渡さない): Design 型の指示が返る。後のセッションはこれでしか指示を取り戻せない

## spec ごとのページ

- spec 1 つにキャンバスのページ (`canvas.json` の `pages`) を 1 つ作る。`id` と `name` はどちらも slug。ページは 1 キャンバスに 40 個までなので、足せないときはユーザーにどの spec のページを片付けるか聞く
- この spec のアートボード (`boards`) と付箋 (`notes`) にはすべて `"page": "<slug>"` を付ける。付けないと最初のページに入る
- アートボードのファイル名 (`boards` のキー) と付箋の id はページで区切られず、キャンバス全体で重ならないようにする。どちらも先頭に `<slug>-` を付ける。付箋の id は 40 文字までなので、行は `<slug>-R<round>-Q<n>`、帯は `<slug>-now` / `<slug>-done` / `<slug>-drop` とする
- ページの中は上から「今回の確認」「決まっていること」「不採用」の 3 つの帯に分け、帯の先頭に付箋を置く。`title1` は複数のアートボードの見出しにしか使えないので、帯や行のアートボードが 1 枚以下のときは `kind` 無しの付箋 (`w` を付ける) にする。名前や題に「(確定)」「(不採用)」の印は付けない — どの帯にあるかが状態である
- 自分の spec のページ・アートボード・付箋だけを変える。`pages` と `order` は全 spec で 1 つの配列なので、自分のページの項目と自分のアートボードのパスだけを足し引きし、残りはそのまま残す。この spec のものかどうかは名前の接頭辞ではなく `page` が slug かどうかで見分ける (`share-card` と `share-card-link` は接頭辞では区別できない)。ほかの spec のものと `launch` には触らない
- 古い 3 ページ (「今回の確認」「決まっていること」「不採用」) が残るキャンバスでは、そのページには触らず、新しい spec から slug のページを使う

## ラウンドの行

- **絵の要る問い 1 つ = 1 行**。「今回の確認」の帯に置き、行頭に付箋「R<round> Q<n> <題>」(`title1`。アートボードが 1 枚なら `kind` 無し) を置き、右に選択肢ごとのアートボードを 1 枚ずつ並べる
- アートボードの名前は `<slug>-R<round>-Q<n>-<選択肢 id>` (ファイルは `project/share-card-link-R5-Q1-A.dc.html`)。1 案が複数画面なら `share-card-link-R5-Q1-A-2` と続ける。`boards` の `title` には slug を除いた `R5-Q1-A` を書き、提案の案は先頭に「(提案)」を付ける (キャンバスの名札にはこれが出る)。ユーザーがそのラウンドを見る前の描き直しは同じ名前に上書きし、見たあとに描き直す案は新しい名前にする (レポート・ledger・spec が指した名前の中身を変えない)
- 同じ問いの案は同じ場面 (同じ画面・同じダミーデータ) で描き、問いで比べる差だけを変える
- 提案の案 (spec Step 3) は、アートボードの題 (`.dc.html` の `<title>`) の先頭に「(提案)」を置く。名前の規則は他の案と同じ
- 画面の移り変わりは、アートボード間のプロトタイプリンク (`<a href="share-card-link-R5-Q1-A-2.dc.html">`) で描く。`mock-evaluator` はこのリンクと行の並びで導線を辿る
- 見ながら動かさないと決められない値 (余白・件数など) は、アートボードに `data-props` の調整を付け、同じ値の `doc-ask` をレポートにも置く (spec Step 2)。値はレポートの返信で受け取る
- 「今回の確認」の帯には現在のラウンドの行だけを置く。決まった画面は「決まっていること」の帯へ、落ちた案は「不採用」の帯へ移す (`boards` の `x` / `y` を変える)

## 作成と公開

- アートボードの HTML を書くのはサブエージェント (spec Step 3 の委任)。書き出し先は `docs/crystallize/specs/<slug>/design/round-<n>/`。親はこのファイルと Design 型が返した指示、名前と寸法、場面、前のラウンドの読み戻し (`design/round-<m>/project/`) の場所を渡す (写しは spec の終了時にしか作られないので、途中のラウンドで既存の絵を見せるには前のラウンドの読み戻しを渡す)。サブエージェントはキャンバスに触らない
- 公開は親が行う (Artifact ツール、`url` = キャンバス)。行の付箋・帯・ページの配置も親が宣言する。どのファイルをどのパスで publish するかは Design 型の指示に従う
- アートボードのファイルと、それを載せた `canvas.json` は同じ公開の呼び出しで送る (Design 型は `canvas.json` に載っていない `.dc.html` も表示するため、別々に送ると途中の状態が見える)
- `canvas.json` はほかの spec のセッションと共有する 1 ファイルなので、送る直前に `action: "read"` + `path: "project/canvas.json"` で読み直し (`url` だけの `read` はページしか返さない)、自分の spec の項目だけを足し替えて送る。先に誰かが保存していると公開は拒否されるので、読み直してやり直す。3 回拒否されたらユーザーに伝えて止める
- 描き直しも同じ手順 (サブエージェントがファイルを直す → 親が再公開 → 再読み戻し → スクリーンショットの取り直し)

## 読み戻しとスクリーンショット

- 公開後、各アートボードと `canvas.json` を `action: "read"` + `paths: ["project/<名前>.dc.html", …, "project/canvas.json"]` + **`out_dir` = `docs/crystallize/specs/<slug>/design/round-<n>` の絶対パス**で読み戻す。`out_dir` を省くと scratchpad に落ちる。ファイルは `<out_dir>/project/<名前>.dc.html` に入る。ディスクの中身がキャンバスの中身と同じになり、`mock-evaluator` と試問はこのディレクトリを読む
- スクリーンショットは読み戻した HTML から作る。`<script src="./support.js"></script>` の行を除いた写しを作り、headless Chrome でアートボードの寸法どおりに描いて PNG にする。例: playwright の `chromium.launch({ channel: 'chrome' })`、`deviceScaleFactor: 2`、viewport をアートボードの寸法に合わせて `page.screenshot`。playwright が無ければ Chrome 単体でよい: `chrome --headless=new --screenshot=<png> --window-size=<w>,<h> file://<写し>` (依存を足さない)。PNG は `design/round-<n>/project/<名前>.png` に置き、絶対パスをラウンドレポートの素材に書く (data URI への埋め込みは `html-report` が行う)
- デザインシステムの部品、`{{holes}}`、`<sc-for>`、`<dc-import>` を使うアートボードはローカルでは正しく描けない。その案はスクリーンショットを付けず、キャンバスへのリンクだけにし、レポートにその旨を 1 行書く

## 終了時

- 確定したアートボードを「決まっていること」の帯へ、落ちた案を「不採用」の帯へ移す
- 確定したアートボードを `action: "read"` + `paths` + `out_dir` = `docs/crystallize/specs/<slug>/design` の絶対パスで読み戻し、`design/project/<名前>.dc.html` を写しとして保存する (読み戻したファイルをそのまま置く。手で直さない)。実装者 (`code-generator`) はこの写しを読む。キャンバスと写しが食い違ったらキャンバスが正本で、写しを読み戻し直す
- 改訂 (挙動ゲートでの外観変更) では、サブエージェントがアートボードの HTML を直し、親が `read` (url) でキャンバスを開いてから再公開し、写しを読み戻す。写しだけを直さない

## Gotchas

- **案をレポートに描かない** — レポートに載せるのはスクリーンショットとリンクだけ。絵の正本はキャンバス 1 つ
- **問いをキャンバスに置かない** — 答えはレポートの返信で受ける。キャンバスのコメントは補助で、設計を変える指摘はレポートのコメントか次のラウンドの問いに移す
- **読み戻しを省かない** — ローカルのファイルを直接スクリーンショットにすると、公開に失敗した案や古い版を見せることがある。ディスクの中身は常にキャンバスから読み戻したもの
