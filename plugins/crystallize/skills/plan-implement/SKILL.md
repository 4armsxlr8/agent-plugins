# plan-implement

要件は事前にすべてを決定できるものではなく、実装や実際の操作を通じて具体化・変更されるものである。事前に要件定義を綿密に行っても、UI は実際に操作して初めて判明する点が存在し、リリース後に利用者のフィードバックによって変更されることもある。計画に対する忠実性とは、無断で計画から逸脱しないことであり、必要な変更を行わないことではない。

`plan-create` スキルが作成した plan (`docs/crystallize/plans/<slug>.md`) と、その plan が参照する spec (`docs/crystallize/specs/<slug>.md`) を受け取り、実装から検証、コミットまでを一貫したルールに基づいて統括する。3つのゲート（機械・挙動・例外）を順に通過させ、**挙動ゲートでの修正が完了するまで diff-review を実行しない** — 修正作業の途中で差分を提示すると、修正のたびに差分が古くなり、十分に確認されないままコミットされてしまうのを防ぐためである。本スキル自体はコードを書かず、実装はすべてサブエージェントに委任する。

## Input / Output

- **Input**: `$ARGUMENTS` = `docs/crystallize/plans/<slug>.md` のパス。省略時は `docs/crystallize/plans/` 直下の `.md` が1つならそれを使い一行で確認を取る。複数あれば AskUserQuestion で選択してもらう。該当する `.md` が無ければ実装を開始せず、`spec` → `plan-create` の順で先に plan を作成するよう案内して終了する
- **Output**: `plan-commit` が作成する1コミット。進行中は `docs/crystallize/plans/<slug>.md` 本体に `## 進行状況`（フェーズ別チェックリスト）と `## Deviations`（逸脱ログ）を追記しながら進め、確定と同時にコミットメッセージに集約されて plan ファイル自体は削除される（補助ファイルは作成しない）。spec ファイルは削除されず、仕様改訂の手順で変更した場合はその差分も同一コミットに含まれる

## 最重要禁則

1. **diff-review はフェーズ4（挙動ゲート）の修正が完了するまで呼び出さない** — 修正途中の古い差分を提示しても適切に確認されず、そのままコミットされてしまうのを防ぐため
2. **サブエージェントの完了報告だけでフェーズ3（機械ゲート）を通過させない** — サブエージェントの自己申告のみでは不十分であるため、フェーズ2の完了報告が全項目揃っていても、テストや lint コマンドは plan-implement 自身が再実行する
3. **要件と矛盾する逸脱や、plan に記載のない大規模な変更に気づいた場合は続行せず作業を停止する** — Deviations に記録して作業を継続してよいのは、影響が可逆的かつ局所的な判断のみである。変更規模の大小の判断に迷う場合は作業を停止する。**この規則はエージェント側の判断による逸脱（実装中に矛盾に気づいた場合）にのみ適用し**、ユーザーからの仕様変更の指示には適用しない — ユーザー自身が要件の変更を求めた場合はフェーズ4の仕様改訂手順で処理する。ここで作業を停止すると、ユーザー自身が指示した要件変更に対して不必要な許可を求め直すことになるためである

各フェーズは完了条件を満たすまで次へ進まない。完了条件を満たしたら、次に何をするかを一行でユーザーに予告してから進む。

## フェーズ1: plan / spec 受領と Deviations 契約

- plan を Read し、先頭の `spec:` 行が参照する spec も Read する（`spec:` 行のパスはリポジトリルート（`git rev-parse --show-toplevel`）基準で解決する）。保持すべき既存の動作、実装計画、検証コマンド、Deviations 規約は plan から取得し、要件、非機能要件、受け入れ基準（テストケース表）は spec から取得する — 保持期間が異なる情報を混在させないためであり、plan は実装完了時に破棄され、spec は将来にわたって保持・改訂される。あわせて**用語集**（リポジトリ直下に `## 用語` または `## Language` を持つ `CONTEXT.md` があればそれ、無ければ `docs/crystallize/CONTEXT.md`、どちらも無ければ spec の用語節）も Read する — 実装で使用する識別子とUIの表示文言は用語集の表記に統一する
- **`spec:` 行がない旧形式の plan は、plan 内の確定事項と受け入れ基準をそのまま情報源として扱い実行する**（以降の「要件」「受け入れ基準」はその場合 plan 内の記述を指す）
- plan に `covers:` 行がある場合（`plan-create` スキルが spec を分割した場合）、この plan が対象とする受け入れ基準は**そこに列挙された AC のみ**とする。以降の「受け入れ基準」はその範囲を指し、範囲外の AC は他の plan が担当するため、未実装として扱わず、テストを作成せず、挙動ゲートのチェックリストにも含めない。`depends-on:` 行がある場合は、そのパス（`spec:` 行と同様にリポジトリルート基準で解決する）が示す先行 plan が `docs/crystallize/plans/` に残っていないかを確認する。残っている場合は実装を開始せず、先行 plan を先に `/plan-implement` で実行するよう案内して終了する（後続 plan は先行 plan のコミットを前提として作成されており、先行 plan を適用せずに進めると重複実装の原因となる）。先行 plan のファイルが存在しない場合は `git log --format=%B --grep='<先行 plan のゴール 1 文>'` で先行コミットが存在するかを確認する — コミットが見つからない場合は「先行 plan が見つからない」として作業を停止し、ユーザーに確認する（ファイルが存在しない原因として、コミット済みである可能性と、ファイルの移動や作成漏れの可能性の両方が考えられるため）
- `## 進行状況` 見出しが無ければ作成する。実装計画の各項目と4つのゲート（機械/挙動/例外/確定）をチェックボックス形式で列挙する。既に存在する場合は最初の未チェック項目から再開する — セッションが切断されても plan を確認することで再開位置が特定できる
- `## Deviations` 見出しが無ければ作成する（本文は空でよい）。**古い plan の Deviations 規約に「implementation-notes.md を作る」と記載されていても従わない** — 本スキルは別ファイルを作成せず、この見出しに直接追記する規則を正とする（現行の `plan-create` スキルも同様の規約で plan を作成する）
- 逸脱の扱い: 計画から外れる必要が生じた場合は安全側の選択を採り、`## Deviations` に一行（計画項目 / 実際の選択 / 理由）を追記して作業を継続する。要件と直接矛盾する逸脱については、矛盾点と spec の該当箇所を整理してユーザーに提示し、指示を仰ぐ（作業は停止した状態を維持する。禁則3のとおりエージェント発の逸脱に限る）
- **完了条件**: plan と spec の読了、`## 進行状況` および `## Deviations` が存在し、次に着手する項目が1つに確定している

## フェーズ2: 実装

- 実装計画の項目を先頭（変更が発生しやすい順）から進める。末尾の定型的な作業（リファクタリング、各モジュールの接続、テスト整備）はまとめて1回の委任で処理してよい。**同一の意図を持つ小さな実装単位が連続する場合も1回の委任にまとめてよい**（サブエージェントの起動ごとにコンテキスト読み込みの処理コストが発生するため。まとめることが許されるのは同一の意図を持つ変更のみであり、異なる目的の変更を混在させると逸脱内容の追跡が困難になるため避ける）
- 各項目の TDD 適否を判定する（適用範囲: 入出力によって期待される動作を確定できる振る舞いの変更は TDD とする。UI、外観、使い捨てプロトタイプ、設定ファイルの更新は対象外とし、フェーズ4の実機確認で検証する）
- 委任は都度のプロンプト指示ではなく **generator スキルの Skill 呼び出し**で行う（委任のたびに指示文を作成すると伝達内容や禁止事項にばらつきが生じるため。指示ルールはスキル側で定義されている）:
  - **TDD 対象スライス**: spec の「受け入れ基準（テストケース表）」の該当行と「テストしないと決めたもの」をそのまま `test-generator` に渡し、RED（失敗するテストと実行ログ）を取得したのち、続けて `code-generator` を実行して GREEN（テスト成功）にする。**ここで設計上の境界（seam）、境界ケース、テスト除外範囲の合意を取り直さない** — 事前に合意を形成する役割は `spec` スキルで完了しており、受け入れ基準表自体が合意内容の記録であるため、実装開始時に改めて仕様を協議する必要はない
  - **非 TDD スライス**: `code-generator` を単独で起動する
  - 渡す情報は、該当項目の計画文、関連する要件、受け入れ基準、テストの実行コマンド、用語集のパス、および「識別子・表示文言は用語集の語を使い、『使わない語』を新たに導入しない」という一文のみとする（起動された generator は用語集の場所を把握していないため、パスとルールを渡さないとコード内の表記が用語集と乖離する）。TDD の場合はさらに、`test-generator` には受け入れ基準表の該当行と「テストしないと決めたもの」を、`code-generator` には RED 状態のテスト一覧を追加する。**UI を含む非 TDD スライスにはさらに、plan の項目にある見た目の正本 (`mock.html` の絶対パス — plan のリポジトリ相対パスをリポジトリルート基準で解決する — と、確定案の `#variant=<id>`・確認した状態。`#variant=` はパスの一部ではなく案の識別子なので別項目として渡す) と、spec の「見た目の正本」節の調整パネルの最終値 (JSON) を加える** — これらが欠けると実装者がモックを参照せずに要件の文言のみから UI を実装し、デザインの詳細（色・余白・角丸・タイポグラフィ・影・アニメーションなど）がモックから乖離する恐れがあるためである。あわせて「実装前に確定案の markup・CSS・`applyTweaks` からトークン表を抜き出し、報告に含める」の一文を添える。**このスライスは effort を high に設定する** — モックをもとにした実装は機械的な変換ではなく設計上の判断を伴うため、`code-generator` の既定（実行コスト優先）の設定よりも高い推論精度を要するためである（モデルの指定ではなく effort パラメータで制御する）。spec 全文や既に合意済みの論点は渡さない
  - **受け入れ基準表にないケースを `test-generator` が提案してきた場合は、spec の改訂候補としてユーザーに1回だけ確認する**（表は合意された内容の記録であり、無断で追加すると想定外のテストが無秩序に増えるため）。採用する場合は受け入れ基準表に行を追加し、改訂履歴に1行（場面は「実装」）を追加してから差し戻す。採用しない場合は「テストしないと決めたもの」に理由を明記して追加し、改訂履歴にも1行（場面は「実装」）を追加する — spec の変更がいかなる場合でも改訂履歴に漏れなく記録されるようにするためである
- 逸脱は generator の報告から plan-implement 自身が `## Deviations` へ転記する。escalate の報告を受けた場合は作業を続行せず、最重要禁則3のとおり停止してユーザーに判断を仰ぐ
- **完了条件**: 進行状況の実装計画項目すべてに完了報告または解決済みの escalate が記録されている（この時点の報告は自己申告の状態で問題ない — 次のフェーズで検証を行う）

## フェーズ3: 機械ゲート — 正しいか

- プロジェクトのテストおよび lint コマンドを plan-implement 自身が実行する。サブエージェントからの「すべて成功した」という報告のみに基づいて次へ進めてはならない
- **テストは対象を限定して実行する**: 修正ループ中の再実行は、変更の影響範囲にあるテスト（変更したファイルやモジュールに対応するもの）のみでよい。**全テストスイートの実行はゲートの完了条件として最後に1回だけ**行う — 検証の正確性を担保しつつ、変更のない箇所のテストを修正ループごとに毎回実行する非効率を防ぐためである
- テストまたは lint が失敗した場合は `code-generator` に差し戻して修正させ、再実行する。12回試行しても成功しない場合は実装を停止してユーザーに報告する
- テストおよび lint がすべて成功したら `code-review` スキルで AI コードレビューを行い、指摘事項を解消してから次へ進む。挙動ゲートより先に実行する理由: 指摘の修正によってコードが変更される可能性があるため、ユーザーによる動作確認を後にしないと確認作業のやり直しが発生するためである
  - 指摘の修正は `code-generator` に差し戻す（指摘一覧を渡し、テストコードは変更しない）。修正後はテストおよび lint を再実行し、必要に応じて code-review も再実行する。この修正ループも12回の試行で解消しない場合は作業を停止してユーザーに報告する
  - 指摘が「テストコード自体の不備」である場合は、実装コード側で無理に結果を合わせようとせず、ユーザーに確認した上で `test-generator` に差し戻す（期待値の勝手な変更を防ぎ、テスト基準自体の変更には人間の承認を必須とするため）
  - effort は **low を基本**とし、次のいずれかに該当する変更は **high** に引き上げる: アーキテクチャ、データモデル、公開インターフェースの変更 / plan の複数項目にまたがる大規模な変更 / 共通基盤など広範に影響が及ぶ箇所
  - 解消せずに許容する指摘は、その理由を `## Deviations` に記録する（diff-review の昇格条件④⑤に該当し、人間によるレビュー対象となるため）
- 変更が**対外境界・依存追加**（diff-review の昇格リスト②③）に関連する場合に限り、`security-review` スキルでセキュリティレビューも実行する。該当判定の基準は diff-review 側の昇格リストとし、同リストが改訂された場合はその内容に従う。該当しない場合は「security-review 対象外」と進行状況に記録して省略する（毎回実行しない理由: 外部境界に関連しない変更に対して網羅的な監査を行っても実行コストが増加するだけで有用な指摘が得られにくく、該当する差分は例外ゲートにおいて人間が確認するためである）
  - 指摘の扱いは code-review と同様とする: 修正は `code-generator` に差し戻してテストおよび lint を再実行し、解消せずに許容する指摘はその理由を `## Deviations` に記録する
- code-review（および実行した場合は security-review）の指摘への対応が完了したら、`simplify` スキルでコード品質の整理（再利用性、単純化、効率化、抽象度）を適用する。code-review の後に配置する理由: 機能的な正しさの修正を先行させないと、リファクタリング後のコードに再修正が発生して作業が重複するためである（欠陥の検出は code-review、コード構造の整理は simplify という役割分担に基づく）
- code-review、security-review、simplify によってコードが1行でも変更された場合は、テストおよび lint を再実行して成功を確認する（この場合も影響範囲を限定した実行でよい）
- **完了条件**: code-review および security-review（実行した場合）の指摘が解消済みまたは Deviations に記録済みであり、simplify の適用が完了し、**最後のコード変更の後に全テストスイートおよび** lint が exit 0 で終了していること（フェーズ2におけるサブエージェントの報告をそのまま流用することは不可）

## フェーズ4: 挙動ゲート — 意図どおりか（diff より先）

- spec の「実機確認に委ねる基準」、「(モック確定・実機で再確認)」印の要件、受け入れ基準のいずれにも外観や UI 操作の項目が無ければ、「UI確認対象なし」と進行状況に記録してフェーズ5へ進む
- 該当項目がある場合は `run` スキルでアプリケーションまたはモックを起動し（ブラウザ対象の場合、環境にブラウザ表示用のツールがあればそれを使用して開き、無ければユーザーにブラウザで開いてもらう。特定の製品名は記載しない — ツール類は利用者側の環境設定に依存するため）、チェックリストを**ユーザーに提示し、ユーザー自身に実際に操作・確認してもらう**。並び順は spec の「実機確認に委ねる基準」と「(モック確定・実機で再確認)」印の付いた要件を先頭にし、続けて受け入れ基準の操作パスとする — 印が付いた項目はモックの挙動をもとに暫定決定された箇所であり、実機での確認時に変更が生じる可能性が高いためである。`covers:` に `実機:` の項目がある場合は、実機確認に委ねる基準とモック確定印の要件はそこに記載されたもののみを掲載する。`docs/crystallize/specs/<slug>/mock.html`（`spec` スキルの検証用モック。spec ディレクトリ配下に保持されている）が存在する場合は比較基準として参照する — 現行案や不採用案も並んでいるため、`data-variant-name` に「(確定)」が付いた案（spec の「見た目の正本」節の `mock.html#variant=<id>`）を確認する。**モック確定印の項目は、確定案と実機を並べて比較確認することを必須とする**（任意にすると記憶との照合になり、デザインの微細な差異は記憶のみでは判別できないため）。実機と確定案の差異が見つかった場合は、要件自体は変更されていないため微修正レーンで処理する
- 問題点や差異が見つかった場合は、修正の性質に応じて対応手順（レーン）を分ける。**いずれの手順であっても、修正がすべて完了するまで diff-review は呼び出さない**
  - **微修正レーン** (テストで検証している振る舞いを変更しない修正 — 外観、文言、定数の調整など): `test-generator` によるテスト作成は行わない（UIや外観は TDD 対象外とする原則に基づく）。指摘事項はユーザーが一通り確認を終えるまで**集約し、1回にまとめて** `code-generator` に委任する。色、余白、文言の修正など1〜2行程度の即時調整であり、ユーザーが画面前で待機している場合に限り、plan-implement が直接編集してよい（サブエージェントへの委任に伴う処理コストが作業自体を上回るためであり、委任原則の例外として扱う）。再検証は lint と影響範囲のテストのみ行い、code-review は再実行しない（すべての変更差分は最終的に例外ゲートで確認されるため）。hot reload など実行中のアプリケーションを終了せずに変更を反映できる手段があれば活用し、その場で再確認を行う
  - **正規レーン** (実装が spec の記述と一致していない修正 — 要件定義は正しいが、実際の動作が要件を満たしていない場合): 通常どおりフェーズ2に差し戻し、修正後は影響範囲のフェーズ3のみを再実行してからこのチェックリストに戻る
  - **仕様改訂レーン** (ユーザーが要件自体の変更を希望した場合): 実装は spec の記述どおりだが、実際の操作を通じて spec 側の定義を変更する必要があると判明した場合。手順は次の4点である
    1. **「これは仕様の変更として spec に記録します: <変更点1行>」と1回だけ宣言する**。以後、同一の変更点について「仕様と違いますがよいですか」と確認し直さない — 一度決定した変更について重ねて確認を求めると、ユーザーが仕様変更を提案しにくくなるのを防ぐためである
    2. spec の要件と受け入れ基準の該当行を書き換え、改訂履歴に1行（日付 / 項目 / 変更 / 理由 / 場面は「挙動ゲート」）を追加する。書き換えた要件行にも否定形の帰結を併記する（spec の要件節の記述規則を維持する）。spec の存在しない旧形式の plan の場合は、同様の内容を plan の `## Deviations` に「仕様改訂」と明記して記載する（記録先がないことを理由に記録を省略しない）
       - **要件の用語が変更された場合は、同一の手順内で用語集も修正する** — 新しい用語を導入した場合、用語の意味を変更した場合、呼称を変更した場合が該当する。用語集の編集は通常 `spec` スキルのみが行うが、この場面における plan-implement は spec の編集担当として動作しているため例外とする。修正しない場合、コードと spec に新しい用語が反映されているにもかかわらず用語集に古い用語が残り、後続の spec がそれを正本として参照してしまうためである。記述規則は `spec` スキルの Gotchas に記載された5項目に従い、変更した用語は spec の「用語」節にも1行記録する（この節は当該 spec で定義または変更した用語を記録する箇所であるため）
       - **外観が変更された場合は、同一の手順内で spec の「見た目の正本」節および `mock.html` の定義内容も修正する** — 確定案が変更された場合は「(確定)」の指定位置と節内の `#variant=<id>` を修正し、値が変更された場合は `TWEAKS` の `value` と節内の最終値 JSON を修正する。実機での確認時に変更が生じることは想定内であるため、変更の都度正本を追随させないと、後続の実装者が古い案や数値を参照してしまうのを防ぐためである
       - **分割 plan（`covers:` 行がある）で受け入れ基準の行が増減した場合は、同一の手順内で `covers:` 行も修正する** — 追加された AC について、その挙動を本 plan で実装する場合は自身の `covers:` に追加する。他の plan が担当する場合は `plans/` に残っている該当 plan の `covers:` に追加し、残っていない（コミット済み）場合は作業を停止してユーザーに報告する（実装済みの範囲に後から要件を追加することになるため、新規 plan を作成するか次の plan に含めるかの判断が必要となるため）。削除された AC は自身の `covers:` から除外する。ここで修正しないと、どの plan にも割り当てられない受け入れ基準が発生し、未実装のまま全 plan がコミットされるのを防ぐためである
    3. 影響を受ける受け入れ基準の行（AC-n）のみを `test-generator` に差し戻す — 「テスト期待値の変更には人間の承認を必須とする」ルールの確認が、手順1の宣言に相当する
    4. `code-generator` で実装 → 影響範囲のみフェーズ3を再実行 → このチェックリストに戻る
    - モック確定印の要件など、受け入れ基準の行に影響しない外観のみの変更であっても手順1および手順2は実施する（spec を現状の実装に一致させることが目的であり、記録を省略すると後続の実装で同様の議論が繰り返されるため）。手順3は対象行が存在しないため省略し、コード側の修正は微修正レーンの手順に従えばよい
- **完了条件**: チェックリストの全項目（実機確認に委ねる基準、モック確定印の要件、受け入れ基準の操作パス）について、ユーザー自身の言葉で「意図通り」であることの確認が得られていること（UI確認対象なしの記録で代替した場合も可）

## フェーズ5: 例外ゲート — 危なくないか

- フェーズ4の修正が完了した後に初めて `diff-review` を Skill ツールで直接起動する（案内文で促すのではなく実行する）: skill = `diff-review`, args = `plan: <plan のパス>`
- ユーザーが既に別のレビュー手段（例: 別の AI レビューツールの実行）を使用すると明言している場合は起動を省略してよいが、レビューの実施自体を省略することは認めない
- **昇格 hunk が0件のとき、diff-review は画面を作成せず「全 M hunk 中、昇格 0 件 (①〜⑥該当なし)。N files +a -d (レビュー対象外 X hunk: reports/plans を除外)。go / no-go を」の1行のみを返す**（`M` は除外後の判定対象 hunk 数。除外が0件なら括弧ごと省略する）。その1行を数値も含めてそのままユーザーに提示し、go / no-go の判断を得る — 画面が表示されないのはレビューの省略ではなく、確認すべき例外事項が存在しなかった結果であり、レビュー未実施とはみなさない
- 昇格対象がある場合は、diff-review によって既に開かれている画面において、決裁カードごとの「このリスクを受け入れるか」の判断として明示的な go / no-go を得る。**plan-implement は画面を再度開いてはならない** — サブエージェントによってブラウザで表示済みであり、開き直すと同一画面のタブが重複して開かれるためである。diff-review の最終応答に「開いたあとに直した」と記載されている場合は、開いているタブの再読み込みを案内するのみでよい。no-go の場合はフェーズ2またはフェーズ4へ差し戻す
- **完了条件**: ユーザーからの明示的な go が得られていること（この go はフェーズ6におけるコミットへの同意を兼ねる）

## フェーズ6: 確定

- フェーズ5で go を得た後、`plan-commit` を Skill ツールで直接起動する（案内文で促すのではなく実行する）: skill = `plan-commit`, args = `<plan のパス>`
- 仕様改訂手順を実施した場合であっても、spec の改訂履歴を本スキル自身でコミットメッセージへ転記してはならない — 転記は `plan-commit` の手順3が担当する（転記の担当箇所を1箇所に限定しないと、記載が重複するか、双方が相手側の処理とみなして記載漏れが発生するため）
- `plan-commit` が返す `git log -1 --stat` の要点をそのまま報告する。各スライスの作業経過を改めて報告する必要はない
- **完了条件**: `plan-commit` が完了し、plan ファイルおよび plan と同名のディレクトリ（`docs/crystallize/plans/<plan の basename>/`）が削除されていること（spec ファイルは残る）

## Gotchas

- **後続スキルの実行を「〜してください」といった案内文だけで済ませない** — 案内文による依頼にとどめると後続スキルが実行されず、不十分なレビューや手動の git 操作に置き換わる事例が頻発したためである。フェーズ5およびフェーズ6は必ず Skill ツールで直接起動する
