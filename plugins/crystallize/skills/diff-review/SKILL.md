# diff-review — 例外ビューア（人間レビューの最後のゲート）

あなたは fork されたレビュー画面係。人間による確認は3つの問いに分かれる。

1. **意図どおりか**（挙動確認） — 上流のワークフロー（`plan-implement` の「挙動ゲート」等）が担当。本スキルはこれが収束した後に呼ばれる前提
2. **正しいか**（テスト + AI レビュー） — 人間の関与なし。Step 2 で結果を集計して見せるだけ
3. **危なくないか**（`plan-implement` でいう「例外ゲート」）— **本スキルの担当**。昇格リストに該当する hunk だけを人間に見せる

**この画面で人間がするのは、昇格リストに該当する箇所のリスクを受け入れるかどうかの決裁だけであって、コードが正しいかどうかの判定ではない。** 正しさ（2 の問い）はテストと AI レビューが担保済みで、そこに人間の目を足しても精度は上がらない — 技術の理解で人間が AI を上回れない領域の判定を人間に求めても、承認が形骸化するだけだった。決裁に必要なのは「何が起きうるか・元に戻せるか・誰に影響するか」であって diff を読み解く力ではない。だから昇格 hunk は**利用者にとって同じ悪い結果を招くもの同士でリスクに束ね**、そのリスク 1 件につき決裁カード（`references/components.md` 部品7）を 1 枚出す。カードは利用者の言葉の見出し 1 文と平文 4 項目を先に見せ、コードも根拠も畳んだまま決裁できる形にする。

過去セッションの分析では、全 hunk を人間に読ませる画面は実際には読み切られず、即興レビューか読み飛ばしに置き換わっていた。本スキルは「全部読む画面」ではなく、**危ない箇所だけを目立たせて残りは畳む例外ビューア**として動く。全 hunk が画面から消えない検算は維持する — 畳むのは省略ではなく整理。

## 呼び出し前提

**動作確認が収束したあとに呼ぶ。** 収束前に呼ぶと次の順序で壊れる: diff 画面を作る → まず UI を触って動作確認する → 「ここ違う」で修正する → diff が古くなる → レビューが飛ばされてコミットされる。この破綻は実績として観測されている。

主経路は `plan-implement` のフェーズ5（例外ゲート）から Skill ツールで `skill: diff-review, args: plan: <plan のパス>` として起動されること（挙動ゲートであるフェーズ4が収束した後にしか呼ばれない契約）。ユーザーが「diffレビュー」「レビュー画面」で直接叩く従来の使い方も変わらず使える。

HTML 生成の共通規約（自己完結・CDN 禁止・チャットに本文を貼らない・保存先と `open`・style.css の土台）は派生元である同プラグインの `html-report` スキル本文を Read してそれに従う。本スキルはその上に diff レビュー固有のルールを足す。

## Input / Output

- **Input**: `$ARGUMENTS` = 比較の基点 (省略時は `git diff HEAD` + 未追跡ファイル)。`plan: docs/crystallize/plans/<slug>.md` があれば意図解説・昇格判定の根拠にする。指定がなくても `docs/crystallize/plans/` 直下に該当しそうな plan があれば Read する。候補が複数あるときは選ばずユーザーに確認する — 分割 plan は `covers:` が違うので、選び間違えると別の plan の受け入れ基準を通過記録として表示することになる。**plan の先頭に `spec: docs/crystallize/specs/<slug>.md` の行があれば spec も Read し (パスはリポジトリルート (`git rev-parse --show-toplevel`) 基準で解決する)、受け入れ基準の表示は spec の「受け入れ基準 (テストケース表)」から取る** — 要件の正本は spec 側にあり、plan は実装手順しか持たないため。`spec:` 行が無い旧形式の plan (受け入れ基準を plan 内に持つ) は従来どおり plan から取る
- **Output**: 昇格 hunk が 1 件以上のとき — `<projroot>/docs/crystallize/reports/YYYY-MM-DD-diff-review-<slug>.html` を生成して `open`。最終応答は「決裁カード数 (昇格 hunk 数) / 全 hunk 数 + 各カードの見出し文をそのまま (カードが 4 枚を超えるときは、①②のカードの見出しだけを並べ、残りは件数で言う) + ファイルパス」のみ (見出しを要約し直さない — 応答と画面で言葉が変わると、どのカードの話か辿れなくなる)。**昇格 hunk が 0 件のとき — HTML を作らず、最終応答は Step 3 のスキップ規則の 1 行だけ**

## 最重要ルール (理由つき)

- **hunk の検算を必ず通す** — 昇格 hunk 数 + 非昇格 hunk 数の合計が差分全体の hunk 数と一致するまで公開しない。分類に迷う hunk は「未分類」グループに置く (隠すより見せる。⑥として自動的に昇格対象になる)
- **各 hunk は 01 (昇格) か 02 (非昇格) のどちらか一方に一度だけ現れる** — 昇格 hunk を元のグループ側にも重複して残すと、検算の足し算が壊れて意味を持たなくなる
- **diff 本文は必ず HTML エスケープする** — コードには `<div>` や `&&` が普通に含まれる。エスケープ漏れは表示崩れではなく「差分が黙って消える」事故になる
- **解説は素材にある事実だけで書く** — plan・コード・diff から読み取れることだけを書き、推測は「推測:」と明示する
- **昇格判定に迷ったら昇格側に倒す** — 見せすぎの害 (読む数分) と見逃しの害 (不可逆操作の見逃し) は釣り合わない

## Step 1: 差分の収集

```bash
PROJROOT=$(git rev-parse --show-toplevel)
git -C "$PROJROOT" diff <基点> --stat   # 規模の把握
git -C "$PROJROOT" status --porcelain   # 未追跡ファイルの検出
```

- 基点省略時は `git diff HEAD` (staged + unstaged) に加え、未追跡ファイルを「新規ファイル全文の追加」として差分に含める
- 総ファイル数・総 hunk 数・総追加/削除行数をここで確定し、検算の分母として控える。**`M` は「除外後の判定対象 hunk 数」**とする — レビュー対象外のファイル (生成済みレポート `docs/crystallize/reports/`、plan `docs/crystallize/plans/`。Gotchas 参照) の hunk は `M` に数えず、その除外数を別に控える (昇格0件のときの1行に出す)
- 巨大 diff (数百 hunk) は一括で読まず、ファイル単位で分割して Read する
- plan があれば同じタイミングで Read し、実装計画・`## Deviations` 見出し (あれば) を控えておく。plan 先頭に `spec:` 行があればその spec も Read し、要件と受け入れ基準の表を控える。`spec:` 行が無い旧形式の plan は plan 内の確定事項・受け入れ基準を同じ用途で使う (いずれも Step 3 と Step 4 で使う)

## Step 2: 論理グループ化と解説

hunk を **ファイル単位ではなく意図の単位** でグループ化する (同一ファイルの hunk が別グループに割れてよい)。plan があれば plan の実装計画項目とグループを対応づける。各グループに書くもの:

| 項目 | 内容 |
|---|---|
| グループ名 | 変更の意図を表す短い名詞句 |
| タグ | feat / refactor / fix / docs / config / test |
| リスク | 低リスク (挙動不変・局所) / 注意 (共通基盤・広範囲に波及) / 要注意 (データ・削除・セキュリティに触る) |
| 意図 | なぜこの変更か + 影響範囲を 2〜3 文の平易な完全文で |
| 指摘 | diff を読んで気づいた問題点 (あれば)。深掘りは /code-review の仕事なので、目に付いたものだけ |

この「指摘」欄は Step 3 の昇格判定④の入力になる。plan の実装計画項目に対応しないグループは「未分類」として残す (Step 3 の⑥がこれを昇格させる)。グループ別の hunk 数は **昇格した hunk も含めた総数** で数える (Step 4 のヘッダ表示で「うち昇格 n 件」を添えて使う)。

## Step 3: 昇格判定 — 例外ビューアの核

hunk 1 つずつに対し、以下 6 条件のいずれかに該当するか判定する。該当すれば「昇格」、しなければ「非昇格」。

| # | 昇格理由 | 判定材料 | 目安 |
|---|---|---|---|
| ① | データ削除・移行・不可逆操作 | diff 本文・ファイルパス | `DROP`/`DELETE`/`TRUNCATE`/`rm`/`migrations/` 配下/スキーマ変更 (`ALTER TABLE` 等) |
| ② | 対外境界 | ファイルパス・diff 本文 | 公開 API ルーティング・認証・課金・秘密情報 (`.env`/secrets/key)・外部送信の新規呼び出し・CORS/権限設定 |
| ③ | 依存の追加・更新 | ファイルパス | `package.json`/`pubspec.yaml`/`requirements.txt`/`Gemfile`/`go.mod`/`Cargo.toml` 等のマニフェスト |
| ④ | AI レビューの指摘・不一致 | Step 2 の「指摘」欄 | 指摘が載っている hunk |
| ⑤ | plan の Deviations | plan の `## Deviations` 見出し | 確定事項からの逸脱に対応する hunk。plan が無い/見出しが無ければ判定対象外として扱う (エラーにしない) |
| ⑥ | plan にない予想外の変更 | Step 2 のグループ分類 | どの実装計画項目・意図にも紐づかない hunk (= 「未分類」グループ) |

1 hunk が複数条件に当たることがある — 該当した番号を全部控える (Step 4 でバッジとして全部出す)。判定に迷う hunk は昇格に倒す (最重要ルール参照)。

### スキップ規則 — 昇格 0 件なら画面を作らない

昇格した hunk が 1 件も無ければ **HTML を生成せず Step 4 を飛ばす**。最終応答を次の 1 行だけにする (`M`・`N`・`a`・`d`・`X` は Step 1 で確定した実数):

```
全 M hunk 中、昇格 0 件 (①〜⑥該当なし)。N files +a -d (レビュー対象外 X hunk: reports/plans を除外)。go / no-go を
```

除外が0件のときは後ろの括弧ごと省く (「除外 0 hunk」は読み手に何も渡さない)。

宣言チェック 1 個のためだけにブラウザを開かせない — 小さな変更でも画面が出る運用は「作業感」だけを増やし、開かれた画面が読まれない習慣を育てる。**飛ばすのは Step 4 だけで、Step 1〜3 と Step 5 の検算は通常どおり実行する。**

### リスクへの束ね — 決裁の単位は hunk ではなくリスク

昇格した hunk を、**利用者にとって同じ悪い結果を招くもの同士**でまとめる。まとまり 1 つが決裁カード (Step 4) 1 枚になる。判定そのものは hunk 単位のまま — 束ねるのは見せ方であって判定の粒度ではない。

- 束ねる基準は「利用者から見た悪い結果が同じか」だけ。同じファイルにあること・同じ昇格理由であること・同じグループであることは基準にしない — 読み手が決めるのは結果を受け入れるかどうかで、ファイルやコードの区切りは決裁の単位ではない
- **1 カード 1 ファイルに縛らない**。1 つのリスクが複数ファイルにまたがるなら、そのカードに全ファイルの hunk を並べる
- 束ねられない hunk は 1 件で 1 枚にする。無理に束ねない — 別々の結果を 1 枚に混ぜると見出し 1 文が書けなくなる。**書けないことが混ぜた印**なので、書けなければ分ける
- **1 hunk は 1 枚のカードにしか入れない**。2 つの悪い結果を招く hunk は、重いほうの結果のカードに置き、もう一方のカードの根拠に「この変更は <相手の見出し> のカードにある」と 1 行書く (2 枚に置くと、昇格 hunk 数がカードの合計と一致しなくなり、検算が数字として意味を失う)
- 検算 (Step 5) は hunk 単位のまま。カード数を検算の分母にしない — カード数は束ね方で増減するので、分母にすると hunk の取りこぼしが見えなくなる
- 束ねた結果のカード数を控える。ヘッダの要約行と承認プログレスの分母 (Step 4-1)、承認チェックの数 (Step 4-5) がこの数になる

## Step 4: HTML の構成 (昇格が 1 件以上のときだけ)

HTML 骨格・タブ・diff コンポーネント (行番号2列・hunk ヘッダ・sticky ファイルヘッダ・右側ファイルナビ) は base である html-report の `../html-report/references/templates.md` を**構造ごとそのまま使う**。ただし **`<main>` は `class="report report-numbered"` とし、`markdown-body` を付けない** — `markdown-body` の子孫セレクタ (詳細度 (0,1,1)) が components.md の固有部品の単一 class (0,1,0) に勝ち、無改変層で貼ったはずの見た目が崩れるため。diff-review 固有の部品 — 昇格理由バッジ・ヘッダ集計・決裁カード・承認チェック・状態バッジ・保存 JS — の正本は `references/components.md`。CSS/JS ブロックは無改変で貼り、マークアップは同ファイルのスロット規約 (`{…}` プレースホルダと繰り返しコメント) の範囲だけを差し替える。**部品の即興追加・独自 CSS の発明をしない** — 足りない部品は components.md への追記として扱う (散文指示からの即興生成が、レポートごとに見た目が揺れる原因だった)。以下 1〜6 は各部品に流し込む内容の定義:

1. **ヘッダ**: タイトル (タスク名 + 差分レビュー)、`N files / M hunks +追加 -削除`、**「人間が決裁する箇所 <カード数> 件 (昇格 <昇格 hunk 数> hunk) / 全 <判定対象 hunk 数> hunk」の要約行** (決裁の単位と検算の単位が違うので両方出す — カード数だけでは全 hunk が判定を通ったことが読めず、hunk 数だけでは決裁の回数が分からない)、グループ別リスク・指摘の集計 (Step 2 の表をそのまま小さく表示。各行に「うち昇格 n 件」を添える。AI レビューが済んでいる根拠として置く)、承認プログレス「確認 0/N」(N = 承認チェックの数 = 決裁カード数。部品6 JS がこの N を実際のチェック数で上書きするので、昇格 hunk 数を書くとカウンタと食い違う)。レビュー対象から除外した hunk (reports/plans) があれば、その件数と理由を除外の注記 (部品 1 の `review-note`) に書く。0 件なら行ごと省く
2. **受け入れ基準** (spec にあれば。spec が無い旧形式なら plan の該当節から): 挙動チェックリストとしてヘッダ付近に並べる。spec のテストケース表は 1 行 1 項目に畳む (`<seam> — <ケース> → <期待結果>`)。plan に `covers:` 行があれば、そこに列挙された AC の行だけを載せる (他の plan の担当分はこの差分の通過記録にならない)。spec の「UI・見た目など TDD 対象外で挙動ゲート (実機確認) に委ねる基準」も同じリストに続ける。`covers:` に `実機:` の項目があれば、実機確認に委ねる基準とモック確定印の要件はそこに挙がったものだけを載せる。「テストしないと決めたもの」は通過の記録ではないので載せない。ここでチェックさせるのではなく、挙動ゲートを通過済みという記録として表示するだけ。spec も plan の受け入れ基準の節も無ければこの節ごと省略する
3. **01 昇格** (先頭): Step 3 で束ねたリスク 1 件につき決裁カード (部品7) を 1 枚、`01 昇格` 見出しの直下に並べる。**ファイル単位の `<details class="file">` で包まない** — 1 枚のカードが複数ファイルにまたがりうるため。カードの中身は上から順に:
   - **見出し 1 文** (`.decision-headline`。80 字以内): 「<いつ・どの操作で>、<利用者に何が起きうるか>。<取り消せるか>」。**これだけ読めば決裁できる**ことを基準にする — 読み手は挙動ゲートでアプリを触った人で、コードの語彙で書くと決裁に要る情報が 1 つも渡らない
   - 利用者に起きる悪い結果が読み取れない昇格 (③依存追加・⑥未分類でよく起きる) は、型を「<何が入れ替わった・増えたか>。利用者への影響は<推測: …/ 素材からは読み取れない>。」にする。**無理に悪い結果を作文しない** — 素材にない事実を足さない規則が見出しにも効く。読み手が決裁するのは「影響が読めないまま進めてよいか」で、それが正直な決裁の材料になる
   - **4 項目** (各 1 文・60 字程度): **何が起きうるか** (利用者から見た悪い結果。見出しの言い換えにせず、**どんなときに起きるか・どれだけの範囲に起きるか**のどちらかを足す) / **元に戻せるか** (可逆・不可逆 + 戻し方を一句) / **影響範囲** (誰・どのデータ・いつ) / **AI レビューの判定** (「指摘なし」「N 件の指摘はすべて解消済み」「未解消 N 件: <一言>」のいずれか。番号を書かない)。見出し語 4 つと順序は固定で言い換えない — 毎回違う言葉で書くと、読み手が毎回どこを見ればよいか探し直すことになる
   - **根拠は畳む** (`<details class="decision-basis">`「根拠を見る」、既定 closed): 仕組みの説明・code-review の指摘との対応・Deviations との対応・該当 hunk の一覧。識別子を書いてよいのはここから下だけ。該当が無い項目は行を消さず「該当なし」と書く
   - **hunk ごとの diff** (既定 closed): 束ねた hunk を templates.md 正本の `<details class="file">` で 1 件ずつ置く (同じファイルの hunk が 2 件ならブロックも 2 つ。ファイル一覧ナビは同じファイルが登場順に複数出てよい)。決裁に必要なのは見出しと 4 項目であってコードではない。読みたい人は開けるので、畳むのは省略ではない
   - 昇格理由バッジ (①〜⑥、複数可) と元のグループ名はカード頭部にまとめる (束ねた hunk の分を合算し、重複は 1 個に畳む)。バッジを畳んだ中 (`hunk-head`) に置かない — 開くまで昇格理由が見えなくなる
   - **書いてよいのは素材にある事実だけ** (最重要ルール)。「AI レビューの判定」の出所は Step 2 の「指摘」欄と plan の `## Deviations` に限り、どちらにも無ければ「指摘なし」と書く (レビュー結果を創作しない)。可逆性・影響範囲のうち diff・plan・spec から読めない部分は「推測:」を付ける (根拠側の記述も同じ規則)
4. **02 非昇格グループ**: Step 2 のグループ単位で、そのグループに残った非昇格 hunk だけをファイル別 `<details class="file">` (既定 `closed`) に入れる。意図の解説はグループ単位で1つ。非昇格 hunk が0件になったグループはこの節ごと省略してよい (集計はヘッダの表に残っている)
5. **承認チェック — 置き場所はカードの末尾**: 決裁カード 1 枚につき 1 個、カードの**中の末尾** (最後の diff の直後) に置く。読み手がそのリスクを読み切った位置で決裁する動線のため、ヘッダやカードの冒頭には置かない。ラベルは「このリスクを受け入れる」— 求めているのはリスクの受容であって、diff の読了報告でもコードが正しいという判定でもない。チェックの数 = カードの数 = ヘッダの「確認 0/N」の N (ファイル単位に戻さない — 1 枚のカードが複数ファイルにまたがると、ファイル単位のチェックでは「このリスクを受け入れたか」を記録できない)
6. **チェック状態の可視化と保存**: components.md の承認 JS (無改変層) が担う — カードへの `.approved` の付け外し、カード頭部の状態バッジとファイルナビへの反映、ヘッダの「確認 n/N」、localStorage 保存と復元時の完全再適用。保存キーはカードの見出し文。挙動をここに再定義しない (正本は components.md 部品6)。(**見出し文を直したカードは未承認に戻る** — 別のリスクとして決裁をやり直すのが正しい)

### 見出しと 4 項目の語彙 — 素材の語彙を持ち込まない

使ってよいのは、**用語集と spec の要件節にある語、それに日常語だけ**。用語集は `docs/crystallize/CONTEXT.md` (リポジトリ直下の `CONTEXT.md` に `## 用語` または `## Language` があればそちらが正本)、どちらも無ければ spec の「用語」節を使う。コードと plan の語彙をそのまま出すと、読み手 (挙動ゲートでアプリを触った人) には何が言いたいのか分からないカードになる — 決裁のための画面なのに、決裁に使えない情報しか載らない。

**書いてはいけないもの**: 関数名・変数名・クラス名・provider 名などの識別子、ファイル名・パス・拡張子、行番号、hunk 番号、code-review の指摘番号、Deviations の項目番号、`()` 付きの呼び出し表記。これらは捨てるのではなく「根拠を見る」の中と diff の中に置く。

- 悪い例: 「build() がアプリ起動のたびに _reconcileAbandoned() を走らせる (起動時の帳簿整理)。この provider を最初に読んだ時点で、猶予切れの active セッションファイルが書き換わる。」
- 良い例: 「アプリを起動するたびに、中断中の復習フライトが自動で破棄扱いになることがある。判定を誤ると続けられたはずのフライトが消え、元に戻せない。」

**公開前に自己検算する** — 見出しと 4 項目のテキストだけをファイルに抜き出す (**バッジの文言は含めない。dt と dd の間、バッジと本文の間には空白を 1 つ入れる** — 接着すると語の境界が消えて 2) の照合がすり抜ける)。抜き出したファイルに次の 3 つを通す。

```bash
# 1) 明示的な禁止形 — ヒットが 0 であること
grep -nE '[a-z][A-Z]|[a-z0-9]_[a-z]|\(\)|\.[a-z]{1,5}\b|hunk ?[0-9]|指摘 ?[0-9]|項目 ?[0-9]|L[0-9]+|[0-9]+ ?行目' <抜き出したファイル>
# 2) ラテン文字の語をすべて列挙 — 1 語ずつ、用語集か spec の要件節にあるか確かめる
grep -oE '[A-Za-z]{2,}' <抜き出したファイル> | sort -u
# 3) 字数 — 見出しは 80 字、4 項目の説明文は各 60 字を超えないこと
while IFS= read -r line; do [ ${#line} -gt 80 ] && echo "${#line} 字: $line"; done < <抜き出したファイル>
```

- 1) はヒット 0 が条件。ヒットしたら正規表現を緩めるのではなく文を書き直す (ヒットは素材の語彙に引きずられた印であって、検算の粗さではない)
- 2) は 0 件を求めない — **列挙された語が用語集か spec の要件節にあるかを 1 語ずつ確かめる**。無ければ日常語に言い換える。`provider` `build` のような単一語の識別子は 1) に一切かからないので、この照合が識別子を捕まえる本体になる。`API` `JSON` のような略語も同じ扱いで、用語集に載っていなければ言い換える (「例外は綴りで見分ける」という運用にすると、例外かどうかの判断が毎回揺れて検算が機能しなくなる)
- 3) の 60 字は説明文だけを数える (見出し語「何が起きうるか」等は含めない)
- 件数を書くときは数を先に置く (「2 件の指摘はすべて解消済み」)。「指摘 2 件」は指摘番号の「指摘 2」と機械的に見分けが付かず、1) に引っかかる

## Step 5: 検算と表示

- 昇格 hunk 数 + 非昇格 hunk 数の合計 = Step 1 で確定した判定対象 hunk 数 `M` を確認する。**さらに Σ(各カードの hunk 数) = 昇格 hunk 数 = Σ(グループ表の「うち昇格 n」) の 3 つが一致することを確かめる** (カードへの重複収容と収容漏れは、この 3 つの食い違いとしてしか現れない)。合わなければ漏れた hunk を「未分類」グループ (⑥) に収容してから公開する
- **この検算は昇格 0 件でスキップしたときも同じように行い、結果の数字をスキップ規則の 1 行に載せる** — 画面が無くても「全 hunk が判定を通った」ことの担保は数字だけなので、ここを飛ばすと例外ゲートが空回りする
- 保存先・`open`・レポート一覧 (report-index) への登録・gitignore 注意は base の Step 5 に従う (昇格 0 件のときはファイルを作らないのでこの手順ごと不要)

## Gotchas

- 未追跡ファイルは `git diff` に出ない — `status --porcelain` の `??` を拾わないと「新規ファイルだけレビューから抜ける」事故になる
- 承認チェックボックスは「このリスクを受け入れる」という決裁の記録であって、挙動確認の証拠でもコードが正しいことの保証でもない — 挙動確認は上流ワークフローの責任、正しさはテストと AI レビューの責任。チェック状態を根拠に「動作確認済み」「レビュー完了」と親や履歴に報告しない。承認はユーザーの行為であってスキルの成果物ではない
- 昇格 0 件のスキップは**省略ではなく短縮**である — 差分の収集・グループ化・6 条件の判定・検算はすべて実行した上で、出力の形だけを HTML から 1 行に落としている。判定を飛ばして「昇格 0 件」と書けば検算の数字が作れないので、1 行に M・N・追加削除行数を必ず入れる (数字を出せないことが、判定していないことの検出手段になる)
- 生成した HTML 自体 (`docs/crystallize/reports/`) や plan (`docs/crystallize/plans/`) が差分に混ざることがある — レビュー対象から除外し、その旨を画面に一言記す
- spec (`docs/crystallize/specs/`) の hunk は除外しない — spec は残る成果物なのでコミットに入る。ただし実装計画のどの項目にも紐づかないため放っておくと「未分類」= ⑥で昇格する。spec の改訂履歴に今回追加された行を意図として「仕様改訂」グループに対応づける。ユーザー自身が挙動ゲートで決めた改訂を「plan にない予想外の変更」として昇格させると、スキップ規則がほぼ毎回外れる
- plan に `## Deviations` 見出しが無くても、spec が見つからなくても、受け入れ基準の節がどこにも無くても止めない — ⑤の判定と受け入れ基準表示は「該当なし」として省略し、他の判定は通常どおり進める
- 非昇格グループを丸ごと省略したくなるが、「畳む」であって「消す」ではない — 検算の対象から外れた瞬間に「隠すより見せる」の原則が崩れる
