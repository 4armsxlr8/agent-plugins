# plan-create

`spec` が確定させた要件 (`docs/crystallize/specs/<slug>.md`) を受け取り、**実装手順** を plan (`docs/crystallize/plans/<slug>.md`) に書き出すスキル。通常は 1 枚。spec が大きく、触るモジュールが重ならず単体で挙動確認できるまとまりに分かれるときだけ複数枚に分ける (手順 3)。1 plan = 1 まとまりのコミット (plan-commit がリファクタと機能変更を分けることはある) なので、分割はコミットの単位を決める判断でもある。
plan は使い捨ての文書で、後段の `/plan-commit` がそのままコミットメッセージ本文にして削除する。要件は spec 側に残るので、plan には手順と、手順を安全にするための情報 (守るべき既存挙動・検証コマンド) だけを書く。

要件を新しく決めることは本スキルの仕事ではない。決め直しが必要になったら `spec` に戻す (手順 2)。

## Input / Output

- **Input**: `$ARGUMENTS` = `docs/crystallize/specs/<slug>.md` のパス。`spec` スキルが複数タスクを扱った場合は**複数の spec パスを渡してもよい** (spec ごとに plan を書き、並列可否の仕分けは手順 6)。省略時は `docs/crystallize/specs/` 直下で最も新しい `.md` を1行で確認する。spec が1つも無ければ plan を書かず、`/spec` で先に要件を決めるよう案内して終了する — spec のない plan は要件を実装計画の中で暗黙に決めることになり、それが決まった経緯がどこにも残らない
- **Output**: `{projroot}/docs/crystallize/plans/<slug>.md` (plan 本体)。作業ファイルは `{projroot}/docs/crystallize/plans/<slug>/` 配下 (`impact.md`)。slug は spec と揃える。分割したときは `plans/<slug>-<n>-<部分名>.md` と同名ディレクトリを plan ごとに作る (手順 3)

## 最重要禁則

1. **プロダクトコードを書かない・編集しない**。Write してよいのは `docs/crystallize/plans/<slug>.md` と `docs/crystallize/plans/<slug>/` 配下のみ。
   理由: impact で既存コードを読み込んだ直後は「ついでに直せる」が最も湧く区間で、書き始めた瞬間に計画がそのコードを正当化する方向へ歪む (サンクコスト)。実装は plan と spec を受け取った別セッションの仕事。spec の書き換えが必要になったら自分で編集せず `spec` スキルを改訂モードで起動する (手順 2)。
2. **要件を plan で決め直さない**。決まっていない要件に気づいたら、実装計画の一項目として埋めずに `spec` へ戻す — ユーザーが見ていない要件が計画に紛れ込むと、どこで決まったかが追えなくなる。

## 手順

### 1. spec を読む

spec を Read し、ゴール・要件・受け入れ基準 (テストケース表)・スコープ外・用語を把握する。あわせて**用語集** (リポジトリ直下に `## 用語` か `## Language` を持つ `CONTEXT.md` があればそれ、無ければ `docs/crystallize/CONTEXT.md`。どちらも無ければ spec の用語節) を Read し、plan 本文の語はそれに従う — plan で語を言い換えると、実装とテストが spec と別の名前を使うことになる。ledger や mock.html は読まない — 決着した論点の経緯は実装に不要で、読むと plan が経緯の再説明で膨らむ。UI の決定も mock.html を開かずに済む — 必要なのは spec の「見た目の正本」節にある確定案の `mock.html#variant=<id>` と確認した状態だけで、手順 4 で UI を含む項目に添える参照になる (経緯ではなく決定そのもの)。

### 2. impact — 守るべき既存挙動の裏取り

開発途中プロジェクト特有の論点 (すでに動いているものとの整合性) を Explore subagent で裏取りし、`docs/crystallize/plans/<slug>/impact.md` に書く。

- 変わる既存挙動 (ユーザーから見えるもの優先)
- 移行が必要なデータ・設定
- 触ってはいけないもの (依存されている挙動・公開インターフェース)
- 変更が及ぶファイル・モジュールの集合 (受け入れ基準ごとに、どの AC がどこを触るか) — 手順 3 の分割判定と手順 6 の交差判定はこの集合だけを根拠にする

**impact から要件レベルの新しい論点が出たら、plan を書き進めずに `spec` スキルを改訂モードで起動する** (Skill ツール、args = spec のパス)。例: 既存挙動と要件が両立しない、移行の可否をユーザーが決めていない。ここで自分で決めると、ユーザーが決めていない要件が実装計画の一項目として紛れ込む。

### 3. 分割の判定

1 つの spec から plan を何枚作るかを決める。**既定は 1 枚**。次の 3 条件を**すべて**満たす AC のまとまりが 2 つ以上あるときだけ分ける:

1. **触るモジュールが重ならない** — impact で見たファイル・モジュールの集合が、まとまりごとに交差しない (交差する分割は、分けても先の plan の完成を待つだけで、並列にも独立した確認にもならない)
2. **その部分だけで受け入れ確認を閉じられる** — そのまとまりが担当する AC を、その plan の完了時点で確認できる。UI を含むまとまりは挙動ゲート (実機) で、含まないまとまり (データモデル・API など) は機械ゲートのテストだけで確認が閉じること。**担当 AC の確認が次の plan を待つまとまりは分けない** — テストが緑でも「意図どおりか」が最後まで分からず、1 plan = 1 まとまりのコミットの前提 (コミットの時点で確認が済んでいる) が崩れる
3. **分ける価値がある大きさ (spec 全体で判定する目安)** — 実装計画の見積もりが 8 項目を超えそう、または impact に挙がったモジュール (プロジェクトの慣習に従う単位) が 3 を超える。数字は固定の閾値ではなく目安で、根拠は「1 コミットとして人がレビューできる幅」と「plan 1 枚あたりの監査・コミットの固定費」の釣り合い。小さな spec を分けると固定費だけが増える

分け方:

- まとまりは「一緒でないと動かない AC」の単位で作る。1 つの AC を複数の plan に割らない
- 順序は plan 群にも「変わりやすい順」を適用する — データモデル・見える挙動を含む plan を先にする。ただし `depends-on:` を書くのは、**後続が先行の成果物 (新しい型・API・データモデル) を呼ぶ場合だけ**。ファイルは交差しないが依存はある、という関係がこれにあたる。互いに独立した機能に分けたなら順序は付けず (`depends-on:` を書かず)、手順 6 で並列に配置できる
- 目安として 1 spec につき 4 枚まで (同時に追える worktree とレビューの数の目安)。5 枚以上に分けたくなるのは spec が複数の機能を抱えている印なので、spec を分ける方向で `spec` の改訂モードへ戻す
- **2 枚以上に分けると判断したときだけ**、配分を 1 行でユーザーに示して合意を取る (「N 枚: <各 plan の名前と covers>。理由: <満たした条件>」)。分割は実装の順序とコミットの単位を決める判断で、ユーザーが後から変えると plan の書き直しになる。1 枚のとき (既定) は合意を取らず手順 4 へ進む

命名: 分割した plan は `docs/crystallize/plans/<slug>-<n>-<部分名>.md` (`<n>` は 1 起点の実装順、`<部分名>` は spec の slug と同じく英小文字とハイフン。例: `share-card-1-share-link.md`, `share-card-2-recipient-page.md`)、作業ファイルは同名のディレクトリ `plans/<slug>-<n>-<部分名>/`。**impact.md は plan ごとに、そのまとまりが触るファイル・モジュールの行だけに絞って各ディレクトリへ書き直し、元の `plans/<slug>/` は削除する** — 全文をコピーすると手順 6 の交差判定が同じ内容同士の比較になって必ず交差し、元のディレクトリを残すと plan-commit がどの plan の削除対象にも入れられず最後まで消えない。

### 4. plan の書き出し

`docs/crystallize/plans/<slug>.md` を次の形式で書く (分割した場合は plan ごとに 1 枚ずつ)。

```markdown
# <ゴール 1 文 (spec の先頭行と同じ。分割した plan は「— <部分名>」を添える)>

spec: docs/crystallize/specs/<slug>.md
covers: AC-1, AC-2, AC-5
depends-on: docs/crystallize/plans/<slug>-1-<部分名>.md

## 守るべき既存挙動
impact の要点 (変わる既存挙動 / 移行が必要なデータ・設定 / 触ってはいけないもの)

## 実装計画 (変わりやすい順)
1. ユーザーが差し替えたくなる可能性が高いもの (データモデル・型・見える挙動) を先頭
2. …
N. 機械的な作業 (リファクタ・配線・テスト整備) は末尾にまとめて 1 項目
各項目に「対応する受け入れ基準の ID (AC-n)」と「TDD 対象 / 対象外」を添える。UI を含む項目にはさらに「見た目の正本: docs/crystallize/specs/<slug>/mock.html#variant=<id> (確認した状態: many)」を添える

## 検証コマンド
テスト・lint のコマンドを 1 行ずつ

## Deviations 規約
計画から逸れる必要が出たら保守的な選択を採り、この plan の `## Deviations` に理由ごと追記して続行する。確定した要件と矛盾する逸脱 (エージェント発) は止めてユーザーに戻す。ユーザー発の仕様変更は spec の改訂として扱う (plan-implement 挙動ゲートの仕様改訂レーン)。
```

- `covers:` と `depends-on:` は `spec:` 行と同じ先頭ブロック (最初の `##` 見出しより前) に置き、1 行 1 キーで書く。`covers:` の値はカンマ区切りの列挙 (範囲記法は使わない — 読む側が 4 スキルあり、解釈が割れる)。どちらも**分割したときだけ**書く。`covers:` はこの plan が実装する受け入れ基準の ID の列挙で、省略時は spec の全 AC を意味する
- `covers:` には AC ID に加えて、この plan が担当する **ID の無い基準** (spec の「実機確認に委ねる基準」と「(モック確定・実機で再確認)」印の要件) を `実機: <基準の冒頭>` の形で列挙する (例: `covers: AC-3, AC-4, 実機: カード余白の見え方`)。ID が無い基準は `covers:` でしか担当を示せず、書かないと全 plan の挙動ゲートに重複して並ぶか、どの plan でも確認されないまま流れる
- `depends-on:` は先行 plan のパスで、無ければ行ごと書かない。**先行 plan が plan-commit で消えていても後続 plan に注記は足さない** — 消えた plan の本文はコミットメッセージに丸ごと残るので、監査側が `git log` から `covers:` を回収する (手書きの注記は書く責任者が決まらず、実際には付かない)
- **並び順が本体**: ユーザーは先頭だけ精読すればよい、という設計にする。網羅的で長い計画は読まれない
- **UI を含む項目 (spec の「実機確認に委ねる基準」か「(モック確定・実機で再確認)」印の要件に対応するもの) には見た目の正本の参照を添える** — spec の「見た目の正本」節から確定案のパス (`mock.html#variant=<id>`) と確認した状態を写す。値 (調整パネルの JSON) は spec にあるので転記しない。参照が無いと `plan-implement` は実装者にモックを渡せず、実装者は要件行の言葉だけから UI を書く (モックと実装の質感が乖離した実績がある)。spec の同節が「該当なし」なら書かない
- `covers:` の各 AC (無ければ spec の全 AC) が、いずれかの実装計画項目に対応していること。対応しない行が残るなら計画に漏れがあるか、spec に実装不能な基準がある (後者なら手順 2 と同じく spec へ戻す)。分割した場合は plan 群の `covers:` の和集合が spec の全 AC と一致し、同じ AC が 2 枚に現れないこと
- 要件・受け入れ基準そのものを plan に転記しない — 二重管理になり、spec を改訂したときに plan 側が古いまま残る。plan-implement は spec も読む

### 5. 監査 (必須)

書き出した plan は、ユーザーに提示する前に `plan-evaluator` (Skill ツール、fork 実行) に監査させる。args = context JSON のパス (次の箇条書き)。誤前提・計画から漏れた受け入れ基準は実装後の手戻りとして跳ね返るため、ここで止める価値がある。

- 渡すのは context JSON (plan のパスを含む) だけ。impact.md は渡さない — 監査が plan + spec だけで行われることが、plan の自己完結性の検査を兼ねる
- 起動時は context JSON を `docs/crystallize/plans/<plan の basename>/eval-context.json` に書いて渡す (`project_dir` / `plan` / `output_contract.eval_file` = `docs/crystallize/plans/<plan の basename>/eval-plan-<稿数>.json`)。パスだけを渡すとフォールバック経路に入り、eval JSON がプロジェクト直下の `output/` に落ちて `plan-commit` の `git add -A` で履歴に紛れ込む。plan と同名のディレクトリに置けば plan-commit が plan ごと消す
- **分割した場合は全 plan を書き切ってから、1 枚ずつ順に監査に出す** — 和集合の検算は兄弟が全部揃っていないと成立しない。監査の指摘で**どれか 1 枚の `covers:` を変えたら、兄弟も全部再監査する** (和集合が変わるため、他の plan の合格が陳腐化する)
- eval ファイル名の `<稿数>` は 1 稿目・2 稿目の番号で、分割 plan の `<n>` とは無関係。plan ごとに自分のディレクトリに置くので衝突しない
- `passed: false` なら指摘箇所を裏取りからやり直して plan を修正し、再監査にかける。`rewrite` (見出し単位の置換案) が返っていればそれを基にする
- **2連続不合格で停止**: 監査が2回連続で `passed: false` になったら、3稿目を書かずに止まる。`score` と不合格の具体的理由 (`feedback_structured.high`) をユーザーに提示し、**plan の底にある前提かゴール自体が間違っていないか**を直接尋ねる。3稿目はその回答を反映してからにする (以降も同様)。同じ plan が2稿続けて落ちるのは、文面の磨き込み不足ではなく前提側の誤りのシグナルとして扱う

合格したら要点をチャットに示す (30 行を超えるなら `html-report` で HTML 化する。plan 本体は md のまま)。

### 6. 複数 plan の仕分けと配置

複数の spec から、または 1 つの spec を分割して複数の plan を作った場合、全 plan の impact を突き合わせ、触るファイル・モジュールの交差を判定する — 交差しなければ並列可、交差するなら順序を決めるか1本に統合する。同じ spec を分割した plan 同士は、交差の判定を手順 3 で済ませてある (条件 1) ので、ここでは再判定せず `depends-on:` の有無だけを見る。突き合わせるのは別 spec 由来の plan と、進行中の他 worktree の plan (交差の基準は同じ)。`depends-on:` で繋がった plan 群は定義上順序があるので並列にしない (先行を先に実装し、後続は同じ worktree で続けて渡す)。仕分け後の探索で見えていなかった交差が判明したら、並列をやめて順序提案に切り替える (誤った並列はマージ衝突として跳ね返る)。

並列可と判定したら**並列配置** (どの worktree でどの plan か・交差したものはどの順序か) を小さな表で提示して合意を取る。**合意後の配置は案内で終わらせず、本スキルが自分で実行する** (案内文止まりの接続は実際には実行されない、が過去セッションで繰り返し観測された失敗の型):

1. `git worktree add` で worktree を作成する (git ネイティブ機能 — 特定ツールに依存しない)
2. `plans/<plan の basename>.md` と `plans/<plan の basename>/` を担当 worktree へ移動する。**spec は追跡状態で扱いを分ける** — `git ls-files --error-unmatch specs/<slug>.md` が通る (追跡済み) なら worktree 側に既に同じファイルがあるので、**移動せず、未コミットの改訂分だけをコピーする** (`mv` すると本流の作業ツリーに spec の削除が残る)。追跡されていない (今回新規に書いた) spec は `specs/<slug>.md` と `specs/<slug>/` ごと移動する — コミットされていないため worktree には現れず、移し忘れると実装セッションが plan 先頭の `spec:` 行を解決できない
3. 各 worktree で対話セッションを起動し、`/plan-implement <plan の絶対パス>` を最初のプロンプトとして渡す。**起動手段は本スキルが決めない** — 環境にセッション起動を担う道具 (worktree 管理ツールや端末の自動化) があればそれを使い、無ければ worktree ごとの雛形プロンプトを提示してユーザーに各ターミナルで開いてもらう。特定の製品名をここに書かない — プラグインは配布物で、利用者ごとの道具は利用者側のスキルや CLAUDE.md が担う。`depends-on:` で繋がった plan 群は先頭の 1 枚だけを送る — 後続は先行の plan-commit が終わってから、同じセッションで次の `/plan-implement` を送る

以降の対話 (挙動ゲート・例外ゲート) は各 worktree のセッションが直接ユーザーと行う。本セッションは配置の完了報告 (worktree 一覧と各セッションの状態) で終了し、司令塔として残らない。

### 7. 案内して終了

**新しいセッションで** `/plan-implement` に plan を渡して実装を開始する旨を案内する。分割した場合は `depends-on:` の順に plan を並べ、1 枚ずつ plan-commit まで通してから次に進むよう添える (後続 plan は先行のコミットを前提に書かれている)。実装 → テスト → 動作確認 → diff の例外確認 → plan-commit までは plan-implement が一本で駆動する。案内と一緒に、新しいセッションにそのまま貼れる最初のプロンプトをコードブロックで提示する (絶対パスで書く — 新セッションがどの cwd で開かれても迷わないため):

```
/plan-implement /path/to/docs/crystallize/plans/<slug>.md
```

## Gotchas

- **plan 本文から `plans/<slug>/` へ相対リンクを張らない** — plan は `/plan-commit` でコミットメッセージになり、`plans/<slug>/` はその時点で削除される。リンク先が消えた文書が履歴に残る。`specs/<slug>.md` へのリンクは可 (spec は残る)
- **プロンプトに plan の要約を膨らませない** — 実装に必要な情報が文書の外に漏れ出すと二重管理になる。足りない情報に気づいたら plan か spec 側に書き足す
- **分けるために分けない** — 手順 3 の 3 条件を満たさない分割は、並列にも独立した確認にもならず、コミットと監査の回数だけ増える。迷ったら 1 枚にし、実装中に大きすぎると分かったらその時点で残りを別 plan に切り出す方が安い
