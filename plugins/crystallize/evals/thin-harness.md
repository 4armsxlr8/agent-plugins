# 実装のルール

plan と、その先頭の `spec:` が指す spec を読んでから実装する。

- spec の受け入れ基準表を完了の定義とする。`covers:` があれば、そこに挙げた AC だけを実装する
- 受け入れ基準表と「テストしないと決めたもの」を黙って書き換えない。表にないケースのテストを足さない。足すべきだと思ったらユーザーに確認する
- 識別子と表示文言は用語集 (リポジトリ直下の `CONTEXT.md`、無ければ `docs/crystallize/CONTEXT.md`、無ければ spec の用語節) の語を使う。「使わない語」を持ち込まない
- 計画から逸れるときは、影響が可逆で局所的なら保守的な選択を採り、plan の `## Deviations` に理由を書いて続ける
- 要件と矛盾する逸脱や plan にない大きな変更に気づいたら、続けずに止まってユーザーに聞く
- テストを通すためにテストの期待値を変えない。テストに誤りがあると思ったらユーザーに聞く
- 同じ失敗を 3 回直して解消しなければ止まり、実装方針が誤っていないかをユーザーに聞く
- 入出力で期待が決まる振る舞いは、受け入れ基準表からテストを先に書いて失敗を確かめてから実装する
- 完了の判定は、最後のコード変更のあとに自分で全テストを実行した結果で行う。サブエージェントの報告だけで完了にしない
- コードレビューは実装したのとは別のコンテキストで行う。壊れる具体的な状況か、反する要件・受け入れ基準・plan の項目を書ける指摘を直す。迷ったら直す
- 対外境界か依存追加に触れる変更はセキュリティレビューも行う
- plan の E2E 評価の対象面が「なし」でなければ、実装を知らないコンテキストで動くものを spec どおりに操作して確かめる
- ユーザーの go なしにコミットしない
