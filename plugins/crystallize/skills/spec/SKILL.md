# spec

実装に入る前に、何を作るかをユーザーと詰め切って **spec 一枚** (`docs/crystallize/specs/<slug>.md`) に書き出す認識合わせ専用スキル。
spec は実装手順ではなく要件の文書で、リポジトリに残り、改訂履歴を持つ。実装手順は後段の `/plan-create` が別文書として書く。

**要件は固定するものではなく育てるもの。認識合わせでどれだけ詰めても、UI は触って初めて分かることが残り、リリース後に利用者の声で変わることも普通にある。忠実性とは『黙って逸れないこと』であって『変えないこと』ではない。**

この前提があるので、本スキルのゴールは「二度と変わらない仕様」ではなく「今わかっていることが漏れなく書かれ、変わったときに戻ってこられる文書」を作ることにある。網羅性ではなく、決めた理由と失ったものが追える状態を目指す。

## Input / Output

- **Input**: `$ARGUMENTS` = タスクの説明。省略時は直近の会話から推定し、一行で確認を取る。既存 spec のパスが渡されたら **改訂モード** (Step 0 参照)。**複数タスクをまとめて渡してもよい — 上限3本** (それ以上はセッションが長くなり、論点がゴールからドリフトする)。複数の場合も各タスクに Step 0〜4 をフルに回して spec を1枚ずつ書く — まとめるのは対話の場であって、詰めの深さではない。`$ARGUMENTS` に `audit: on` が含まれていたら、そのトークンを取り除いた残りをタスクの説明として扱い、Step 2 の質問監査を有効にする (トークンを残すと slug やタスク要約に混ざる)。slug はゴール 1 文から英小文字とハイフンで 3〜5 語に圧縮する (例: `share-card-link`)。plan・plan-implement・plan-commit・diff-review はこの slug をそのまま使う
- **Output**: `{projroot}/docs/crystallize/specs/<slug>.md` (spec 本体。追跡ファイルとして残る)。作業ファイルは `{projroot}/docs/crystallize/specs/<slug>/` 配下

| ファイル | 寿命 | 中身 |
|---|---|---|
| `docs/crystallize/specs/<slug>.md` | 残る | **最終成果物**: spec 本体 (改訂履歴つき) |
| `docs/crystallize/specs/<slug>/ledger.md` | 残る | design tree (論点と依存) / 確定事項 / 監査記録 |
| `docs/crystallize/specs/<slug>/mock.html` | 残る | **ラウンドシート**兼反応用モック (1タスク1ファイル。案はファイル内で切り替え、質問と回答パネルも同じ画面に載る。ラウンドをまたいで同じファイルを育てる) |
| `docs/crystallize/specs/<slug>/question-round-<n>.md` | 残る | 質問監査を行った場合のみ作る監査入力 (Step 2)。シートの QUESTIONS 宣言から起こす |
| `docs/crystallize/specs/<slug>/eval-context.json`, `eval-question-round-<n>.json` | 残る | 質問監査を行った場合のみ作る監査の context と eval JSON (Step 2)。監査件数の正本は ledger なので、残っても読み返す必要はない |
| `docs/crystallize/CONTEXT.md` (置き場の判定は Step 0) | 残る | **用語集**: プロジェクトに 1 つだけ置く語の正本。spec をまたいで育つので `<slug>/` の外に置く。**書き手は `spec` だけ** — 例外は `plan-implement` の仕様改訂レーンで、あの場面の plan-implement は spec の編集者として動いているため (書き手を増やすと、同じ語の定義が別々に足されて揺れる) |

## 最重要禁則

1. **プロダクトコードを書かない・編集しない**。Write してよいのは `docs/crystallize/specs/<slug>.md`、`docs/crystallize/specs/<slug>/` 配下、そして用語集 (Step 0 で判定した `docs/crystallize/CONTEXT.md` かリポジトリ直下の `CONTEXT.md`) のみ。
   理由: コードを書き始めた瞬間、認識合わせが「もう書いたコード」を正当化する方向に歪む (サンクコスト)。実装は spec と plan を受け取った別セッションの仕事。例外: `html-report` が生成する `docs/crystallize/reports/` 配下の HTML (報告の体裁であって成果物ではないため)。hook へ昇格する場合もこのパスと用語集は除外する。
2. **会話だけで合意を確定させない**。当たり前すぎて話題に上がらない好みは質問では出てこない。各 Step は必ず「見て反応できる成果物」(モック・代替物・spec 案) を返し、反応をもって確定とする。

## Step 0: 既存文書との突き合わせ

まず**用語集を Read する**。置き場の判定はこの順で行い、以降のすべての Step はここで決まった 1 ファイルだけを用語集として扱う:

1. リポジトリ直下に `CONTEXT.md` があり、その中に `## 用語` または `## Language` 見出しがあれば、**それが正本**。この場合 `docs/crystallize/CONTEXT.md` は作らない (直下の `CONTEXT.md` を使う別の運用と同じファイルを共有するため。用語集を 2 つに割ると、どちらが正かを読む側が決められなくなる)
2. それ以外は `docs/crystallize/CONTEXT.md` が正本 (直下に `CONTEXT.md` があっても用語の見出しを持たないなら、それは用語集ではない — 別の目的のファイルに語を書き足さない)
3. どちらも無ければ用語集はまだ無い。ここでは作らない (Step 2 で最初の語が確定した時点で `docs/crystallize/CONTEXT.md` に作る)

続けて `docs/crystallize/specs/` の既存 spec を一覧し、**今回の依頼と同じ画面・モジュール・データに触れるもの**を読む。**用語集が無いとき、または用語集をこの spec で初めて使うとき (Step 2 の移行のため) だけ**、それらの「用語」節も読む — 用語集があるなら語の正本はそちらで、spec の用語節はその spec で決めた・変えた語の記録でしかない (spec が溜まるほど用語節の読み集めは重くなり、同じ語の食い違う定義を並べて読むことになる)。

- 既存 spec の記述と今回の依頼が食い違っていたら、**最初のラウンドの質問として突きつける** (例: 「既存 spec では X を Y としていますが、今回は Z にしたいということですか」)。ここで拾わない矛盾は、実装後に「前に決めたことと違う」として跳ね返る
- **用語集の語・コードの識別子・今回の依頼の語の食い違い**も同じく質問にする (例: 「用語集では X を Y と定義していますが、今回は Z の意味ではありませんか」「コードでは X を Y と呼んでいますが、用語集の Z と同じものですか」)。直すのは合意を取ってから — どちらが正かを自分で決めない。検出は用語集の側から回す — **各語と、その語の「使わない語」に挙がっている同義語を識別子として `grep -rin` し、ヒットした語がコードで何と呼ばれているかを見る** (依頼の語から探すと、用語集にしか無い語の腐りが見つからない)。用語集が空か存在しないときはこの手順ごと不要
- コードとユーザーの説明が食い違うときも同様に質問にする
- 既存 spec も用語集も無ければこの Step は 1 行 (「既存 spec・用語集なし」) で終える

**改訂モード** (`$ARGUMENTS` が既存 spec のパス): 全文を作り直さない。

1. spec を Read し、**記述とコードの現状がずれていないか**を先に確認する (spec を残す方針の代償はこの乖離なので、改訂のたびに必ず見る)。ずれていたら改訂履歴に「リリース後」として先に1行入れる。**用語集の語とコードの識別子の食い違い**もこの乖離チェックに含める — 用語集も残る文書なので、放置すると spec と同じ形で腐る。直すのは質問で合意を取ってから (自分で決めない)
2. 今回の変更点だけを design tree にし、差分の論点だけを Step 2 のラウンドにかける
3. 変えた項目を改訂履歴に追記する。触っていない節は触らない

## Step 1: design tree の初期化と blindspot

タスクを1行に要約して `docs/crystallize/specs/<slug>/ledger.md` を作る。台帳は 3 節:

| 節 | 中身 |
|---|---|
| design tree | 論点と、その論点が前提にしている別の論点 (依存)。解決した論点は印を付ける |
| 確定事項 | 決まったことと、決めた理由・失ったもの |
| 監査記録 | 質問数 / 監査した数 / 不合格数 / 不合格の理由 (Step 2) |

Explore subagent でコードベースを探索させ、結果を「ユーザーがまだ考えていなさそうな論点」に翻訳して tree に足す。

- 探索対象: タスクに関係する既存実装・命名や構造の慣習・過去の設計判断の痕跡・触ると壊れやすい箇所
- **探索の完了を待たずに Step 2 へ進む** — 待つとユーザーが手空きになる時間が伸びるだけで、質問の質は上がらない。具体的には (a) 背景実行できる環境なら Explore を背景で起動し、そのまま第1ラウンドを提示する (b) できない環境なら、依存のない論点だけで第1ラウンドを先に提示し、**ユーザーが答えている間に** Explore を走らせる。どちらの場合も探索結果に依存する質問は次のラウンドに回す
- 親は要約だけ受け取る (探索の生ログを親 context に吸わせない)
- 一般論の注意点は論点にしない。このコードベースの実物に grounding した論点だけが論点になる

**各ラウンドの冒頭で ledger 先頭のタスク要約を読み直す** — 長い認識合わせでは論点がゴールからドリフトする。要約に対して意味のない論点は深追いせず捨てる。

## Step 2: grilling ラウンド

design tree の **frontier** — 前提にしている論点がすべて解決済みの論点 — を洗い出し、**1ラウンドにまとめて番号付きで出す**。まだ open な論点の答えに依存する質問は次のラウンドへ送る (依存関係が段階化を自動的に作るので、一問ずつ聞く必要はない)。

**事実質問と決定質問を分ける**。コードベース・API 仕様・ライブラリの機能有無・プラットフォーム制約は事実であってユーザーの好みではない — Explore / WebSearch / WebFetch / 公式ドキュメントで自分で取る。ユーザーに聞くのは好みと優先順位だけ。事実をユーザーに聞くと、ユーザーは推測で答え、その推測が確定事項として記録される。

### 出し方 — ラウンドシート (HTML) と貼り戻し

ラウンドの質問は **ラウンドシート** `docs/crystallize/specs/<slug>/mock.html` に載せてブラウザで見せ、回答は、ユーザーがシートの [貼り付ける文章を作る] で作った固定形のテキストをターミナルに貼り戻す形で受け取る (形は `references/reply-format.md`)。シートの実体はモックキット (`references/mock-kit.md`) で、案 (variant)・調整パネル・回答パネルが同じ画面にある — **絵を見る場所と答える場所を分けない**。ターミナルの選択肢ダイアログで答えさせると、選ぶ瞬間に絵が画面に無く、案の採否と理由が口頭の散文として agent の解釈を一度通る。

- **1 ラウンド = 1 往復**。質問と、そのラウンドの絵 (案・調整パネル・代替物) を同じシートに置く。質問はシートの `QUESTIONS` 宣言に書く (`id` / `title` / `question` / `premise` / `recommended` / `reason` / `options[{id, label, gain, loss, variant?, rejected?}]`) — 上の質問フォーマットの 4 行を写す (`question` = 質問行、`premise` = 前提行、`gain` / `loss` = 選択肢の得られる / 失われる挙動、`recommended` + `reason` = 推奨行の答えと理由)。**`QUESTIONS` と `ROUND` は親が書く** (案の作成は Step 3 でサブエージェントに委任するが、問いは出題側の仕事)。案を選ばせる問いは選択肢に `variant` を付ける — 選んだ瞬間にステージがその案に切り替わり、選ぶときに絵が見えている。案の `data-variant` と `data-variant-name` は親が委任前に決めて渡す (綴りが食い違うと選んでもステージが動かず、誰にも気づかれない)。案が 0 のシート (第 1 ラウンドなど、まだ絵が無いとき) は親がキットを複製して `QUESTIONS` だけ書く
- **推奨は既定で選ばれた状態で出す。無回答 = お任せ = 推奨で確定。** ユーザーは推奨に反対する問いだけ触ればよい。「選ばない (お任せに戻す)」は明示の委任で、同じ扱い
- **1 ラウンドの問数は 3±1。5 問以上並べない** — 人の判断コストが本体。frontier がそれより広ければ、設計を大きく動かす順に切り、残りを次のラウンドに送る (ラウンドが増えるのは構わない。1 ラウンドが重いと往復そのものが止まる)
- **同じファイルをラウンドをまたいで育てる**。`ROUND.round` を進め、前のラウンドで決まった問いは消す。**前のラウンドで捨てた案は取り消し線で残す** (`.cz-variant` に `data-rejected`、`data-variant-name` の前に「(不採用)」)。決まった問いを絞って問い直すときは、落ちた選択肢を消さず `rejected: true` で取り消し線にして残す — どちらも「これは前に落とした案か」を人の記憶に頼らせないため
- 問いが 0 (モックへの反応だけ求める) でも、案が 0 (見た目のないラウンド) でもシートは出す — 案が無ければ回答パネルがステージの位置にインラインで出る。見た目のないタスクの代替物 (API レスポンス例・CLI 出力例) はフレームの中に静的に置く
- **貼り戻しが届く前に次のラウンドや Step 4 に進まない** — 確認ゲートの意味が消える。待つ間は Explore の結果の翻訳など、回答に依存しない作業をする
- 貼り戻された回答は `references/reply-format.md` の規則で読む。`(未選択 = お任せ)` の問は推奨で確定。「見ていた案」「調整パネル」の行は、ユーザーが最後に見ていた案と値なので、案の採否の問いの答えと食い違えば問い直す。「全体へのコメント」に設計を変える指摘があれば design tree に足す
- **フォールバック**: ブラウザで開けない環境 (ssh・コンテナ・`open` が無い) では、絶対パスと `file://` URL を示してユーザーに開いてもらう。それも不可能なときだけ AskUserQuestion に落とす — 4 行を question 本文と option の説明に写し、1 回 4 問まで。focus mode では AskUserQuestion で終わるターンの地の文が表示されないので、文面の質問と同じターンに混ぜない。この経路では選択の確定の復唱を省かない

### 試問 — シートを見せる前の検査

シートを開く前に、**文脈ゼロの subagent** (Agent ツール、general-purpose。fork は文脈を引き継ぐので使わない) にシートの絶対パスと読者宣言 1 行 (誰が読むか + 説明なしで使ってよい語) だけを渡し、**同期で結果を待つ**。作業の経緯・コード・会話は渡さない — 書き手は題材の全文脈を頭に持っているので「これで伝わる」の自己判定は構造的に甘い。問いが 1 つ以上あるラウンドでは必ず行う。検査は 4 つ:

1. **弁別** — 各問について、それぞれの選択肢を選んだ場合の画面や挙動の違いを、シートだけから説明できるか。`variant` の付いた選択肢は、対応する `data-variant` の markup を読み比べて、案どうしの構造が実際に違うと言えるか (ブラウザ表示の道具がある環境では切り替えて見てよいが、無くても HTML を読めば判定できる形で問う)。説明できない問いを挙げる
2. **実質 1 択** — 推奨でない選択肢を選ぶ理由 (`gain`) が読み取れるか。読み取れない問いを挙げる (その問いは人に判断を求めていない)
3. **音読** — 音読して不自然な文・意味の取れない文を逐語で挙げ、30 秒で趣旨を 3 文で言う
4. **内輪語** — 読者宣言の許可語の外で、説明なしに使われている語・初見の造語を列挙する

落ちた問いは直す — 弁別できなければ絵を加えるか案の構造を分け直す、`gain` が書けなければ実質 1 択なので問いを落として推奨で進める、内輪語は注釈でなく一般語に置き換える。再試問は同じ subagent に差分だけ送って 1 回、**計 2 巡で打ち切る**。2 巡目に残ったのが軽微 (語彙 1〜2 語・語順) ならそのまま出す。重大 (選択肢の弁別不能・意味の取れない文) なら 3 巡目に進まず、読者宣言に戻ってラウンドを組み直す — 検査で磨ける限界を超えているのは書き手側の問題だから。試問は下の質問監査の代わりではない — 質問監査は前提と二択の論理を、試問は読み手に伝わるかを見る (読みやすさのうち文面だけで判定できる 2 点、音読と内輪語は質問監査も `legibility` として採点する)。

### 質問フォーマット

```
Q<n> <題>
前提: <この質問が前提にしていること。違っていたら前提側を撃ってください>
質問: <挙動の選択肢として書く。技術の選択肢にしない>
選択肢: 各選択肢に「選ぶと得られる挙動」と「選ぶと失われる挙動 (否定形)」を1行ずつ
推奨: <推奨する答えと理由1文>
```

この書式が 4 規則 (1 前提の裏取り / 2 二択の証明義務 / 3 前提の開示 / 4 喪失の開示) のうち 3 つを構造として担保する — **規則 1 前提の裏取り** (前提行に書けない前提は自分で検証してから出す)、**規則 3 前提の開示** (前提行そのもの)、**規則 4 喪失の開示** (選択肢の否定形1行)。散文で要求すると書き落とされるので、行として固定する。

残る **規則 2 二択の証明義務** だけは書式では担保できないので手順として残す: 「A と B どちらを優先しますか」型の質問は、**両立できないメカニズムを1文で書けたときだけ出す**。書けなければ偽の二択の証拠なので、先に両立案を設計する。

「推奨」行は誘導ではなく grilling の意図的な設計 — 推奨のない質問はユーザーに設計を丸投げすることになり、答えが「おまかせします」に落ちる。推奨に反対されることが情報になる。

### 選択の確定 (失われる体験の復唱確認)

複数案からユーザーが1つを選んだら、採らなかった案で**失われる挙動を否定形の一文**で復唱し、同意を得てから確定事項に記録する。例: 「この選択では、リンクを受け取った人はあなたの作品一覧を見られません。画像だけです。よろしいですか」

- 選択の瞬間にユーザーが見ているのは選んだ案の絵であり、選択肢に喪失が書いてあっても、確定の直前にもう一度否定形で突きつけないと実感されないまま通過する (実例: 「画像がすべて」のラベルで確定した選択が、挙動ゲートで「リンク先で一覧が見える」認識とのズレとして発覚した)
- **省いてよい条件**: シートの回答パネルで選ばれ、その選択肢の `loss` 行 (失われる挙動の否定形) が選択肢の直下に出ていた場合。ユーザーは喪失を読みながら選んでいるので、復唱は同じ文を 2 度読ませることになり往復が 1 つ増えるだけ。`loss` が空だった問い、フォールバックの AskUserQuestion 経由、口頭で受けた反応では省かない
- **「案 A で出して反応を見てから案 B を検討」型の段階導入では必須** (省略条件を満たしていても) — ユーザーの頭に案 B の絵が残ったまま確定しやすい
- 復唱への「いいえ」は選び直しであって手戻りではない。ledger の該当確定事項を未解決に戻してから聞き直す

### 語の確定 (用語集への書き込み)

ラウンドの中で語が決まったら — 新しい語を導入した、既存の語の意味を変えた、同義語のうちどれを使うか決めた — **その場で用語集に書く**。具体的には、**回答を受けたターンの中で、次のラウンドの質問を組み立てる前に Write する** (次のラウンドを組んでから書こうとすると、書き漏れるうえ、次のラウンドで矛盾を突く材料が手元に無い)。書き方の規律 5 つは Gotchas にまとめてある。

用語集がまだ無ければ、**最初の 1 語が確定した時点で作る**。空の用語集を先に作らない — 中身のないファイルは読まれず、読まれない正本には次に書く人も従わない。**この用語集を初めて使うときは、既存 spec の用語節にあるプロジェクト固有の語をこの時点で移す** — 新しく作った場合だけでなく、直下の `CONTEXT.md` を用語集として初めて採用した場合も含む (移行が走るのは「用語集ができた瞬間」ではなく「この spec が用語集を初めて読んだ瞬間」。用語集を読み始めた後は既存 spec の用語節を読まなくなるので、移し忘れた語は誰の視界にも入らなくなる)。既に用語集に同じ語があれば移さない。spec 間で定義が食い違う語も移さず、次のラウンドの質問にする。形式:

```markdown
# <プロジェクト名 (またはコンテキスト名)>

1〜2 文で、この用語集が扱う範囲。

## 用語

- **<語>**: 何であるかを 1〜2 文で。 _使わない語_: <同義語 1>, <同義語 2>
- **<語>**: …

### <自然なまとまりがあれば小見出し>
- …
```

### 質問監査 (任意)

`$ARGUMENTS` に `audit: on` が含まれるか、ユーザーが「質問監査」と言ったときだけ、**ラウンド単位で1回** `question-evaluator` (Skill ツール、fork 実行) に監査させる。

- ラウンドの全質問を `docs/crystallize/specs/<slug>/question-round-<n>.md` に上記フォーマットのまま書く (先頭にタスク一行要約)。**シートの `QUESTIONS` 宣言から機械的に起こす** (`question` → 質問行、`premise` → 前提行、`options` の `gain` / `loss` → 選択肢行、`recommended` + `reason` → 推奨行) — 同じ問いを 2 箇所に手で書くと、監査に出した文とユーザーが見た文がずれる。先頭にはタスク一行要約に加えて試問と同じ読者宣言 1 行を置く (監査の `legibility` と試問の内輪語の判定が同じ許可語で揃う)。起動時は context JSON を `docs/crystallize/specs/<slug>/eval-context.json` に書いて渡す (`project_dir` / `plan` = 質問ファイルのパス / `output_contract.eval_file` = `docs/crystallize/specs/<slug>/eval-question-round-<n>.json`)。質問ファイルのパスだけを渡すとフォールバック経路に入り、eval JSON がプロジェクト直下の `output/` に落ちて、後段 `plan-commit` の `git add -A` で履歴に紛れ込む。実装案や ledger は含めない — 案を見せると監査側が同じバイアスに迎合する
- `passed: false` が返ったら、`feedback_structured` で名指しされた質問だけを前提の裏取りからやり直し、そのラウンドを再監査する。名指しされていない質問は書き直さない
- **再監査は 1 回まで**。2 回連続で `passed: false` になった質問は 3 稿目を書かない — 残った指摘が軽微 (言い回し) ならそのまま出し、重大 (前提の誤り・偽の二択) なら問いを落として自分で調べ直すか、前提そのものが違っていないかをユーザーに 1 行で聞く (`plan-create` の 2 連続不合格停止と同じ扱い。同じ文を磨き続けても前提側の誤りは直らない)
- **監査した / しないに関わらず、ledger の監査記録に件数を残す** (質問数 / 監査数 / 不合格数 / 不合格理由)。任意化した監査を将来戻すか消すかは、この数字が数セッション分たまってから決める。記録がないと「効いていない」も「効いている」も言えない

### 終了条件

frontier が空 (設計・挙動を変えうる未解決論点がゼロ) で、かつユーザーが「認識が揃った」と明示したとき。片方だけでは終わらない — tree が空でもユーザーが引っかかっていれば論点が漏れており、ユーザーが「もういい」と言っても tree に残っていれば実装中に出てくる。

**Step 2 と Step 3 は往復する** — モックへの反応で出た新しい論点は design tree に足し、前提が解決済みになった時点で次のラウンドで聞く。終了条件の判定は、モックの反応で出た論点も含めて frontier が空になったときに行う。一方通行にすると、モックで初めて見える論点が spec に入らないまま書き出しに進む。

## Step 3: モック (見て反応できる成果物)

「見ればわかる」タイプの基準を、実装前に成果物への反応で言語化させる。**モックの規約の正本は `references/mock-kit.md`** — 端末フレーム・切替バー・状態スロット・調整パネル・並置の作法はすべて同ファイルで定義する。ここには案数の判定規則だけ置く。

| 論点の種類 | 案数 |
|---|---|
| 値・程度の論点 (間隔・件数・色・速度・閾値) | **1案 + 調整パネル** |
| 構造の論点 (レイアウト・情報階層・主要操作) が1つ | **2案** (対立する2構造) |
| 構造の論点が複数、または方向性そのものが未定 | **3案** (上限) |

**3案を既定にしない**。親は委任前に「N 案。分けたい論点: …」を1行書く — 書けない案は作らない。案は構造的に違うこと。色や文言だけの違いは案ではない。

- **1タスク1ファイル** `docs/crystallize/specs/<slug>/mock.html` (Step 2 のラウンドシートと同じファイル)。案はファイル内に置き、mock-kit の切替バーで切り替える。案ごとに別ファイルを作らない (ブラウザのタブが増え、案の行き来が「開き直し」になる)
- **既存画面の改修では、現行画面の忠実な再現を先頭の案として置く** (`data-variant="A" data-variant-name="現状"`)。現物の取得は**ユーザーに依頼する** — 第 1 ラウンドの案内で対象画面のスクショ 1 枚を頼み、受け取ったら data URI にして案 A に埋める (エージェントは画面を持たないので自分では撮れない。ブラウザ対象で既存の HTML があるなら DOM 再現でもよい)。変更は次の案以降に差分として描き、変わる箇所を赤系で示す (現状 = 無彩色)。現状の再現が信頼の根で、乖離したモックへの反応は現状への反応として使えない。スクショが得られないときは現状の案を置かず、その旨をシートに 1 行書く (想像で描いた「現状」は無いより悪い)。ゼロからの新規画面ではこの案は要らない
- **終了条件を満たしたら決定をシートに焼き込む** (親が行う) — (1) 採用した案 = **確定案**の `data-variant-name` の前に「(確定)」を付け、`<section>` の並びで先頭に移す (hash 無しで開いたとき最初に出る案 = 確定案。既存改修で先頭に置いた「現状」の案は残すが、焼き込み後は先頭ではなくなる)。(2) `TWEAKS` の各 `value` を最後の貼り戻しの `調整パネル:` の値に書き換える (探索の初期値のままだと、後から開いた人が決めた値を見られない)。(3) 不採用の案は `data-rejected` を付け、`data-variant-name` の前に「(不採用)」を付けて残す。(4) `QUESTIONS` を `[]` にする (閉じたラウンドの問いが残っていると、後から開いた人が有効な【回答】を作れてしまう。パネルは空でも出るので、見ていた案と調整パネルの値の持ち出しは残る)。これで `mock.html` 単体が決定の記録になり、Step 4 の「見た目の正本」がそれを指す。挙動ゲート (`plan-implement`) と実装 (`code-generator`) はこのシートを基準に使うので、探索状態のまま残すと実装者が見るべき案と値を選べない
- 見た目のないタスクは反応できる代替物を出す — API レスポンス例・データモデル案・CLI 出力例・変換前後のサンプルデータ (フレームの中に静的に置く)
- モック作成はサブエージェントに委任し、`references/mock-kit.md` と `assets/mock-kit.html` の**絶対パス** (スキル本文の先頭に注入される「Base directory for this skill」を起点に組み立てる。`${CLAUDE_PLUGIN_ROOT}` はスキルの Bash では空なので使わない。サブエージェントは親の cwd もこの base directory も知らない) と、**親が決めた TWEAKS キー一覧 (キー名・型・range・単位・初期値) と状態キー**を渡す。キー一覧を各サブエージェントに任せると、パネルは個々に綺麗でも案どうしが比較不能になる
- 反応は Step 2 の貼り戻し (案の採否の問い + 見ていた案 + 調整パネルの最終値 + 全体へのコメント) で受け取る。反応 (採用・不採用・「ここは違う」) は理由ごと ledger の確定事項に記録し、**モックの反応で決めた要件には「(モック確定・実機で再確認)」の印**を付ける。モックは触感が本物と違うので、ここで決めたことは実機で覆りうる。覆ったときに改訂として淡々と処理できるよう、由来を残しておく

## Step 4: spec の書き出し

`docs/crystallize/specs/<slug>.md` を次の形式で書く。ファイルパス・コード断片は書かない (腐るため)。例外は 2 つ — モックやプロトタイプが決定をコードより正確に表す場合 (状態遷移・スキーマ・型) の断片と、「見た目の正本」節の `mock.html` のパスと `TWEAKS` の最終値 (パスは `specs/<slug>/mock.html` で slug 固定・spec と同じ寿命なので腐らない。flat な key-value は決定の記録であってコードではない。散文に圧縮すると質感の決定が失われ、実装者がモックを見ないまま UI を書く原因になる)。

```markdown
# <ゴール 1 文>

## 課題
ユーザー視点の 1 段落。

## 解決
ユーザー視点の 1 段落。

## 要件
- <挙動の箇条書き>。挙動に関わる項目には否定形の帰結を併記 (「= その結果 X は起きない / 見えない」)
- モックの反応で決めた項目には末尾に「(モック確定・実機で再確認)」の印

## 非機能要件
- 性能・オフライン・アクセシビリティ・データ量の境界など。該当なしなら「該当なし」と書く

## 見た目の正本
- 確定案: docs/crystallize/specs/<slug>/mock.html#variant=<id> (確認した状態: many, empty / 端末: phone)  ← UI を含まない spec は「該当なし」の 1 行だけ
- 調整パネルの最終値: {"cardGap": 12, "accentColor": "#3f6ad8", ...}  ← 最後の貼り戻しの `調整パネル:` 行をそのまま

「確認した状態」は、確定案の `data-state` キーのうち、ラウンド中の貼り戻しの `見ていた案:` 行に実際に現れたもの (貼り戻しごとに 1 つずつ運ばれるので、各ラウンドの行から集める)。

## 受け入れ基準 (テストケース表)
| ID | seam | ケース | 期待結果 |
|---|---|---|---|
| AC-1 | <public な境界> | <代表 1 点 / 境界の両側 / 異常系を 1 行ずつ> | <観測可能な結果> |

ID は追番で、**一度振ったら再利用しない** — 改訂で行を消しても番号を詰めない (plan・テスト・改訂履歴が同じ行を指し続けられなくなる)。

テストしないと決めたもの:
- <対象> — <理由>

実機確認に委ねる基準 (UI・見た目など TDD 対象外で挙動ゲートに委ねるもの):
- <観測可能な基準>

## スコープ外
- …

## 用語
この spec で新しく決めた語・意味を変えた語だけ。無ければ「なし」と書く。
- **<語>**: 1〜2 文の定義。意味を変えた語には「<前の定義> から変更」を添える

## 改訂履歴
| 日付 | 項目 | 変更 | 理由 | 発見した場面 (認識合わせ / 実装 / 挙動ゲート / リリース後) |
```

**「受け入れ基準 (テストケース表)」がそのまま後段 `test-generator` の入力になる。** seam / ケース / テストしない範囲の 3 要素は、従来 `plan-implement` が実装開始時にユーザーと合意していた 3 要素そのもので、それをここで確定させるので **plan-implement は seam の合意を取らず、表から test-generator へ直接渡す**。表が薄いと実装セッションで詰め直しが発生するので、この節は spec の中で最も手を抜けない。

- seam は既存の境界を優先し、できるだけ上位の1つに寄せる (seam を増やすほど、実装の内部構造をテストが固定してしまう)
- ケースには境界を含める — 数量の 0/1/多/上限、時刻の跨ぎ、中断・再実行、空・重複・順序 のうち、このタスクに該当するもの。境界の取りこぼしは実装後の手戻りとして露見した実績がある
- テストしない範囲は「書き忘れ」と区別できるよう理由つきで明記する

**「見た目の正本」節は、モックで決めた質感 (色・余白・角丸・タイポグラフィ・影・動き・階層・密度) を実装者に届ける唯一の経路**。要件行は挙動を言葉で書くもので、質感は言葉に圧縮すると失われる。ここに書くのはパスと値だけで、見た目の説明は書かない — 説明は `mock.html` の確定案そのものが担う。`plan-create` は UI を含む計画項目にこの参照を添え、`plan-implement` は UI スライスの `code-generator` に渡す。

**「用語」節は正本ではなく変更の記録**。語の定義の正本は用語集で、spec 側には**この spec で決めた語・変えた語だけ**を残す — 同じ語の定義を 2 箇所に置くと、片方だけが改訂されて食い違い、どちらが正かを読む側が決められなくなる。ここに書く語は Step 2 で用語集に書いたものを写すだけで、用語集に無い語を spec 側だけに足さない (足した語は次の spec から見えない)。

書いたら要点だけをチャットに示し (30 行を超えるなら `html-report` で HTML 化する。spec 本体は md のまま)、確認を得て終了する。**spec に plan-evaluator 相当の監査は設けない** — spec の妥当性を決めるのはユーザーの反応であって、独立コンテキストの採点ではない。

## Step 5: 案内

次は**同じセッションで** `/plan-create` に進む旨を案内する。**作成した spec のパスをすべて並べて `/plan-create` に渡す** (複数タスクを扱った場合も spec 1 枚ずつに分けない — 並列可否の仕分けは `plan-create` 側の手順 6 がまとめて行う)。spec と plan は続けて作ってよい (plan は spec を読むだけで、ユーザーとの新しい合意を必要としない)。実装は plan ができてから新しいセッションで始める。

**`plan-create` スキルから改訂モードで呼ばれた場合はこの案内を出さず、改訂した spec のパスと変更点1行を返して呼び出し元の手順 4 (plan の書き出し) へ戻す** — ただし改訂で受け入れ基準の行が増減した場合は手順 3 (分割の判定) からやり直す。`/plan-create` の再起動は二重実行になるので行わない。

## Gotchas

- **モックに本物の配線をしない** — バックエンドや実データに繋いだ瞬間「実装禁止」が崩れ、捨てるコストが生まれて反応が歪む。単一 HTML + ダミーデータで十分。調整パネルのインライン JS はダミーデータを動かすだけなので配線に当たらない (禁止対象はバックエンド・実データへの接続)
- **3案を惰性で作らない** — 「どの論点を分けるための案か」を書けない案は、選択肢を増やしているのではなく判断を薄めている。値の論点なら1案 + 調整パネルの方が速く決まる
- **事実をユーザーに聞かない** — 「このライブラリはこれをできますか」はユーザーへの質問ではなく自分の調査不足。聞かれたユーザーは推測で答え、推測が確定事項として記録される
- **blindspot を一般論で埋めない** — 「テストを書きましょう」「エラー処理に注意」は論点ではなくノイズ。このコードベースで実際に見つかった慣習・過去の判断だけを論点にする
- **網羅性で安心しない** — 長く網羅的な spec は読まれず、読まれない spec は認識合わせに寄与しない。要件は挙動の単位で書き、説明で膨らませない
- **シートを開くのはラウンドにつき 1 回、試問のあと** — 試問で直したら開く前に直す。開いたあとに直しても開き直さない (同じファイルのタブが増えるだけ。ユーザーは再読み込みで見られる)。直した事実は案内に 1 行添える
- **ラウンドをまたぐとき `ROUND.round` を進める** — 進めないと前のラウンドの下書きが復元され、答えたつもりの回答が混ざる
- **`QUESTIONS` の選択肢に「その他」を置かない** — 別の案は「全体へのコメント」に書いてもらう。その他が選ばれた回答は agent が解釈するしかなく、固定形で受ける意味が消える
- **用語集に書くときの規律 5 つ** (Step 2 の書き込みはこれに従う):
  1. **用語の節だけにする** — 仕様・実装の詳細・ファイルパス・作業メモを書かない。それぞれ spec と plan が置き場で、混ぜると寿命の違う記述が同じファイルに溜まり、3 つ目の正本ができる。**直下の `CONTEXT.md` を用語集として使っている場合は `## 用語` (または `## Language`) 節の中だけに書き、他の節には触らない** — あのファイルは別の運用のものを間借りしている
  2. **定義は 2 文以内で「何であるか」を書き、「何をするか」を書かない** — 振る舞いを書き始めると仕様が紛れ込み、実装が変わるたびに用語集が腐る
  3. **同義語は 1 つに決め、残りを「使わない語」に並べる** — どれでもよいことにすると、コード・spec・会話の 3 箇所で別の語が使われ続け、同じものを指しているかどうかを毎回確かめることになる
  4. **このプロジェクト固有の語だけを載せる** — タイムアウト・リトライのような一般的な技術用語を載せ始めると、用語集が辞書になって読まれなくなる
  5. **決まった瞬間にその場で書く** — ラウンドの終わりや spec の書き出し時にまとめて書くと書き漏れ、かつ次の質問で矛盾を突く材料が手元に無い
