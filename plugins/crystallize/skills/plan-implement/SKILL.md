# plan-implement

`find-unknowns` が作った plan (`docs/crystallize/plans/<slug>.md`) を受け取り、実装 → 検証 → コミットまでを一続きの契約で駆動する統括役。3つの門（機械・挙動・例外）を順に通し、**挙動の門が収束するまで diff-review を作らない** — 修正ループの途中で diff を出すと、直すたびに陳腐化して結局読まれずコミットに流れる（過去のセッションで繰り返し観測された失敗パターン）。コードは書かず、実装はすべてサブエージェントに委任する。

## Input / Output

- **Input**: `$ARGUMENTS` = `docs/crystallize/plans/<slug>.md` のパス。省略時は `docs/crystallize/plans/` 直下の `.md` が1つならそれを使い一行で確認を取る。複数あれば AskUserQuestion で選んでもらう。該当する `.md` が無ければ実装を始めず、`find-unknowns` で先に plan を作るよう案内して終了する
- **Output**: `plan-commit` が作る1コミット。進行中は `docs/crystallize/plans/<slug>.md` 本体に `## 進行状況`（フェーズ別チェックリスト）と `## Deviations`（逸脱ログ）を書き足しながら進め、確定と同時にコミットメッセージへ畳み込まれて消える（補助ファイルは作らない）

## 最重要禁則

1. **diff-review はフェーズ4（挙動の門）が収束するまで呼ばない** — 陳腐化した diff を見せると読まれずコミットに流れる
2. **サブエージェントの完了報告だけでフェーズ3（機械の門）を済ませない** — 自己申告は証拠ではない。フェーズ2の完了報告が全項目揃っていても、テスト/lint コマンドは plan-implement 自身が実行し直す
3. **確定事項と矛盾する逸脱、plan にない大規模変更に気づいたら続行せず止める** — Deviations に書いて進めてよいのは可逆・局所的な選択だけ。大小の判断に迷ったら止める側に倒す

各フェーズは完了条件を満たすまで次へ進まない。完了条件を満たしたら、次に何をするかを一行でユーザーに予告してから進む。

## フェーズ1: plan 受領と Deviations 契約

- plan を Read し、確定事項・実装計画・受け入れ基準・Deviations 規約を把握する
- `## 進行状況` 見出しが無ければ作る。実装計画の各項目 + 4つの門（機械/挙動/例外/確定）をチェックボックスで列挙する。既にあれば最初の未チェック項目から再開する — セッションが切れても plan を読めば再開点がわかる
- `## Deviations` 見出しが無ければ作る（本文は空でよい）。**古い plan の Deviations 規約が「implementation-notes.md を作る」と書いていても従わない** — 本スキルは別ファイルを作らず、この見出しに直接追記する契約が正（現行の find-unknowns も同じ規約で plan を書く）
- 逸脱の扱い: 計画から逸れる必要が出たら保守的な選択を採り、`## Deviations` に一行（計画項目 / 実際の選択 / 理由）を追記して続行する。確定事項と直接矛盾する逸脱は、矛盾点と plan 該当箇所を並べてユーザーに提示し判断を仰ぐ（作業は止めたまま）
- **完了条件**: plan 読了、`## 進行状況` / `## Deviations` が存在し、次に着手する項目が1つに定まっている

## フェーズ2: 実装

- 実装計画の項目を先頭（変わりやすい順）から進める。末尾の機械的作業（リファクタ・配線・テスト整備）はまとめて1回の委任にしてよい。**意図が同じ小さなスライスが連続する場合も1回の委任に束ねてよい**（fork は1回ごとに起動と文脈読み込みの固定費を払うため。束ねてよいのは意図が同じもの同士だけ — 別の意図を混ぜると逸脱の追跡が濁る）
- 各項目の TDD 適否を判定する（適用範囲: 入出力で正解を固定できる挙動変更は TDD。UI・見た目・使い捨てプロトタイプ・設定更新は対象外とし、フェーズ4の実機確認に委ねる）
- 委任は即興の Agent プロンプトではなく **generator スキルの Skill 呼び出し**で行う（委任のたびに契約文を書き直すと渡す情報も禁則もぶれる。契約はスキル側に固定してある）:
  - **TDD 対象スライス**: まず seam・境界ケース・テストしない範囲を plan から起こして**ユーザーに確認**する（tdd の「書く前に合意」規則の担い手は本スキル。fork は対話できない）。合意後 `test-generator` を起動して RED（失敗するテスト + 実行証拠）を得て、続けて `code-generator` を起動して GREEN にする
  - **非 TDD スライス**: `code-generator` を単独で起動する
  - 渡すのは該当項目の計画文 + 関連する確定事項 + 受け入れ基準 + テストの実行コマンドだけ。TDD の場合はさらに、`test-generator` には合意済みの seam・境界ケース・テストしない範囲を、`code-generator` には RED 状態のテスト一覧を加える。ledger 全体や決着済みの論点は渡さない
- 逸脱は generator の報告から plan-implement 自身が `## Deviations` へ転記する。escalate の報告を受けたら続行せず、最重要禁則3のとおり止めてユーザーに戻す
- **完了条件**: 進行状況の実装計画項目すべてに完了報告または解決済み escalate が付いている（この時点の報告は自己申告のままでよい — 検証は次のフェーズが行う）

## フェーズ3: 機械の門 — 正しいか

- プロジェクトのテスト・lint コマンドを plan-implement 自身が実行する。サブエージェントの「全緑でした」報告だけでは進めない
- **テストは選別して回す**: 修正ループ中の再実行は、変更の影響範囲のテスト（変更したファイル・モジュールに対応するもの）だけでよい。**全量スイートは門の完了条件としてだけ1回**回す — 検算の原則は保ったまま、全量実行を最後の1回に集約する（変更していない部分のテストを毎周道連れにしない）
- 失敗したら `code-generator` に差し戻して修正させ、再実行する。12回試みても収束しなければ実装を止めてユーザーに報告する
- テスト・lint が緑になったら `code-review` スキルで AI コードレビューを行い、指摘を解消してから次へ進む。挙動の門より先に置く理由: 指摘の修正でコードが変わりうるため、ユーザーの動作確認を後にしないと確認がやり直しになる
  - 指摘の修正は `code-generator` に差し戻す（指摘の一覧を渡す。テストは不変のまま）。修正後はテスト・lint を再実行し、必要なら code-review も再実行する。この修正ループも12周で収束しなければ止めてユーザーに報告する
  - 指摘が「テスト自体の欠陥」を指す場合は、実装で辻褄を合わせさせず、ユーザーに確認のうえ `test-generator` に差し戻す（期待値の保護 — 基準側の変更は人間の確認を経る）
  - effort は **low を基本**とし、次のいずれかに該当する変更は **high** に上げる: アーキテクチャ・データモデル・公開インターフェースに触れる / plan の複数項目にまたがる大きな変更 / 共通基盤など影響が長く残る箇所
  - 解消せず受け入れる指摘は理由を `## Deviations` に記録する（diff-review の昇格④⑤として人間の目に入る）
- code-review の指摘を畳んだら `simplify` スキルで品質整理（再利用・単純化・効率・抽象度）を適用する。code-review の後に置く理由: 正しさの修正を先に済ませないと、整理した形の上にまた修正が乗って二度手間になる（バグ探しは code-review、品質整理は simplify という役割分担どおり）
- code-review / simplify で1行でもコードが変わったら、テスト・lint をもう一度実行して緑を確認する（ここも影響範囲の選別でよい）
- **完了条件**: code-review の指摘が解消済みまたは Deviations に記録済み、simplify の適用が済み、**最後のコード変更より後に全量の**テスト・lint が exit 0 で終わっている（フェーズ2のサブエージェント報告の使い回しは不可）

## フェーズ4: 挙動の門 — 意図どおりか（diff より先）

- 受け入れ基準・確定事項に見た目や UI 操作の項目が無ければ、「UI確認対象なし」と進行状況に記録してフェーズ5へ進む
- あれば `run` スキルでアプリ/モックを起動し（ブラウザ対象で Orca が使える環境なら `orca-cli` でもよい。無ければユーザーにブラウザで開いてもらう）、受け入れ基準の操作パスをチェックリストとして**ユーザーに提示し、ユーザー自身に触ってもらう**。`docs/crystallize/plans/<slug>/mock-*.html`（find-unknowns Step2 の反応用モック。plan-commit まで削除されず残っている）があれば見比べの基準として使ってよい
- 「ここ違うな」が出たら修正の性質でレーンを分ける。**どちらのレーンでも、このループが収束するまで diff-review は呼ばない**
  - **微修正レーン** (テストで固定した挙動の契約を変えない修正 — 見た目・文言・定数調整など): TDD の重機を回さない (`test-generator` を呼ばない — UI・見た目は TDD 対象外の原則の再適用)。指摘はユーザーが一通り触り終えるまで**束ね、まとめて1回** `code-generator` に委任する。色・余白・文言レベルの1〜2行の即時調整でユーザーが画面の前で待っている場合に限り、plan-implement が直接編集してよい (委任の固定費が作業を上回るため — 委任原則の明文化された例外)。再検証は lint + 影響範囲のテストのみで、code-review は再実行しない (差分の全量は最後に例外の門を通る)。hot reload など実行中のアプリを保ったまま反映できる手段があれば使い、その場で再確認する
  - **正規レーン** (挙動の契約が変わる修正 — ロジック・データ・受け入れ基準に触れるもの): 従来どおりフェーズ2に差し戻し、修正後は影響範囲のフェーズ3だけ再実行してからこのチェックリストに戻る
- **完了条件**: 受け入れ基準の操作パスすべてについて、ユーザー自身の言葉で「意図通り」の確認が取れている（UI確認対象なしの記録で代えた場合も可）

## フェーズ5: 例外の門 — 危なくないか

- フェーズ4収束後に初めて `diff-review` を Skill ツールで直接起動する（案内文にしない）: skill = `diff-review`, args = `plan: <plan のパス>`
- ユーザーが既に別のレビュー手段（例: codex のレビューループ）を使うと明言している場合は起動を省いてよいが、レビューそのものの省略は認めない
- 生成された画面をユーザーに確認してもらい、明示的な go / no-go を得る。no-go ならフェーズ2かフェーズ4へ差し戻す
- **完了条件**: ユーザーの明示的な go が得られている（この go はフェーズ6のコミット同意を兼ねる）

## フェーズ6: 確定

- フェーズ5の go を受けて `plan-commit` を Skill ツールで直接起動する（案内文にしない）: skill = `plan-commit`, args = `<plan のパス>`
- `plan-commit` が返す `git log -1 --stat` の要点をそのまま報告する。スライスごとの経過は語り直さない
- **完了条件**: `plan-commit` が完了し、plan ファイルと `docs/crystallize/plans/<slug>/` が削除されている

## Gotchas

- **下流スキルへの接続を「〜してください」の案内文に退化させない** — 過去の運用で、案内文止まりの下流スキル接続は高い頻度で実際には実行されず、即興レビューや手動 git 操作に置き換わることが繰り返し観測された。フェーズ5・6は必ず Skill ツールで直接起動する
