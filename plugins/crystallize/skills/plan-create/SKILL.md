# plan-create

`spec` が確定させた要件 (`docs/crystallize/specs/<slug>.md`) を受け取り、**実装手順** を plan (`docs/crystallize/plans/<slug>.md`) に書き出すスキル。通常は 1 ファイル。spec の規模が大きく、変更対象のモジュールが重複せず、単体で動作確認ができるまとまりに分かれる場合のみ複数ファイルに分割する (手順 3)。1 つの plan は 1 回の一まとまりのコミットに対応するため (plan-commit がリファクタリングと機能変更を分けることはある)、分割はコミットの単位を決定する判断でもある。
plan は一時的な文書であり、後続の `/plan-commit` がそのままコミットメッセージ本文として使用した後に削除する。要件は spec 側に残るため、plan には実装手順と、安全に実装するための情報 (維持すべき既存の動作・検証コマンド) のみを記述する。

新しい要件の策定は本スキルの役割ではない。要件の再検討が必要になった場合は `spec` に戻す (手順 2)。

## Input / Output

- **Input**: `$ARGUMENTS` = `docs/crystallize/specs/<slug>.md` のパス。`spec` スキルが複数タスクを扱った場合は**複数の spec パスを渡してもよい** (spec ごとに plan を作成し、並列実行の可否判定は手順 6 で行う)。省略時は `docs/crystallize/specs/` 直下で最も新しい `.md` を対象として確認する。spec が 1 つも存在しない場合は plan を作成せず、`/spec` で先に要件を定義するよう案内して終了する。spec のない plan は要件を実装計画の中で暗黙的に決定することになり、その決定経緯が記録に残らなくなるためである。
- **Output**: `{projroot}/docs/crystallize/plans/<slug>.md` (plan 本体)。作業ファイルは `{projroot}/docs/crystallize/plans/<slug>/` 配下 (`impact.md`)。slug は spec と揃える。分割したときは `plans/<slug>-<n>-<部分名>.md` と同名ディレクトリを plan ごとに作成する (手順 3)。

## 最重要禁則

1. **プロダクトコードを書かない・編集しない**。Write してよいのは `docs/crystallize/plans/<slug>.md` と `docs/crystallize/plans/<slug>/` 配下のみ。
   理由: impact で既存コードを調査した直後は、関連する修正を同時に行いたくなりやすいが、コードを編集し始めると計画がその変更を正当化する方向に偏る恐れがある。実装は plan と spec を受け取った別のセッションで行う。spec の修正が必要になった場合は、直接編集せずに `spec` スキルを改訂モードで起動する (手順 2)。
2. **要件を plan で再決定しない**。未決定の要件を発見した場合は、実装計画の項目として扱わずに `spec` へ戻す。ユーザーが確認していない要件が計画に含まれると、決定経緯を追跡できなくなるためである。

## 手順

### 1. spec を読む

spec を Read し、ゴール、要件、受け入れ基準 (テストケース表)、スコープ外、用語を把握する。あわせて**用語集** (リポジトリ直下に `## 用語` または `## Language` を持つ `CONTEXT.md` があればそれを参照し、無ければ `docs/crystallize/CONTEXT.md` を参照する。どちらも無ければ spec の用語節) を Read し、plan 本文の用語はそれに従う。plan 内で用語を言い換えると、実装やテストで spec と異なる名称が使われる原因となる。ledger や mock.html は読まない。解決済みの検討経緯は実装手順に不要であり、参照すると plan の記述が経緯の説明で冗長になるためである。UI の決定事項も mock.html を直接開かずに確認できる。必要な情報は spec の「見た目の正本」節にある確定案の `mock.html#variant=<id>` と確認した状態のみであり、これらは手順 4 で UI を含む項目に付記する参照先となる (経緯ではなく決定事項そのものを参照する)。

### 2. impact — 守るべき既存挙動の裏取り

開発中のプロジェクトにおける既存機能との整合性を Explore subagent で調査・確認し、`docs/crystallize/plans/<slug>/impact.md` に記述する。

- 変更される既存の動作 (ユーザーから見えるものを優先)
- 移行が必要なデータや設定
- 変更してはいけない箇所 (他から依存されている動作や公開インターフェース)
- 変更対象となるファイル・モジュールの集合 (受け入れ基準ごとに、どの AC がどのファイルを変更するか) — 手順 3 の分割判定と手順 6 の重複判定は、この集合のみを根拠とする

**impact の調査から要件に関わる新たな課題が判明した場合は、plan を書き進めずに `spec` スキルを改訂モードで起動する** (Skill ツール、args = spec のパス)。例: 既存の動作と要件が両立しない、データの移行可否についてユーザーの判断が得られていない。ここで独自に判断すると、ユーザーの合意がない要件が実装計画の一項目として混入することになる。

### 3. 分割の判定

1 つの spec から作成する plan の数を決定する。**既定は 1 ファイル**。次の 3 条件を**すべて**満たす AC のまとまりが 2 つ以上ある場合のみ分割する:

1. **変更対象のモジュールが重複しない** — impact で確認したファイルおよびモジュールの集合が、まとまり同士で重複しない (重複がある状態で分割しても、先行する plan の完了を待つことになり、並列作業も独立した検証も行えない)
2. **その範囲だけで受け入れ確認を完結できる** — そのまとまりが対象とする AC を、その plan の完了時点で確認できる。UI を含むまとまりは挙動ゲート (実際の画面や端末) で、含まないまとまり (データモデルや API など) は自動テストのみで確認が完結すること。**対象 AC の確認に後続の plan の完了が必要となるまとまりは分割しない** — 自動テストが成功しても意図どおりに動作しているかが完了時まで検証できず、1 つの plan が 1 つのコミットに対応するという前提 (コミットの時点で検証が完了していること) が成立しなくなる
3. **分割する妥当性がある規模 (spec 全体で判定する目安)** — 実装計画の見積もりが 8 項目を超える見込みがある、または impact に挙げられたモジュール (プロジェクトの構成単位) が 3 を超える。この数値は固定の基準ではなく目安であり、「1 つのコミットとして人間がレビューしやすい規模」と「plan 1 ファイルごとの監査やコミットにかかる作業コスト」の均衡を根拠とする。規模の小さい spec を分割すると、作業コストのみが増加する

分け方:

- まとまりは「相互に依存して単体では動作しない AC」の単位で構成する。1 つの AC を複数の plan に分割しない
- 順序は複数の plan に対しても「変更可能性の高い順」を適用する — データモデルや外部から見える挙動を含む plan を先にする。ただし `depends-on:` を記述するのは、**後続の plan が先行 plan の成果物 (新しい型・API・データモデルなど) を呼び出す場合のみ**とする。変更対象ファイルは重複しないが依存関係が存在するケースがこれに該当する。互いに独立した機能に分割した場合は依存関係を設定せず (`depends-on:` を記述せず)、手順 6 で並列に配置できるようにする
- 目安として 1 つの spec につき最大 4 ファイルまでとする (同時に管理できる worktree とレビューの数の目安)。5 ファイル以上に分割が必要と思われる場合は、spec が複数の機能を抱えすぎていることを示しているため、spec 自体を分割する目的で `spec` の改訂モードに戻す
- **2 ファイル以上に分割すると判断した場合のみ**、分割案を 1 行でユーザーに提示して合意を得る (「N 枚: <各 plan の名前と covers>。理由: <満たした条件>」)。分割は実装の順序とコミットの単位を決定する判断であり、後から変更されると plan の再作成が必要になるためである。1 ファイルの場合 (既定) は合意を取らず手順 4 へ進む

命名: 分割した plan は `docs/crystallize/plans/<slug>-<n>-<部分名>.md` (`<n>` は 1 から始まる実装順、`<部分名>` は spec の slug と同様に英小文字とハイフンを使用。例: `share-card-1-share-link.md`, `share-card-2-recipient-page.md`)、作業ファイルは同名のディレクトリ `plans/<slug>-<n>-<部分名>/` とする。**impact.md は plan ごとに、そのまとまりが変更するファイル・モジュールの行のみに絞り込んで各ディレクトリへ再作成し、元の `plans/<slug>/` は削除する** — 内容をそのまま複製すると手順 6 の重複判定で同一内容の比較となり必ず重複と判定される。また、元のディレクトリを残すと plan-commit の削除対象に含まれず削除されずに残ってしまうためである。

### 4. plan の書き出し

`docs/crystallize/plans/<slug>.md` を次の形式で書く (分割した場合は plan ごとに 1 ファイルずつ)。

```markdown
# <ゴール 1 文 (spec の先頭行と同じ。分割した plan は「— <部分名>」を添える)>

spec: docs/crystallize/specs/<slug>.md
covers: AC-1, AC-2, AC-5
depends-on: docs/crystallize/plans/<slug>-1-<部分名>.md

## 守るべき既存挙動
impact の要点 (変わる既存挙動 / 移行が必要なデータ・設定 / 触ってはいけないもの)

## 実装計画 (変わりやすい順)
1. ユーザーが差し替えたくなる可能性が高いもの (データモデル・型・見える挙動) を先頭
2. …
N. 機械的な作業 (リファクタ・配線・テスト整備) は末尾にまとめて 1 項目
各項目に「対応する受け入れ基準の ID (AC-n)」と「TDD 対象 / 対象外」を添える。UI を含む項目にはさらに「見た目の正本: docs/crystallize/specs/<slug>/mock.html#variant=<id> (確認した状態: many)」を添える

## 検証コマンド
テスト・lint のコマンドを 1 行ずつ
E2E 評価の対象面: ブラウザ (URL と起動方法) | モバイル端末 (アプリ名と起動方法) | CLI (コマンド) | なし。前提状態 (テスト用アカウント・初期データなど) があれば同じ行に添える

## Deviations 規約
計画から逸れる必要が出たら保守的な選択を採り、この plan の `## Deviations` に理由ごと追記して続行する。確定した要件と矛盾する逸脱 (エージェント発) は止めてユーザーに戻す。ユーザー発の仕様変更は spec の改訂として扱う (plan-implement 挙動ゲートの仕様改訂レーン)。
```

- `covers:` と `depends-on:` は `spec:` 行と同じ先頭ブロック (最初の `##` 見出しより前) に配置し、1 行につき 1 キーで記述する。`covers:` の値はカンマ区切りの列挙とする (範囲記法は使用しない。解釈するスキルが複数あり、解釈の違いが生じるのを防ぐため)。いずれも**分割した場合のみ**記述する。`covers:` はその plan が実装する受け入れ基準の ID を列挙したものであり、省略時は spec の全 AC を対象とすることを意味する
- `covers:` には AC ID に加えて、その plan が担当する **ID のない基準** (spec の「実機確認に委ねる基準」および「(モック確定・実機で再確認)」と記された要件) を `実機: <基準の冒頭>` の形式で列挙する (例: `covers: AC-3, AC-4, 実機: カード余白の見え方`)。ID のない基準は `covers:` で担当を明示しないと、すべての plan の挙動確認で重複して提示されるか、どの plan でも確認されないまま見落とされる原因となる
- `depends-on:` には先行する plan のファイルパスを指定し、依存関係がない場合は行ごと省略する。**先行する plan が plan-commit によって削除された後でも、後続の plan に注釈を追加しない**。削除された plan の内容はコミットメッセージにすべて記録されており、監査時に `git log` から `covers:` の情報を取得できるためである
- **項目の並び順を最重要視する**: 重要な変更内容が先頭に並び、確認者が冒頭を確認するだけで全体の方針を把握できる構成にする。網羅的で長大な計画は読まれない
- **UI を含む項目 (spec の「実機確認に委ねる基準」または「(モック確定・実機で再確認)」と記された要件に対応するもの) には見た目の正本の参照を付記する** — spec の「見た目の正本」節から確定案のパス (`mock.html#variant=<id>`) と確認した状態を転記する。調整値の JSON などは spec に記載されているため転記しない。参照がない場合、`plan-implement` が実装担当にモックを伝達できず、文章のみから UI を実装してモックと仕上がりが乖離する原因となる。spec の該当節が「該当なし」の場合は記載しない
- `covers:` に指定した各 AC (省略時は spec の全 AC) が、いずれかの実装計画項目に対応している必要がある。対応しない項目が存在する場合は計画に漏れがあるか、spec に実装不可能な基準が含まれている (後者の場合は手順 2 と同様に spec へ差し戻す)。分割した場合は、各 plan の `covers:` の和集合が spec の全 AC と一致し、同一の AC が複数の plan に重複して現れないようにする
- **「E2E 評価の対象面」にはプロジェクトが公開している操作面 (Web サーバーの URL、モバイル端末のアプリ、CLI コマンド) とその起動方法を書く。どの操作ツールがあるかは書かない** — plan-create と plan-implement は別セッションで動き、ブラウザやモバイル端末を操作するツールの有無は実装セッションの環境に依存するため、plan-create の環境で判定しても実装時には当てにならない。対象面はコードベースから静的に確認できる事実であり、ツールの有無は plan-implement が実行時に確認して判定不能として扱う。ライブラリなど操作面を持たないプロジェクトは「なし」と書く。受け入れ基準の操作パスが特定のアカウントや初期データを前提とするなら、その用意の仕方を前提状態として添える (evaluator は自力で用意できない前提を持つ行を採点しないため)
- 要件や受け入れ基準の記述そのものを plan に転記しない。二重管理を防ぎ、spec が改訂された際に plan 側の記述が不整合になるのを避けるためである (plan-implement は spec も直接参照する)

### 5. 監査 (必須)

書き出した plan は、ユーザーに提示する前に `plan-evaluator` (Skill ツール、fork 実行) に監査させる。args = context JSON のパス (次の箇条書き)。誤った前提や計画から漏れた受け入れ基準は、実装後の手戻りの原因となるため、この段階で検出して防ぐ。

- 引数として渡すのは context JSON (plan のパスを含む) のみとし、impact.md は渡さない。plan と spec のみを用いて監査を行うことで、plan 単体で情報が完結しているかを検証できるためである
- 起動時は context JSON を `docs/crystallize/plans/<plan の basename>/eval-context.json` に記述して渡す (`project_dir` / `plan` / `output_contract.eval_file` = `docs/crystallize/plans/<plan の basename>/eval-plan-<稿数>.json`)。パスのみを渡すとデフォルトのフォールバック処理が実行され、eval JSON がプロジェクト直下の `output/` に生成されて `plan-commit` の `git add -A` によってコミット履歴に含まれてしまう。plan と同名のディレクトリに配置すれば、plan-commit の実行時に plan と一緒に削除される
- **分割した場合はすべての plan を作成し終えてから、1 ファイルずつ順に監査にかける** — 和集合の検証は分割されたすべての plan が揃っていないと成立しない。監査の指摘で**どれか 1 つの `covers:` を変更した場合は、他の plan もすべて再監査する** (和集合が変化し、他の plan の合格結果が無効になるため)
- eval ファイル名の `<稿数>` は 1 稿目・2 稿目を示す番号であり、分割 plan の `<n>` とは関係しない。plan ごとに専用のディレクトリに配置するためファイル名は衝突しない
- `passed: false` の場合は指摘箇所の事実確認からやり直して plan を修正し、再監査にかける。`rewrite` (見出し単位の置換案) が返されている場合はそれを参考にする
- **2回連続で不合格の場合は停止する**: 監査が 2 回連続で `passed: false` になった場合は、3 稿目を作成せずに停止する。`score` と不合格の具体的な理由 (`feedback_structured.high`) をユーザーに提示し、**plan の前提条件やゴールそのものに誤りがないか**を直接確認する。3 稿目はその回答を反映した上で作成する (以降も同様)。同じ plan が 2 稿連続で不合格となるのは、表現の推敲不足ではなく、前提条件に誤りがある可能性が高いためである

合格した場合は要点をチャットで提示する (30 行を超える場合は `html-report` で HTML 化する。plan 本体は md のまま保持する)。

### 6. 複数 plan の仕分けと配置

複数の spec から作成した場合、または 1 つの spec を分割して複数の plan を作成した場合は、すべての plan の impact を照合し、変更対象となるファイルやモジュールの重複を判定する。重複がなければ並列実行可能とし、重複がある場合は実行順序を決定するか 1 つの plan に統合する。同じ spec を分割した plan 同士は、重複の判定を手順 3 で済ませてあるため (条件 1)、ここでは再判定を行わず `depends-on:` の有無のみを確認する。照合の対象は、別の spec に由来する plan および進行中の他の worktree にある plan とする (重複判定の基準は同様)。`depends-on:` で関連付けられた複数の plan は定義上実行順序が存在するため、並列には配置しない (先行する plan を先に実装し、後続の plan は同一の worktree で続けて渡す)。仕分け後の調査で想定外の重複が判明した場合は、並列実行を取りやめて順次実行の提案に切り替える (誤って並列実行するとマージ時のコンフリクトにつながるためである)。

並列実行が可能と判定した場合は、**並列配置** (どの worktree にどの plan を割り当てるか、重複があるものはどの順序で進めるか) を一覧表で提示してユーザーの合意を得る。**合意後の配置処理は案内にとどめず、本スキル自身が実行する** (ユーザーへの案内のみにとどめると後続の作業が実行されないままになる恐れがあるためである):

1. `git worktree add` で worktree を作成する (Git の標準機能を使用し、特定の外部ツールには依存しない)
2. `plans/<plan の basename>.md` と `plans/<plan の basename>/` を担当の worktree へ移動する。**spec は Git による追跡状態に応じて扱いを分ける** — `git ls-files --error-unmatch specs/<slug>.md` が成功する (追跡済み) 場合は、worktree 側にもすでに同じファイルが存在するため、**ファイルを移動せず、未コミットの変更分のみをコピーする** (`mv` を実行すると元の作業ツリーで spec が削除扱いとなるため)。追跡されていない (今回新規作成した) spec は `specs/<slug>.md` および `specs/<slug>/` ごと移動する。コミットされていないファイルは worktree 側に反映されず、移動を怠ると実装セッションで plan 先頭の `spec:` 行の参照を解決できなくなるためである
3. 各 worktree で対話セッションを起動し、`/plan-implement <plan の絶対パス>` を初期プロンプトとして渡す。**起動方法は本スキル側で固定しない** — 環境にセッション起動用のツール (worktree 管理ツールやターミナルの自動化スクリプトなど) が存在する場合はそれを利用し、存在しない場合は worktree ごとのプロンプト雛形を提示してユーザー自身に各ターミナルで開いてもらう。特定の製品名はこの文書に記述しない。配布用のプラグインであるため、各環境に応じたツール設定は利用側のスキルや CLAUDE.md に委ねる。`depends-on:` で関連付けられた複数の plan は先頭の 1 つのみを渡し、後続の plan は先行の plan-commit が完了した後に同じセッションで次の `/plan-implement` を渡す

以降の対話 (挙動ゲート・例外ゲート) は各 worktree のセッションが直接ユーザーと行う。本セッションは配置の完了報告 (worktree 一覧と各セッションの状態) を行って終了し、全体の管理役としてプロセスを維持しない。

### 7. 案内して終了

**新しいセッションで** `/plan-implement` に plan を渡して実装を開始する旨を案内する。分割した場合は `depends-on:` の順序に従って plan を並べ、1 ファイルずつ plan-commit によるコミットまで完了させてから次に進むよう注記する (後続の plan は先行するコミットを前提として記述されているためである)。実装、テスト、動作確認、差分の例外確認、plan-commit の実行までは plan-implement が一連の流れとして処理する。案内と合わせて、新しいセッションにそのまま貼り付けて実行できる初期プロンプトをコードブロックで提示する (新しいセッションのカレントワーキングディレクトリに依存しないよう、絶対パスで記述する):

```
/plan-implement /path/to/docs/crystallize/plans/<slug>.md
```

---

## Gotchas

- **plan 本文から `plans/<slug>/` へ相対リンクを設定しない** — plan は `/plan-commit` 実行時にコミットメッセージの本文として使用され、`plans/<slug>/` はその時点で削除されるため、リンク切れとなった文書が履歴に残ってしまう。`specs/<slug>.md` へのリンクは問題ない (spec は削除されずに残る)
- **プロンプトに plan の要約を過剰に記述しない** — 実装に必要な情報が文書の外部に分散すると二重管理になる。不足している情報に気づいた場合は、plan または spec の文書自体に追記する
- **不必要な分割を行わない** — 手順 3 の 3 条件を満たさない分割は、並列作業も独立した検証も実現できず、コミットや監査の手数のみが増加する。判断に迷う場合は 1 ファイルにまとめ、実装中に規模が大きすぎると判明した時点で残りの作業を別 plan に切り出す方が効率的である
