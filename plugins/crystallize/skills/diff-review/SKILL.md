# diff-review — 例外ビューア（人間レビューの最後のゲート）

あなたは fork されたレビュー画面係。人間による確認は3つの問いに分かれる。

1. **意図どおりか**（挙動確認） — 上流のワークフロー（`plan-implement` の「挙動ゲート」等）が担当。本スキルはこれが収束した後に呼ばれる前提
2. **正しいか**（テスト + AI レビュー） — 人間の関与なし。Step 2 で結果を集計して見せるだけ
3. **危なくないか**（`plan-implement` でいう「例外ゲート」）— **本スキルの担当**。昇格リストに該当する hunk だけを人間に見せる

過去セッションの分析では、全 hunk を人間に読ませる画面は実際には読み切られず、即興レビューか読み飛ばしに置き換わっていた。本スキルは「全部読む画面」ではなく、**危ない箇所だけを目立たせて残りは畳む例外ビューア**として動く。全 hunk が画面から消えない検算は維持する — 畳むのは省略ではなく整理。

## 呼び出し前提

**動作確認が収束したあとに呼ぶ。** 収束前に呼ぶと次の順序で壊れる: diff 画面を作る → まず UI を触って動作確認する → 「ここ違う」で修正する → diff が古くなる → レビューが飛ばされてコミットされる。この破綻は実績として観測されている。

主経路は `plan-implement` のフェーズ5（例外ゲート）から Skill ツールで `skill: diff-review, args: plan: <plan のパス>` として起動されること（挙動ゲートであるフェーズ4が収束した後にしか呼ばれない契約）。ユーザーが「diffレビュー」「レビュー画面」で直接叩く従来の使い方も変わらず使える。

HTML 生成の共通規約（自己完結・CDN 禁止・チャットに本文を貼らない・保存先と `open`・style.css の土台）は派生元である同プラグインの `html-report` スキル本文を Read してそれに従う。本スキルはその上に diff レビュー固有のルールを足す。

## Input / Output

- **Input**: `$ARGUMENTS` = 比較の基点 (省略時は `git diff HEAD` + 未追跡ファイル)。`plan: docs/crystallize/plans/<slug>.md` があれば意図解説・昇格判定・受け入れ基準表示の根拠にする。指定がなくても `docs/crystallize/plans/` 直下に該当しそうな plan があれば Read する
- **Output**: `<projroot>/docs/crystallize/reports/YYYY-MM-DD-diff-review-<slug>.html` を生成して `open`。最終応答は「昇格件数/全hunk数 + 要注意点の要約 (3 行以内) + ファイルパス」のみ

## 最重要ルール (理由つき)

- **hunk の検算を必ず通す** — 昇格 hunk 数 + 非昇格 hunk 数の合計が差分全体の hunk 数と一致するまで公開しない。分類に迷う hunk は「未分類」グループに置く (隠すより見せる。⑥として自動的に昇格対象になる)
- **各 hunk は 01 (昇格) か 02 (非昇格) のどちらか一方に一度だけ現れる** — 昇格 hunk を元のグループ側にも重複して残すと、検算の足し算が壊れて意味を持たなくなる
- **diff 本文は必ず HTML エスケープする** — コードには `<div>` や `&&` が普通に含まれる。エスケープ漏れは表示崩れではなく「差分が黙って消える」事故になる
- **解説は素材にある事実だけで書く** — plan・コード・diff から読み取れることだけを書き、推測は「推測:」と明示する
- **昇格判定に迷ったら昇格側に倒す** — 見せすぎの害 (読む数分) と見逃しの害 (不可逆操作の見逃し) は釣り合わない

## Step 1: 差分の収集

```bash
PROJROOT=$(git rev-parse --show-toplevel)
git -C "$PROJROOT" diff <基点> --stat   # 規模の把握
git -C "$PROJROOT" status --porcelain   # 未追跡ファイルの検出
```

- 基点省略時は `git diff HEAD` (staged + unstaged) に加え、未追跡ファイルを「新規ファイル全文の追加」として差分に含める
- 総ファイル数・総 hunk 数・総追加/削除行数をここで確定し、検算の分母として控える
- 巨大 diff (数百 hunk) は一括で読まず、ファイル単位で分割して Read する
- plan があれば同じタイミングで Read し、確定事項・受け入れ基準・`## Deviations` 見出し (あれば) を控えておく (Step 3 と Step 4 で使う)

## Step 2: 論理グループ化と解説

hunk を **ファイル単位ではなく意図の単位** でグループ化する (同一ファイルの hunk が別グループに割れてよい)。plan があれば plan の実装計画項目とグループを対応づける。各グループに書くもの:

| 項目 | 内容 |
|---|---|
| グループ名 | 変更の意図を表す短い名詞句 |
| タグ | feat / refactor / fix / docs / config / test |
| リスク | 低リスク (挙動不変・局所) / 注意 (共通基盤・広範囲に波及) / 要注意 (データ・削除・セキュリティに触る) |
| 意図 | なぜこの変更か + 影響範囲を 2〜3 文の平易な完全文で |
| 指摘 | diff を読んで気づいた問題点 (あれば)。深掘りは /code-review の仕事なので、目に付いたものだけ |

この「指摘」欄は Step 3 の昇格判定④の入力になる。plan の実装計画項目に対応しないグループは「未分類」として残す (Step 3 の⑥がこれを昇格させる)。グループ別の hunk 数は **昇格した hunk も含めた総数** で数える (Step 4 のヘッダ表示で「うち昇格 n 件」を添えて使う)。

## Step 3: 昇格判定 — 例外ビューアの核

hunk 1 つずつに対し、以下 6 条件のいずれかに該当するか判定する。該当すれば「昇格」、しなければ「非昇格」。

| # | 昇格理由 | 判定材料 | 目安 |
|---|---|---|---|
| ① | データ削除・移行・不可逆操作 | diff 本文・ファイルパス | `DROP`/`DELETE`/`TRUNCATE`/`rm`/`migrations/` 配下/スキーマ変更 (`ALTER TABLE` 等) |
| ② | 対外境界 | ファイルパス・diff 本文 | 公開 API ルーティング・認証・課金・秘密情報 (`.env`/secrets/key)・外部送信の新規呼び出し・CORS/権限設定 |
| ③ | 依存の追加・更新 | ファイルパス | `package.json`/`pubspec.yaml`/`requirements.txt`/`Gemfile`/`go.mod`/`Cargo.toml` 等のマニフェスト |
| ④ | AI レビューの指摘・不一致 | Step 2 の「指摘」欄 | 指摘が載っている hunk |
| ⑤ | plan の Deviations | plan の `## Deviations` 見出し | 確定事項からの逸脱に対応する hunk。plan が無い/見出しが無ければ判定対象外として扱う (エラーにしない) |
| ⑥ | plan にない予想外の変更 | Step 2 のグループ分類 | どの実装計画項目・意図にも紐づかない hunk (= 「未分類」グループ) |

1 hunk が複数条件に当たることがある — 該当した番号を全部控える (Step 4 でバッジとして全部出す)。判定に迷う hunk は昇格に倒す (最重要ルール参照)。

## Step 4: HTML の構成

diff は base `references/templates.md` の diff コンポーネント (行番号2列・hunk ヘッダ・sticky ファイルヘッダ・右側ファイルナビ) を **構造ごとそのまま使う**。変えるのは `<details class="file">` の `open`/`closed` の既定と、昇格 hunk への理由バッジの追加だけ。バッジ用の CSS は style.css を編集せず、レポート内の追記分 `<style>` に色は CSS 変数 (`var(--primary)` 等) 経由で足す。タブ・HTML 骨格の雛形も base の `references/templates.md` を流用する。

1. **ヘッダ**: タイトル (タスク名 + 差分レビュー)、`N files / M hunks +追加 -削除`、**「人間が見るべき箇所 N 件 / 全 M hunk」の要約行**、グループ別リスク・指摘の集計 (Step 2 の表をそのまま小さく表示。各行に「うち昇格 n 件」を添える。AI レビューが済んでいる根拠として置く)、承認プログレス「確認 0/N」(N = 昇格件数)
2. **受け入れ基準** (plan にあれば): 挙動チェックリストとしてヘッダ付近に並べる。ここでチェックさせるのではなく、挙動ゲートを通過済みという記録として表示するだけ。plan が無い/受け入れ基準の節が無ければこの節ごと省略する
3. **01 昇格 hunk** (先頭、`open`): 該当ファイルごとに `<details class="file" open>` を作り、昇格した hunk だけを入れる。各 hunk の `hunk-head` に昇格理由バッジ (①〜⑥、複数可) を添え、元のグループ名を一言添える
4. **02 非昇格グループ**: Step 2 のグループ単位で、そのグループに残った非昇格 hunk だけをファイル別 `<details class="file">` (既定 `closed`) に入れる。意図の解説はグループ単位で1つ。非昇格 hunk が0件になったグループはこの節ごと省略してよい (集計はヘッダの表に残っている)
5. **承認チェック — 置き場所は diff の下端**: 昇格ファイル単位で、`<details class="file">` の**中の末尾** (最後の hunk テーブルの直後) に置く。読み手はコードをスクロールで読み切った位置で宣言する動線のため、ヘッダやファイル冒頭には置かない。ラベルは「diff を読んだ」ではなく「挙動確認済み + この昇格箇所を見た」の宣言にする。**昇格が 0 件のときはチェック対象がないので、代わりに宣言チェックを1つだけ置く**(文言例:「挙動確認済み・昇格該当なし」)
6. **チェック状態の可視化 — 畳んだままでも分かるように**: チェック変更で `details.file` に `.approved` クラスを付け外しし、(a) `summary.file-head` に状態バッジ — 承認済みは ✓ (緑系。`--diff-add-fg` を流用)、未承認の昇格ファイルは「未確認」バッジ、(b) 右側ファイルナビの該当項目にも同じ状態を反映する。vanilla JS でヘッダのカウンタ「確認 n/N」に反映し、localStorage に保存する (キーはレポートファイル名)。**復元時はカウンタだけでなく `.approved` クラスとバッジも再適用する** — 保存状態と見た目がずれると「確認済みに見えるのに未保存」の混乱が生まれる

## Step 5: 検算と表示

- 昇格 hunk 数 + 非昇格 hunk 数の合計 = Step 1 の総 hunk 数を確認する。合わなければ漏れた hunk を「未分類」グループ (⑥) に収容してから公開する
- 保存先・`open`・gitignore 注意は base の Step 4 に従う

## Gotchas

- 未追跡ファイルは `git diff` に出ない — `status --porcelain` の `??` を拾わないと「新規ファイルだけレビューから抜ける」事故になる
- 承認チェックボックスは「挙動確認済み + 昇格箇所を見た」の宣言の記録であって、挙動確認そのものの証拠ではない — 挙動確認は上流ワークフローの責任であり、チェック状態を根拠に「動作確認済み」「レビュー完了」と親や履歴に報告しない。承認はユーザーの行為であってスキルの成果物ではない
- 生成した HTML 自体 (`docs/crystallize/reports/`) や plan (`docs/crystallize/plans/`) が差分に混ざることがある — レビュー対象から除外し、その旨を画面に一言記す
- plan に `## Deviations` 見出し・受け入れ基準の節が無くても止めない — ⑤の判定と受け入れ基準表示は「該当なし」として省略し、他の判定は通常どおり進める
- 非昇格グループを丸ごと省略したくなるが、「畳む」であって「消す」ではない — 検算の対象から外れた瞬間に「隠すより見せる」の原則が崩れる
