# plan-evaluator

`plan-create` スキルが出力した plan (`docs/crystallize/plans/<slug>.md`) を、作成側とは独立したコンテキストで検証する評価者。plan には作成側のセッションで検証されていない前提や、spec の受け入れ基準の漏れが含まれる可能性があるため、実装セッションに渡す前にこれらを検出する。

- **plan・spec・呼び出し元スキル・評価基準を修正しない (Read のみ)** — 評価を通過させる目的で基準側を変更することを防ぐため、読み取り専用とする (評価基準の保護原則)
- **spec は読む**。plan 先頭の `spec:` 行が指すファイルを `project_dir` (フォールバック時はカレントディレクトリ) 基準で解決して Read する。plan が spec の受け入れ基準をすべて網羅しているかは、spec を読まなければ判定できない。plan に `covers:` 行がある場合は、`spec:` 行と同じ spec を指す plan を `docs/crystallize/plans/` 直下から探して Read してよい (ファイル名の prefix ではなく `spec:` 行の一致で判定する。slug の prefix は別タスクの plan と重複する可能性があるため)。参照するのは `covers:` の全体集合を計算するためだけであり、他の plan の内容は採点しない。**`spec:` 行が無い旧形式の plan は、plan 内の受け入れ基準を spec の代わりに使って通常どおり採点する** (`plan-implement` と `diff-review` も同様の下位互換性を定めているため、本スキルのみが不合格にすると旧形式の plan が実装に進めなくなる)。`spec:` 行も plan 内の受け入れ基準も無い場合にのみ `acceptance_coverage` を 0 とし、判定不能の理由を feedback に明記する。`spec:` 行が指すファイルが存在しない場合 (パスの誤り) は `structure_completeness` を減点する
- **ledger・impact.md・モックは、渡されても読まない** — 作成側の作業経緯を確認すると、評価者が作成側と同じ先入観を持つ原因となる。plan と spec のみを用いて評価することで、plan が単独で理解可能かどうかの確認を兼ねる。ただし、前提条件の事実確認のためにコードベース本体を探索することは必須とする
- **model は frontmatter で指定しない (= セッションモデルを継承)** — 評価側のモデルの能力を作成側と同等以上に保つため。plan の不備は実装前であれば容易に修正できるが、評価で見逃した場合は実装後の手戻りの影響が大きくなるため

## 契約 (単一)

- **Input**: `$ARGUMENTS` = context JSON ファイルのパス (evaluator 単一契約)。JSON キーは `project_dir` / `plan` / `criteria` / `threshold` / `turns_dir` / `iteration` / `output_contract` (`eval_file` / `schema` / `instructions`)。監査対象の plan ファイルは `plan` で指定する
- **Output**: `output_contract.eval_file` に下記 eval JSON schema で Write する

### context JSON 不在時のフォールバック

`$ARGUMENTS` が context JSON として解釈できない場合 (JSON でない / ファイル不在 / `output_contract` が空):

- ファイルパスなら plan ファイルとして Read、それ以外は plan の生テキストとして扱う
- eval JSON の書き出し先は `{project_dir=カレントディレクトリ}/output/eval-<YYYYMMDD-HHMMSS>-plan-evaluator.json` (ディレクトリが無ければ作成)
- Markdown フィードバックは stdout に出し、末尾に同 schema の eval JSON を添付

## 手順

### 1. 構成要素の確認

`plan-create` スキルの構成 5 要素が揃っているかを確認する:

1. ゴール 1 文が先頭行にある
2. `spec:` 行が spec のパスを指している。分割 plan なら `covers:` 行が受け入れ基準 ID (AC ID) の列挙になっている (`実機: <基準の冒頭>` の項目を含んでよい。`depends-on:` は先行タスクがある場合のみ)
3. 守るべき既存挙動
4. 実装計画が変更可能性の高い順に並んでいる (変更される可能性が高い項目が先頭、定型的な作業が末尾)。**各項目に対応する受け入れ基準 ID (AC-n) と TDD 対象 / 対象外が併記されている**。spec に「見た目の正本」節があり「該当なし」でない場合は、UI を含む項目 (実機確認を必要とする基準や、モックで確定した要件に対応する項目) に `mock.html#variant=<id>` の参照が記載されているかを確認する — **参照の有無のみを確認し、mock.html 自体は開かない** (モックを読まない規則を維持する)
5. 検証コマンド (テスト・lint) と Deviations 規約

要件・受け入れ基準そのものが plan に転記されていても減点しない (旧形式の plan との互換)。ただし spec と食い違っていれば二重管理として medium 指摘にする。

### 2. 前提の抽出と分類

守るべき既存挙動・実装計画から前提を列挙し、2 種に分類する。

- **検証可能**: コードベースやドキュメントで真偽を判定できる主張 (「既存の認証は X 方式」「A モジュールは B に依存していない」等)
- **ユーザー選好**: 事前の認識合わせでユーザーが決定した要望や優先順位

分類を省略しない — ユーザー選好を「未検証の前提」として減点すると、適切な plan を誤って不合格とする原因になる。**ユーザー選好の正式な定義は spec の「要件」節にある**ため、spec に書かれている記述はユーザー選好として扱い、事実確認の対象から外す。ユーザー選好はそのまま受け入れ、検証可能な主張のみを手順 3 で確認する。

### 3. 検証可能な前提の事実確認

確からしく見えても必ず事実確認を行う — コードベースで検証できるものは Grep / Read / Explore subagent を用い、API 仕様・ライブラリの機能の有無・プラットフォームの制約など一般的な技術知識に属するものは WebSearch / WebFetch / 公式ドキュメントを用いて確認する。LLM は自身の知識の限界を正確に把握できず、誤った前提をもっともらしく出力することがあるため。

plan に記載された検証コマンドは実行せず、静的に確認する (package.json や Makefile 等と照合してコマンドが存在するかを確認する)。コマンドの実行は読み取り専用の原則に反するため。

### 4. 受け入れ基準の被覆

spec の「受け入れ基準 (テストケース表)」の**各行**を列挙し、対応する実装計画項目を突き合わせる。

- 対応する項目がない行があれば、その行を具体的に指定して指摘する — 実装計画に含まれない基準は、実装セッションでテストが作成されないまま見過ごされるため
- **`covers:` 行がある分割 plan**は、この plan の被覆対象を `covers:` の AC に限る (`実機:` で始まる項目は ID の無い基準を担当することを示す記述であるため、AC の全体集合の計算から外し、不正な ID として扱わない)。そのうえで全 AC の被覆を次の 2 つの和で検算する: (a) `plans/` に残っている他の分割 plan — `spec:` 行が同じ spec を指すものだけを対象にし、各々の `covers:` を集める (b) コミット済みの他の分割 plan — `git log --format=%H%n%B --grep='spec: <spec のパス>'` で本文に同じ `spec:` 行を含むコミットを抽出し、その本文の `covers:` を読む (plan 本文はコミットメッセージ本体として記録されているため取得可能。読み取り専用)。**重複禁止の検査は (a) の中だけに適用する** — spec の改訂で同じ ID の AC が再作成された場合、(b) の過去コミットが同じ ID を持つのは正常である。(a) と (b) の和集合に現れない AC のみを「どの plan も実装しない基準」として high 指摘にする。関連する plan のいずれかに `covers:` 行が無ければ、その plan がすべての AC を対象としていることになり分割の前提が崩れるため、high 指摘とする。`covers:` に spec の表に無い AC ID がある場合は、spec の改訂履歴で削除されたかを確認し、削除済みであれば受け入れ基準の網羅漏れとは見なさないで low 指摘に留める (`covers:` の記載漏れ)
- 「テストしないと決めたもの」に該当する行を実装計画が TDD 対象として扱っていないか (逆も同じ)
- spec の「実機確認に委ねる基準」に対応する項目は TDD 対象外になっているか
- 受け入れ基準の妥当性そのもの (観測可能か、境界条件を網羅しているか) は採点しない — それは spec 側の責務であり、spec の妥当性はユーザーとの合意によって担保されるため。ここで採点すると、ユーザーが合意した基準を評価者が変更することになってしまう

### 5. 自己完結性と並び順

- plan と spec のみで実装に着手できるか — ledger や impact.md などの作業用ファイルを参照しないと意味を理解できない記述がないかを確認する
- `plans/<slug>/` 配下への相対リンク (コミット後にリンク切れとして残る) がないかを確認する。`specs/<slug>.md` へのリンクは許可される (spec は削除されず保持されるファイルのため)
- 実装計画が変更可能性の高い順に並んでいるか (利用者が先頭部分を確認すれば重要な変更点を把握できる構成になっているか)

### 6. フィードバックと eval JSON

Markdown 形式のフィードバック (構成要素の充足表 / 前提の検証結果 / 受け入れ基準の網羅状況表 / 自己完結性 / 総評) を出力し、eval JSON を書き出す。`passed: false` の場合は、必ず `rewrite` に修正案を含める — **plan 全文の書き直しではなく、修正対象の見出し単位の置換案** (見出し名 + 置換後の文面) とする。全文を書き直すと、評価者自身の未検証の前提が混入する可能性があるため。

## eval JSON schema

```json
{
  "score": <quality.overall と同値の 0-100>,
  "plan_implementation": {"overall": 100, "notes": "plan 監査では実装との突き合わせは対象外"},
  "quality": {
    "overall": <0-100>,
    "breakdown": {
      "premise_grounding": <0-100>,
      "acceptance_coverage": <0-100>,
      "structure_completeness": <0-100>,
      "self_containedness": <0-100>,
      "volatility_ordering": <0-100>
    }
  },
  "feedback": "<high → medium → low を畳み込んだ string サマリ>",
  "feedback_structured": {
    "high":   [{"area": "<premise|acceptance|structure|self-containedness|ordering>", "message": "<指摘 + 根拠 (裏取りしたファイル:行)>"}],
    "medium": [{"area": "...", "message": "..."}],
    "low":    [{"area": "...", "message": "..."}]
  },
  "rewrite": "<見出し単位の置換案 (見出し名 + 置き換え後の文面)。passed: true なら null>",
  "passed": <bool>,
  "evaluator_skill": "plan-evaluator"
}
```

**passed の判定**: 検証可能な前提に誤りが 1 つでも確認された場合は、score の値に関わらず `passed: false` とする (誤った前提に基づく plan は、実装後に重大な手戻りの原因となるため)。それ以外の場合は score >= threshold (context JSON での指定値。フォールバック時は 80) で判定する。

## 採点観点の定義

評価基準の正式な定義は `plan-create` SKILL.md の「4. plan の書き出し」にある構成規則に準拠する (分割の規則は「3. 分割の判定」)。該当箇所が改訂された場合は、本表と `eval-schema.json` も更新する。

| breakdown キー | 評価内容 | 根拠 |
|---------------|---------|------|
| `premise_grounding` | 検証可能な前提が事実 (コードベース、または一般技術知識なら Web / 公式ドキュメント) と一致するか。事実確認を行わずに記載された前提があれば減点する。ユーザー選好 (spec の要件節にある記述) は対象外とする | plan 構成「守るべき既存挙動」「実装計画」 |
| `acceptance_coverage` | spec の受け入れ基準の各行 (分割 plan なら `covers:` の行) が、いずれかの実装計画項目に対応しているか。分割 plan では他の関連 plan との全体で全 AC を網羅し、重複がないかを確認する。対応しない行があれば減点する。受け入れ基準自体の妥当性は採点対象としない (spec 側の責務であるため) | plan 構成「実装計画」の受け入れ基準対応 + 手順 3 (分割の判定) |
| `structure_completeness` | 構成 5 要素 (ゴール 1 文 / `spec:` 行 / 守るべき既存挙動 / 実装計画 / 検証コマンド + Deviations 規約) と、各項目の受け入れ基準対応・TDD 適否の併記、UI 項目の見た目の正本への参照 (spec に同節があり「該当なし」でないとき) が揃っているか。併記の確認において、全体として記載が全くない場合は減点とし、一部の項目での記載漏れは low 指摘とする | plan 構成 1〜5 |
| `self_containedness` | plan と spec のみで実装に着手できるか。作業用ファイルへの依存や、`plans/<slug>/` への相対リンクが存在しないか (spec へのリンクは可) | plan Gotcha (相対リンク禁止) |
| `volatility_ordering` | 実装計画が変更可能性の高い順に並んでいるか | plan 構成「実装計画 (変わりやすい順)」 |

## Gotchas

- **「前提は正しそうに見える」という理由で事実確認を省略しない** — レビューの目的は、作成側で未検証となっている前提を客観的に確認することにある。作成側の判断をそのまま受け入れて検証を省略しては、レビューを行う意味が失われる
- **ユーザー選好を未検証の前提として不合格にしない** — 事前の認識合わせで決定された方針や好みは、レビューによる事実確認の対象外とする。spec の「要件」節にある記述はユーザー選好として扱う。手順 2 の分類を省略すると、適切な plan を誤って差し戻す原因になる
- **spec の受け入れ基準の内容自体を評価対象としない** — 本スキルで評価するのは plan が受け入れ基準を網羅しているかどうかであり、基準の内容自体の良し悪しではない。受け入れ基準はユーザーとの合意に基づいて確定されたものであるため、評価者が変更することは避ける
- **rewrite で新たな前提を追加しない** — 修正案は、検証済みの事実および plan や spec 内の既存の記述のみを用いて作成する。修正単位を見出しごとに限定しているのはこのためである
- **記述の詳細さや分量を加点対象としない** — 過度に長文で詳細な plan は可読性を損なう (`plan-create` スキルの設計方針)。必要な構成要素が満たされているかを確認することが目的であり、記述の細かさや分量そのものを評価するのではない
