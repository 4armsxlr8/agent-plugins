# find-unknowns

実装に入る前に、ユーザーの unknowns（未知）を洗い出して潰し切るための **認識合わせ専用** スキル。
開発途中プロジェクトの「次の機能・次の改修」単位で毎回発動する想定。
最終成果物は **plan 一枚** (`docs/crystallize/plans/<task-slug>.md`)。unknowns の洗い出しはその plan を正確にするための手段と位置づける。
plan は後段の `/plan-commit` がそのままコミットメッセージ本文に使い、コミット時に削除する。

## Input / Output

- **Input**: `$ARGUMENTS` = タスクの説明。省略時は直近の会話から推定し、一行で確認を取る。**複数タスク (issue) をまとめて渡してもよい — 上限3本** (それ以上はセッションが長くなり、論点がゴールからドリフトする)。複数の場合も各タスクに Step 0〜5 を省略せずフルに回して plan を1枚ずつ作る — まとめるのは対話の場であって、調査の深さではない。並列可否は Step 4 で判定し、Step 6 で配置まで案内する
- **Output**: 最終成果物は `{projroot}/docs/crystallize/plans/<task-slug>.md` (ゴール・確定事項・実装計画・受け入れ基準を一本化した plan)。作業ファイルは `{projroot}/docs/crystallize/plans/<task-slug>/` 配下に置く

| ファイル | 中身 |
|---|---|
| `docs/crystallize/plans/<task-slug>.md` | **最終成果物**: plan 本体 + 実装セッションへの引き継ぎ (Step 5) |
| `docs/crystallize/plans/<task-slug>/ledger.md` | unknowns 台帳 (未解決の論点 + 確定事項) |
| `docs/crystallize/plans/<task-slug>/mock-*.html` | 反応用モック (配線なし・ダミーデータの単一 HTML) |
| `docs/crystallize/plans/<task-slug>/impact.md` | 既存挙動・データ・他機能への影響 |
| `docs/crystallize/plans/<task-slug>/question-<n>.md` | 質問監査用ファイル (Step 3) |

## 最重要禁則

1. **プロダクトコードを書かない・編集しない**。Write してよいのは `docs/crystallize/plans/<task-slug>.md` と `docs/crystallize/plans/<task-slug>/` 配下のみ。
   理由: コードを書き始めた瞬間、認識合わせが「もう書いたコード」を正当化する方向に歪む (サンクコスト)。実装は docs/crystallize/plans/<task-slug>.md を受け取った別セッションの仕事。
2. **会話だけで合意を確定させない**。Unknown Knowns (見ればわかる好み) は質問では出てこない — 当たり前すぎて話題に上がらないため。各フェーズは必ず「見て反応できる成果物」を返し、反応をもって確定とする。

## unknowns の 4 分類 (台帳の分類キー)

| 分類 | 意味 | 主に潰すフェーズ |
|---|---|---|
| Known Unknowns | まだ決めていないと自覚していること | Step 3 インタビュー |
| Unknown Knowns | 当たり前すぎて口に出さないが、見れば「これじゃない」とわかること | Step 2 モック |
| Unknown Unknowns | 論点として存在に気づいていないこと | Step 1 blindspot pass |
| Known Knowns | すでに合意済みのこと | ledger の確定事項に記録 |

## Step 0: スコープ確認と台帳の初期化

`$ARGUMENTS` (なければ会話) からタスクを一行に要約してユーザーに示し、`docs/crystallize/plans/<task-slug>/ledger.md` を作る。台帳の先頭にタスクの一行要約を置き、「未解決」「確定事項」の 2 セクションを続ける。以降の全フェーズで、出てきた論点は未解決へ、決まったことは確定事項へ移す。

**各フェーズの冒頭で ledger.md 先頭のタスク要約を読み直す** — 長い認識合わせセッションでは論点がゴールからドリフトする。要約に対して意味のない論点は深追いせず捨てる。

## Step 1: Blindspot pass (Unknown Unknowns)

Explore subagent でコードベースを探索させ、結果を「ユーザーがまだ考えていなさそうな論点」に翻訳して提示する。

- 探索対象: タスクに関係する既存実装・命名や構造の慣習・過去の設計判断の痕跡・触ると壊れやすい箇所
- 親は探索結果の要約だけ受け取り、論点リストに変換して ledger に記録する (探索の生ログを親 context に吸わせない)
- 一般論の注意点は書かない。このコードベースの実物に grounding した論点だけが unknowns になる

## Step 2: ブレスト + 反応用成果物 (Unknown Knowns)

「見ればわかる」タイプの基準を、実装前に成果物への反応で言語化させる。

- 見た目・UX があるタスク: 方向性の違うモックを複数案、配線なし・ダミーデータの単一 HTML で作り、`open` で開いて反応をもらう
- **微調整したくなるプロパティにはモック内に調整パネルを付ける**: サイズ・間隔・色・速度・件数・閾値など「見ながら値を決めたい」プロパティは、スライダー・数値入力・カラーピッカー等の UI をモックに埋め込み、ユーザーがその場で動かして好みの値を決められるようにする — 一往復ずつ聞き直さずに数値の認識合わせが済む
  - パネルには現在値を常時表示し、「設定をコピー」ボタン (現在値一式を JSON でクリップボードへ。`navigator.clipboard` が使えない環境向けに同じ JSON をテキスト表示でも出す) を付ける。ユーザーは確定値を貼り返すだけでよく、親はそれを ledger の確定事項に転記する
- 見た目がないタスク: 反応できる代替物を出す — API レスポンス例、データモデル案、CLI 出力例、変換前後のサンプルデータ等
- モック各案の作成は並列のサブエージェント (下位モデル) に任せ、親は指示とレビューに専念する
- 反応 (採用・不採用・「ここは違う」) は理由ごと ledger の確定事項に記録する。複数案から1つを採用する反応は、Step 3 の「失われる体験の復唱確認」を通してから確定する

## Step 3: インタビュー (Known Unknowns)

台帳の未解決項目を、一問ずつユーザーに聞いて潰す。

- **答えによってアーキテクチャや挙動が変わる質問を優先**する。答えが設計を変えない質問はしない
- 一問ずつ聞く。前の答えが次の質問を変えるため、一括リストは無駄な質問と浅い回答を生む
- 質問は技術の選択肢ではなく **挙動の選択肢** に翻訳する (例: 「SQLite と Hive どちらにしますか」ではなく「オフラインでも過去データを見られるようにしますか」)。選択肢化できる質問は AskUserQuestion で出す
- 回答は ledger の確定事項へ

### 質問の関所 (バイアス対策)

質問は自分の仮実装案の分岐点から生成されるため、案に含まれた思い込み (偽の二択・誤った前提) をそのまま引き継ぐ。ユーザーに出す前に 4 規則 + 監査を通す。

1. **前提の裏取り**: 質問の前提を一文で抜き出し、コードベースで検証可能ならコードベースで、API 仕様・ライブラリの機能有無・プラットフォーム制約など一般技術知識に属するものは WebSearch / WebFetch / 公式ドキュメントで検証する。ユーザーに聞いてよいのは、検証しても残る好み・優先順位だけ
2. **二択の証明義務**: 「A と B どちらを優先しますか」型の質問は、両立できないメカニズムを一文で書けたときだけ出す。書けなければ偽の二択の証拠 — 先に両立案を設計する
3. **前提の開示**: 質問文に「前提: 〜と考えています。違っていたらご指摘ください」を含め、ユーザーが選択肢ではなく前提側を撃てるようにする
4. **喪失の開示**: 選択肢の説明には、それを選ぶと**できなくなること・失われる体験**を否定形で含める (例: 「画像がすべて」ではなく「リンク先で作品一覧は見られない」)。「挙動の選択肢に翻訳する」原則の続き — 選択肢は「得られる挙動」だけでなく「失われる挙動」も挙動レベルで示して初めて対等になる。肯定形の説明だけでは、採らなかった案の喪失が実感されないまま確定する (実例: 「画像がすべて」のラベルで確定した選択が、挙動ゲートで「リンク先で一覧が見える」認識とのズレとして発覚した)

**監査 (必須・全質問)**: 各質問は、出す前に `question-evaluator` (Skill ツール、fork 実行) に監査させる。ここの精度が後工程のやり直し確率を直接下げるため、時間とトークンをかける価値がある。

- 監査の観点は 4 規則に加え、**選択肢リストが答えの空間を狭めていないか** (両立案の欠落、自然な選択肢が「その他」に押し込まれる構成) も含む
- 質問ファイル `docs/crystallize/plans/<task-slug>/question-<n>.md` に「タスク一行要約 + 質問文 (前提の開示込み) + 選択肢案」を書き、そのパスを args で渡す
- 実装案や ledger は質問ファイルに含めない — 案を見せると監査側が同じバイアスに迎合する
- `passed: false` (前提誤り・偽の二択等) なら、その質問は捨てて規則 1 の裏取りからやり直す。`rewrite` (書き直し案) が返っていればそれを基に再監査にかける

### 失われる体験の復唱確認 (選択の確定)

複数案からユーザーが1つを選んだら (モック反応・AskUserQuestion のどちら経由でも)、採らなかった案で**失われる挙動を否定形の一文**で復唱し、同意を得てから確定事項に記録する。例: 「この選択では、リンクを受け取った人はあなたの作品一覧を見られません。画像だけです。よろしいですか？」

- 規則 4 (喪失の開示) の確定側の対 — 選択の瞬間にユーザーが見ているのは選んだ案の絵であり、選択肢に喪失が書いてあっても、確定の直前にもう一度否定形で突きつけないと実感されないまま通過する
- **「案 A で出して反応を見てから案 B を検討」型の段階導入の選択では必須** — ユーザーの頭に案 B の絵が残ったまま確定しやすい
- 復唱への「いいえ」は選び直しであって手戻りではない — ここで出るズレは実装後の挙動ゲートで出るズレの先取り。選び直しになったら、ledger の該当確定事項を未解決に戻してから聞き直す

## Step 4: 既存挙動への影響洗い出し

開発途中プロジェクト特有の unknowns — 「すでに動いているものとの整合性」を潰す。Explore subagent で裏取りし、`docs/crystallize/plans/<task-slug>/impact.md` に書く。

- 変わる既存挙動 (ユーザーから見えるもの優先)
- 移行が必要なデータ・設定
- 触ってはいけないもの (依存されている挙動・公開インターフェース)

影響から新しい論点が出たら Step 3 に戻る。Step 1〜4 は一方通行ではなく、**ledger の未解決項目のうち「設計・挙動を変えうるもの」がゼロになるまで** 回す。

**並列の仕分け (複数タスクのとき)**: 全タスクの impact を突き合わせ、触るファイル・モジュールの交差を判定する — 交差しなければ並列可、交差するなら順序を決めるか1本に統合する。進行中の他 worktree の plan があれば、それとの交差も同じ基準で確認する。仕分け後の探索で見えていなかった交差が判明したら、並列をやめて順序提案に切り替える (誤った並列はマージ衝突として跳ね返る)。

## Step 5: plan の書き出し (`docs/crystallize/plans/<task-slug>.md`)

最終成果物の plan を一枚に書く。実装セッションにそのまま渡せる自己完結の文書にする (ledger や impact.md を読まなくても実装に入れること)。構成:

1. **ゴール 1 文** (先頭行。後でコミットメッセージの要約行の素になる)
2. **確定事項** (ledger の確定事項から転記)。**テスト・lint の検証コマンドを1行含める** — 実装フェーズの各エージェントが毎回コマンドを探索せずに済む。挙動に関わる確定事項には**否定形の帰結** (その結果、何が起きない・見えない・できないか) を一文併記する (例: 「受け手体験は汎用 LP で開始」→「= リンク先に共有者個人のデータは一切表示されない」) — 実装セッションが plan を引き継いだ時点で認識ズレに気づける保険
3. **実装計画 — 変わりやすい順**。並び順が本体:
   - 先頭: ユーザーが差し替えたくなる可能性が高いもの — データモデルの変更、新しい型インターフェース、ユーザーに見える挙動
   - 末尾: 機械的な作業 (リファクタリング・配線・テスト整備) を畳んで一括記載
   - ユーザーは先頭だけ精読すればよい、という設計にする
4. **守るべき既存挙動** (impact.md の要点)
5. **観測可能な受け入れ基準** (「テスト全緑」「初回表示 3 秒以内」のような挙動レベル)。挙動が変わる境界 — 数量の 0/1/多/上限、時刻の跨ぎ、中断・再実行、空・重複・順序 — を洗い出し、該当するものは基準に含める (境界の取りこぼしは実装後の手戻りとして露見した実績がある)
6. **Deviations 規約**: 「計画から逸れる必要が出たら保守的な選択を採り、この plan 自体の `## Deviations` 見出しの下に理由ごと追記して続行する (別ファイルを作らない — plan-commit で plan がそのままコミットメッセージになるため、逸脱の記録も一緒に履歴へ残る)。認識合わせに戻すべき大きな逸脱 (確定事項と矛盾する等) は作業を止めてユーザーに戻す」

**監査 (必須)**: 書き出した plan は、ユーザーに提示する前に `plan-evaluator` (Skill ツール、fork 実行) に監査させる。args = `docs/crystallize/plans/<task-slug>.md` のパス。誤前提・観測不能な受け入れ基準は実装後の手戻りとして跳ね返るため、ここで止める価値がある。

- ledger や impact.md は渡さない — 監査が plan 単体で行われることが、plan の自己完結性の検査を兼ねる
- `passed: false` なら指摘箇所を裏取りからやり直して plan を修正し、再監査にかける。`rewrite` (見出し単位の置換案) が返っていればそれを基にする
- 再監査は 3 周を上限とし、収束しなければ未解決の指摘を添えてそのままユーザーへの提示に進む (無限ループを避けるための打ち切り上限)

30 行を超えるなら html-report で HTML 化して提示する (plan 本体は md のまま)。

## Step 6: 案内して終了

最後に次の流れを案内して終了する:

1. 新しいセッションで `/plan-implement` に `docs/crystallize/plans/<task-slug>.md` を渡して実装を開始する (実装 → テスト → 動作確認 → diff の例外確認 → plan-commit までは plan-implement が一本で駆動し、各接続はスキルが自分で呼ぶ)

案内と一緒に、**新しいセッションにそのまま貼れる最初のプロンプト** をコードブロックで提示する。雛形 (パスは実際の値に置き換え、絶対パスで書く — 新セッションがどの cwd で開かれても迷わないため):

```
/plan-implement /path/to/docs/crystallize/plans/<task-slug>.md
```

複数タスクで並列可と判定した場合は、**並列配置** (どの worktree でどの plan か・交差したものはどの順序か) を小さな表で提示して合意を取る。**合意後の配置は案内で終わらせず、本スキルが自分で実行する** (案内文止まりの接続は実際には実行されない、が過去セッションで繰り返し観測された失敗の型):

1. `git worktree add` で worktree を作成する (git ネイティブ機能 — 特定ツールに依存しない)
2. `docs/crystallize/plans/<task-slug>.md` と `docs/crystallize/plans/<task-slug>/` を担当 worktree へ移動する (plan はこの時点ではまだコミットされていないため、worktree を切っても自動では現れない。`docs/` 配下は追跡対象のパスであり、plan は確定時に削除されるまでの間だけ一時的に履歴に入る)
3. 各 worktree でセッションを起動する — Orca が使える環境なら orca-cli で worktree を管理下に置いて Claude を起動し、`/plan-implement <plan の絶対パス>` を terminal send で送る。無い環境では、worktree ごとの雛形プロンプトを提示してユーザーに各ターミナルで開いてもらう (対話セッションが必要なため、起動だけは環境の道具に依存する)

以降の対話 (挙動ゲート・例外ゲート) は各 worktree のセッションが直接ユーザーと行う。本セッションは配置の完了報告 (worktree 一覧と各セッションの状態) で終了し、司令塔として残らない — 進捗の観察はユーザー側の道具 (Orca があれば cardStatus) が担う。

プロンプトに plan の要約や補足を膨らませない — 実装に必要な情報が plan の外に漏れ出すと、plan の自己完結性が崩れて二重管理になる。足りない情報に気づいたら plan 側に書き足す。

## Gotchas

- **モックに本物の配線をしない** — バックエンドや実データに繋いだ瞬間「実装禁止」が崩れ、捨てるコストが生まれて反応が歪む。単一 HTML + ダミーデータで十分。調整パネルのインライン JS はダミーデータを動かすだけなので配線に当たらない (禁止対象はバックエンド・実データへの接続)
- **blindspot pass を一般論で埋めない** — 「テストを書きましょう」「エラー処理に注意」は unknowns ではなくノイズ。このコードベースで実際に見つかった慣習・過去の判断だけを論点にする
- **計画の網羅性で安心しない** — 長く網羅的な計画は読まれず、読まれない計画は認識合わせに寄与しない。変わりやすい順に並べて先頭に注意を集める
- **禁則 1 の昇格判断**: 実装禁止が破られる事故が再発したら、Gotcha に留めず hook (PreToolUse で `docs/crystallize/plans/` 外への Write/Edit をブロック) へ昇格する
- **plan 本文から作業ファイルへ相対リンクを張らない** — plan は `/plan-commit` でコミットメッセージになり、`docs/crystallize/plans/<task-slug>/` はその時点で削除される。リンク先が消えた文書が履歴に残る
