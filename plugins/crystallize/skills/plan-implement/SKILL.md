# plan-implement

要件は固定するものではなく育てるもの。認識合わせでどれだけ詰めても、UI は触って初めて分かることが残り、リリース後に利用者の声で変わることも普通にある。忠実性とは『黙って逸れないこと』であって『変えないこと』ではない。

`plan-create` スキルが作った plan (`docs/crystallize/plans/<slug>.md`) と、その plan が指す spec (`docs/crystallize/specs/<slug>.md`) を受け取り、実装 → 検証 → コミットまでを一続きの契約で駆動する統括役。3つのゲート（機械・挙動・例外）を順に通し、**挙動ゲートが収束するまで diff-review を作らない** — 修正ループの途中で diff を出すと、直すたびに陳腐化して結局読まれずコミットに流れる（過去のセッションで繰り返し観測された失敗パターン）。コードは書かず、実装はすべてサブエージェントに委任する。

## Input / Output

- **Input**: `$ARGUMENTS` = `docs/crystallize/plans/<slug>.md` のパス。省略時は `docs/crystallize/plans/` 直下の `.md` が1つならそれを使い一行で確認を取る。複数あれば AskUserQuestion で選んでもらう。該当する `.md` が無ければ実装を始めず、`spec` → `plan-create` の順で先に plan を作るよう案内して終了する
- **Output**: `plan-commit` が作る1コミット。進行中は `docs/crystallize/plans/<slug>.md` 本体に `## 進行状況`（フェーズ別チェックリスト）と `## Deviations`（逸脱ログ）を書き足しながら進め、確定と同時にコミットメッセージへ畳み込まれて消える（補助ファイルは作らない）。spec は消えない — 仕様改訂レーンで書き換えた場合、その差分は同じコミットに入る

## 最重要禁則

1. **diff-review はフェーズ4（挙動ゲート）が収束するまで呼ばない** — 陳腐化した diff を見せると読まれずコミットに流れる
2. **サブエージェントの完了報告だけでフェーズ3（機械ゲート）を済ませない** — 自己申告は証拠ではない。フェーズ2の完了報告が全項目揃っていても、テスト/lint コマンドは plan-implement 自身が実行し直す
3. **要件と矛盾する逸脱、plan にない大規模変更に気づいたら続行せず止める** — Deviations に書いて進めてよいのは可逆・局所的な選択だけ。大小の判断に迷ったら止める側に倒す。**これはエージェント発の逸脱（実装中に矛盾に気づいた場合）だけの規則**で、ユーザー発の仕様変更には適用しない — ユーザーが要件そのものを変えたいと言ったときはフェーズ4の仕様改訂レーンで処理する。ここで止めると、ユーザーが自分で変えた要件について許可を求められることになる

各フェーズは完了条件を満たすまで次へ進まない。完了条件を満たしたら、次に何をするかを一行でユーザーに予告してから進む。

## フェーズ1: plan / spec 受領と Deviations 契約

- plan を Read し、先頭の `spec:` 行が指す spec も Read する（`spec:` 行のパスはリポジトリルート（`git rev-parse --show-toplevel`）基準で解決する）。守るべき既存挙動・実装計画・検証コマンド・Deviations 規約は plan から、要件・非機能要件・受け入れ基準（テストケース表）は spec から取る — 寿命が違う情報を混ぜないため、plan は使い捨て、spec は残って改訂される。あわせて**用語集**（リポジトリ直下に `## 用語` か `## Language` を持つ `CONTEXT.md` があればそれ、無ければ `docs/crystallize/CONTEXT.md`。どちらも無ければ spec の用語節）も Read する — 実装で付ける識別子と表示文言はここの語に合わせる
- **`spec:` 行がない旧形式の plan は、plan 内の確定事項と受け入れ基準をそのまま情報源にして従来どおり動かす**（以降の「要件」「受け入れ基準」はその場合 plan 内のそれを指す）
- plan に `covers:` 行があれば（`plan-create` スキルが spec を分割した場合）、この plan が扱う受け入れ基準は**そこに列挙された AC だけ**。以降の「受け入れ基準」はその範囲を指し、範囲外の AC は他の plan の担当なので、不足として扱わない・テストを書かない・挙動ゲートのチェックリストにも載せない。`depends-on:` 行があれば、そのパス（`spec:` 行と同じくリポジトリルート基準で解決する）の先行 plan が `docs/crystallize/plans/` にまだ残っていないかを確認し、残っていれば実装を始めず、先行 plan を先に `/plan-implement` に渡すよう案内して終了する（後続 plan は先行のコミットを前提に書かれており、先行が無いまま進めると同じ箇所を二重に書く）。ファイルが無いときは `git log --format=%B --grep='<先行 plan のゴール 1 文>'` で先行のコミットが実在することを確かめる — 無ければ「先行 plan が見つからない」として止め、ユーザーに確認する（ファイルが無いことは、コミット済みの証拠にも、移動・書き忘れの証拠にもなる）
- `## 進行状況` 見出しが無ければ作る。実装計画の各項目 + 4つのゲート（機械/挙動/例外/確定）をチェックボックスで列挙する。既にあれば最初の未チェック項目から再開する — セッションが切れても plan を読めば再開点がわかる
- `## Deviations` 見出しが無ければ作る（本文は空でよい）。**古い plan の Deviations 規約が「implementation-notes.md を作る」と書いていても従わない** — 本スキルは別ファイルを作らず、この見出しに直接追記する契約が正（現行の `plan-create` スキルも同じ規約で plan を書く）
- 逸脱の扱い: 計画から逸れる必要が出たら保守的な選択を採り、`## Deviations` に一行（計画項目 / 実際の選択 / 理由）を追記して続行する。要件と直接矛盾する逸脱は、矛盾点と spec の該当箇所を並べてユーザーに提示し判断を仰ぐ（作業は止めたまま。禁則3のとおりエージェント発の逸脱に限る）
- **完了条件**: plan と spec の読了、`## 進行状況` / `## Deviations` が存在し、次に着手する項目が1つに定まっている

## フェーズ2: 実装

- 実装計画の項目を先頭（変わりやすい順）から進める。末尾の機械的作業（リファクタ・配線・テスト整備）はまとめて1回の委任にしてよい。**意図が同じ小さなスライスが連続する場合も1回の委任に束ねてよい**（fork は1回ごとに起動と文脈読み込みの固定費を払うため。束ねてよいのは意図が同じもの同士だけ — 別の意図を混ぜると逸脱の追跡が濁る）
- 各項目の TDD 適否を判定する（適用範囲: 入出力で正解を固定できる挙動変更は TDD。UI・見た目・使い捨てプロトタイプ・設定更新は対象外とし、フェーズ4の実機確認に委ねる）
- 委任は即興の Agent プロンプトではなく **generator スキルの Skill 呼び出し**で行う（委任のたびに契約文を書き直すと渡す情報も禁則もぶれる。契約はスキル側に固定してある）:
  - **TDD 対象スライス**: spec の「受け入れ基準（テストケース表）」の該当行と「テストしないと決めたもの」をそのまま `test-generator` に渡し、RED（失敗するテスト + 実行証拠）を得て、続けて `code-generator` を起動して GREEN にする。**ここで seam・境界ケース・テストしない範囲の合意を取り直さない** — tdd の「書く前に合意」規則の担い手は `spec` スキルに移っており、この表がその合意の記録そのもの。実装セッションの冒頭でもう一度仕様の話をさせない
  - **非 TDD スライス**: `code-generator` を単独で起動する
  - 渡すのは該当項目の計画文 + 関連する要件 + 受け入れ基準 + テストの実行コマンド + 用語集のパスと「識別子・表示文言は用語集の語を使い、『使わない語』を新たに導入しない」の一文だけ（fork した generator は用語集の在り処を知らないので、パスと規則を渡さないとコードだけが別の語で書かれる）。TDD の場合はさらに、`test-generator` には受け入れ基準表の該当行と「テストしないと決めたもの」を、`code-generator` には RED 状態のテスト一覧を加える。**UI を含む非 TDD スライスにはさらに、plan の項目にある見た目の正本 (`mock.html` の絶対パス — plan のリポジトリ相対パスをリポジトリルート基準で解決する — と、確定案の `#variant=<id>`・確認した状態。`#variant=` はパスの一部ではなく案の識別子なので別項目として渡す) と、spec の「見た目の正本」節の調整パネルの最終値 (JSON) を加える** — これが無いと実装者はモックを一度も見ずに要件行の言葉だけから UI を書き、質感 (色・余白・角丸・タイポグラフィ・影・動き) がモックから乖離する (実績あり)。あわせて「実装前に確定案の markup・CSS・`applyTweaks` からトークン表を抜き出し、報告に含める」の一文を添える。**このスライスは effort を high にする** — モックの翻訳は機械的作業ではなく判断作業で、`code-generator` の既定 (コスト効率優先) の想定から外れる (モデル指定ではなく effort で制御する)。spec 全文や決着済みの論点は渡さない
  - **表にないケースを `test-generator` が提案してきたら、spec の改訂候補としてユーザーに1回だけ聞く**（表は合意の記録なので、勝手に足すとテストが黙って増殖する）。採るなら受け入れ基準の表に行を足し、改訂履歴に1行（場面は「実装」）を追加してから差し戻す。採らないなら「テストしないと決めたもの」に理由つきで足し、改訂履歴にも1行（場面は「実装」）を足す — spec を書き換えたのに履歴に残らない経路を作らない
- 逸脱は generator の報告から plan-implement 自身が `## Deviations` へ転記する。escalate の報告を受けたら続行せず、最重要禁則3のとおり止めてユーザーに戻す
- **完了条件**: 進行状況の実装計画項目すべてに完了報告または解決済み escalate が付いている（この時点の報告は自己申告のままでよい — 検証は次のフェーズが行う）

## フェーズ3: 機械ゲート — 正しいか

- プロジェクトのテスト・lint コマンドを plan-implement 自身が実行する。サブエージェントの「全緑でした」報告だけでは進めない
- **テストは選別して回す**: 修正ループ中の再実行は、変更の影響範囲のテスト（変更したファイル・モジュールに対応するもの）だけでよい。**全量スイートはゲートの完了条件としてだけ1回**回す — 検算の原則は保ったまま、全量実行を最後の1回に集約する（変更していない部分のテストを毎周道連れにしない）
- 失敗したら `code-generator` に差し戻して修正させ、再実行する。12回試みても収束しなければ実装を止めてユーザーに報告する
- テスト・lint が緑になったら `code-review` スキルで AI コードレビューを行い、指摘を解消してから次へ進む。挙動ゲートより先に置く理由: 指摘の修正でコードが変わりうるため、ユーザーの動作確認を後にしないと確認がやり直しになる
  - 指摘の修正は `code-generator` に差し戻す（指摘の一覧を渡す。テストは不変のまま）。修正後はテスト・lint を再実行し、必要なら code-review も再実行する。この修正ループも12周で収束しなければ止めてユーザーに報告する
  - 指摘が「テスト自体の欠陥」を指す場合は、実装で辻褄を合わせさせず、ユーザーに確認のうえ `test-generator` に差し戻す（期待値の保護 — 基準側の変更は人間の確認を経る）
  - effort は **low を基本**とし、次のいずれかに該当する変更は **high** に上げる: アーキテクチャ・データモデル・公開インターフェースに触れる / plan の複数項目にまたがる大きな変更 / 共通基盤など影響が長く残る箇所
  - 解消せず受け入れる指摘は理由を `## Deviations` に記録する（diff-review の昇格④⑤として人間の目に入る）
- 変更が**対外境界・依存追加**（diff-review の昇格リスト②③）に触れる場合に限り、`security-review` スキルでセキュリティレビューも実行する。該当判定の正本は diff-review 側の昇格リスト — 同表が改訂されたらそちらに従う。該当しなければ「security-review 対象外」と進行状況に記録して飛ばす（毎回走らせない理由: 境界に触れない変更への網羅監査はコストだけ増えて指摘が出ない。該当する diff はどのみち例外ゲートで人間の目にも入る）
  - 指摘の扱いは code-review と同じ: 修正は `code-generator` に差し戻してテスト・lint を再実行し、解消せず受け入れる指摘は理由を `## Deviations` に記録する
- code-review（と、実行した場合は security-review）の指摘を畳んだら `simplify` スキルで品質整理（再利用・単純化・効率・抽象度）を適用する。code-review の後に置く理由: 正しさの修正を先に済ませないと、整理した形の上にまた修正が乗って二度手間になる（バグ探しは code-review、品質整理は simplify という役割分担どおり）
- code-review / security-review / simplify で1行でもコードが変わったら、テスト・lint をもう一度実行して緑を確認する（ここも影響範囲の選別でよい）
- **完了条件**: code-review と security-review（実行した場合）の指摘が解消済みまたは Deviations に記録済み、simplify の適用が済み、**最後のコード変更より後に全量の**テスト・lint が exit 0 で終わっている（フェーズ2のサブエージェント報告の使い回しは不可）

## フェーズ4: 挙動ゲート — 意図どおりか（diff より先）

- spec の「実機確認に委ねる基準」、「(モック確定・実機で再確認)」印の要件、受け入れ基準のいずれにも見た目や UI 操作の項目が無ければ、「UI確認対象なし」と進行状況に記録してフェーズ5へ進む
- あれば `run` スキルでアプリ/モックを起動し（ブラウザ対象なら、環境にブラウザ表示を担う道具があればそれで開き、無ければユーザーにブラウザで開いてもらう。特定の製品名は書かない — 利用者ごとの道具は利用者側のスキルが担う）、チェックリストを**ユーザーに提示し、ユーザー自身に触ってもらう**。並び順は spec の「実機確認に委ねる基準」と「(モック確定・実機で再確認)」印の付いた要件が先頭、続けて受け入れ基準の操作パス — 印の付いた項目はモックの反応で仮決めした箇所で、実機で覆る確率が最も高い。`covers:` に `実機:` の項目があれば、実機確認に委ねる基準とモック確定印の要件はそこに挙がったものだけを載せる。`docs/crystallize/specs/<slug>/mock.html`（`spec` スキルのラウンドシート兼反応用モック。spec 配下なので消えずに残っている）があれば見比べの基準に使う — 現状の案や不採用の案も並んでいるので、`data-variant-name` に「(確定)」の付いた案 (spec の「見た目の正本」節の `mock.html#variant=<id>`) を見る。**モック確定印の項目は、確定案と実機を並べて確認するのを必須にする** (任意にすると記憶との照合になり、質感の差は記憶では検出できない)。実機と確定案の差が見つかったら、要件は変わっていないので微修正レーンで扱う
- 「ここ違うな」が出たら修正の性質でレーンを分ける。**どのレーンでも、このループが収束するまで diff-review は呼ばない**
  - **微修正レーン** (テストで固定した挙動の契約を変えない修正 — 見た目・文言・定数調整など): TDD の重機を回さない (`test-generator` を呼ばない — UI・見た目は TDD 対象外の原則の再適用)。指摘はユーザーが一通り触り終えるまで**束ね、まとめて1回** `code-generator` に委任する。色・余白・文言レベルの1〜2行の即時調整でユーザーが画面の前で待っている場合に限り、plan-implement が直接編集してよい (委任の固定費が作業を上回るため — 委任原則の明文化された例外)。再検証は lint + 影響範囲のテストのみで、code-review は再実行しない (差分の全量は最後に例外ゲートを通る)。hot reload など実行中のアプリを保ったまま反映できる手段があれば使い、その場で再確認する
  - **正規レーン** (実装が spec と食い違っていた修正 — 要件は正しいが挙動がそれに届いていないもの): 従来どおりフェーズ2に差し戻し、修正後は影響範囲のフェーズ3だけ再実行してからこのチェックリストに戻る
  - **仕様改訂レーン** (ユーザーが要件そのものを変えた修正 — 「やっぱりこうしたい」): 実装は spec のとおりだが、触ってみて spec の側が間違っていたと分かった場合。手順は次の4つ
    1. **「これは仕様の変更として spec に記録します: <変更点1行>」と1回だけ宣言する**。以後、同じ点について「仕様と違いますがよいですか」と聞き直さない — 反復は本人が決めたことの許可をもう一度求める作業で、ユーザーが仕様の変更を言い出しにくくなる
    2. spec の要件と受け入れ基準の該当行を書き換え、改訂履歴に1行（日付 / 項目 / 変更 / 理由 / 場面は「挙動ゲート」）を追加する。書き換えた要件行にも否定形の帰結を併記する（spec の要件節の作法を維持する）。spec の無い旧形式の plan なら、同じ内容を plan の `## Deviations` に「仕様改訂」と明記して書く（記録先が無いことを理由に記録を省かない）
       - **要件の語が変わったときは、同じ手順の中で用語集も直す** — 新しい語を導入した / 意味を変えた / 呼び方を変えた場合。用語集の書き手は通常 `spec` だけだが、この場面の plan-implement は spec の編集者として動いているので例外にあたる。直さないと、コードと spec が新しい語で用語集だけが古い語のまま残り、次の spec がそれを正本として読む。書き方の規律は `spec` スキルの Gotchas にある 5 つに従い、変えた語は spec の「用語」節にも 1 行残す（あの節はこの spec で決めた語・変えた語の記録）
       - **見た目が変わったときは、同じ手順の中で spec の「見た目の正本」節と `mock.html` の焼き込みも直す** — 確定案が変わったなら「(確定)」の位置と節の `#variant=<id>`、値が変わったなら `TWEAKS` の `value` と節の最終値 JSON。実機で覆ることは前提 (印の付いた項目は覆る確率が最も高い) なので、覆るたびに正本を追随させないと、次の実装者が古い案と値を写す
       - **分割 plan（`covers:` 行がある）で受け入れ基準の行が増減したときは、同じ手順の中で `covers:` 行も直す** — 追加した AC は、その挙動を実装するのがこの plan なら自分の `covers:` に足す。他の plan の担当なら `plans/` に残っているその plan の `covers:` に足し、残っていない（コミット済み）なら止めてユーザーに伝える（実装済みの範囲に後から要件を足すことになるため、新しい plan を立てるか次の plan に載せるかの判断が要る）。削除した AC は自分の `covers:` から外す。ここで直さないと、どの plan の担当でもない AC が生まれて誰も実装しないまま全 plan がコミットされる
    3. 影響する受け入れ基準の行（AC-n）だけを `test-generator` に差し戻す — 「期待値の変更は人間の確認を経る」規則のその確認が、1 の宣言にあたる
    4. `code-generator` で実装 → 影響範囲だけフェーズ3を再実行 → このチェックリストに戻る
    - モック確定印の要件など、受け入れ基準の行に影響しない見た目だけの変更でも 1・2 は行う（spec を現実に合わせるのが目的で、記録を省くと次の実装で同じ議論をやり直す）。3 は差し戻す行が無いので省き、コード側は微修正レーンの作法でよい
- **完了条件**: チェックリストの全項目（実機確認に委ねる基準・モック確定印の要件・受け入れ基準の操作パス）について、ユーザー自身の言葉で「意図通り」の確認が取れている（UI確認対象なしの記録で代えた場合も可）

## フェーズ5: 例外ゲート — 危なくないか

- フェーズ4収束後に初めて `diff-review` を Skill ツールで直接起動する（案内文にしない）: skill = `diff-review`, args = `plan: <plan のパス>`
- ユーザーが既に別のレビュー手段（例: 別の AI レビューツールのループ）を使うと明言している場合は起動を省いてよいが、レビューそのものの省略は認めない
- **昇格 hunk が0件のとき、diff-review は画面を作らず「全 M hunk 中、昇格 0 件 (①〜⑥該当なし)。N files +a -d (レビュー対象外 X hunk: reports/plans を除外)。go / no-go を」の1行だけを返す**（`M` は除外後の判定対象 hunk 数。除外が0件なら括弧ごと省く）。その1行を検算の数字ごとそのままユーザーに示して go / no-go を得る — 画面が無いのは省略ではなく「見せるべき例外がなかった」という結果で、レビュー未実施として扱わない
- 昇格ありなら生成された画面を開いてもらい、決裁カードごとの「このリスクを受け入れるか」の判断として明示的な go / no-go を得る。no-go ならフェーズ2かフェーズ4へ差し戻す
- **完了条件**: ユーザーの明示的な go が得られている（この go はフェーズ6のコミット同意を兼ねる）

## フェーズ6: 確定

- フェーズ5の go を受けて `plan-commit` を Skill ツールで直接起動する（案内文にしない）: skill = `plan-commit`, args = `<plan のパス>`
- 仕様改訂レーンを通っていても、spec の改訂履歴をここで自分でコミットメッセージへ転記しない — 転記は `plan-commit` の手順3の担当（転記の担い手を1箇所にしないと、二重に入るか両方が相手に任せて落ちる）
- `plan-commit` が返す `git log -1 --stat` の要点をそのまま報告する。スライスごとの経過は語り直さない
- **完了条件**: `plan-commit` が完了し、plan ファイルと plan と同名のディレクトリ（`docs/crystallize/plans/<plan の basename>/`）が削除されている（spec は残る）

## Gotchas

- **下流スキルへの接続を「〜してください」の案内文に退化させない** — 過去の運用で、案内文止まりの下流スキル接続は高い頻度で実際には実行されず、即興レビューや手動 git 操作に置き換わることが繰り返し観測された。フェーズ5・6は必ず Skill ツールで直接起動する
