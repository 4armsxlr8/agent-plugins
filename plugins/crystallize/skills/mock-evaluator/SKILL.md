# mock-evaluator

`spec` スキルが作ったモック (`docs/crystallize/specs/<slug>/mock.html`) を、作成側とは独立したコンテキストで、その画面を使う人の立場から辿り、使いにくい箇所を指摘する評価者。案は親エージェントが言葉にできた論点から作られ、その論点はユーザーの発言から作られる。そのため作成側は「言われたとおりの形」を複数並べるところで止まりやすく、言われたとおりに作ると使いにくい箇所と、誰も口にしていない別の形は作成側では検出されにくい。本スキルはそれらをユーザーに見せる前に検出する。

本文書では、モックを依頼して案を選ぶ人を「ユーザー」、モックに描かれた画面を実際に使う人を「使う人」と書く (同じ人であることもある)。

`spec` が毎ラウンド行う**試問** (問いの文面が読めるか・選択肢の違いが分かるか) と `question-evaluator` (問いの前提と二者択一の論理) は問いを検査する。本スキルは問いではなく**絵と導線**を検査するので、どちらの代替にもならない。

- **モックの HTML と、context JSON で渡された文だけを見る**。ledger・spec・plan・対象アプリのコード・作成役の報告は、渡されても読まない — 作成側の検討経緯を読むと「そう決めた理由」に納得してしまい、初めて触る人がつまずく箇所に気づけなくなる
- **何も修正しない (Read と対象の操作のみ)** — モック・キット・評価基準を編集しない (評価基準の保護原則)。直す案は `suggestion` に書いて返す
- **ユーザーが口にした形も疑う対象に含める** — context JSON の `stated_form` は評価の前提ではなく検査対象である。そのとおりの流れを辿って使いにくければ、どの案の出来とも別にそれを報告する。ただし採否を決めるのはユーザーなので、本スキルは「辿るとこうなる」という観測だけを書き、取り下げさせる判定はしない
- **fork された環境ではユーザーと対話できない** — 何をするための画面かが `task` からも `stated_form` からも読み取れない場合は、推測で辿らず `undecidable: true` で終了する
- **model は opus を指定する** — 親セッションが軽いモデルで動いていても、評価側の能力を作成側と同等以上に保つため

## 契約 (単一)

- **Input**: `$ARGUMENTS` = context JSON ファイルのパス。JSON キーは次のとおり
  - `project_dir`: リポジトリルート
  - `plan`: 評価対象の `mock.html` のパス (`project_dir` 基準。evaluator 単一契約のキー名に合わせている)
  - `task`: タスクのジョブストーリー 1 文 (使う人・場面・したいこと・結果)
  - `user`: この画面を使う人の 1 行 (誰が・どんな場面で使うか)
  - `stated_form`: ユーザーが口にした形 (どの画面で・何が出て・何をするか) の 1〜3 文。`spec` が作成役に渡したものと同じ文。ユーザーが形を口にしていないタスクでは省略される
  - `structure_shown`: 前のラウンドまでにユーザーが見て選んだ構造のまま、値だけを詰めるラウンドなら `true`。省略時は `false`
  - `variants`: 手順 3 で辿る案の `data-variant` の配列。省略時は下記の評価対象の全案。再評価で描き直した案だけを辿るために使う
  - `iteration` / `output_contract` (`eval_file` / `schema` / `instructions`): plan-evaluator と同じ。`threshold` は受け取っても合否には使わない
- **Output**: `output_contract.eval_file` に下記 eval JSON schema で Write する

**評価対象の案**は、`data-rejected` が付いておらず、`data-variant-name` が「現状」で始まらない案とする。「現状」の案は既存画面のスクリーンショットや再現で、描き直す対象ではない。辿らず、手数を比べる基準としてだけ読む。

`$ARGUMENTS` が context JSON として解釈できない場合 (JSON でない / `output_contract` が空) は、ファイルパスなら `mock.html` として扱い、`task`・`user`・`stated_form` が無い旨を feedback に明記したうえで、シート内の `QUESTIONS` の `premise` を手がかりに評価する。eval JSON の書き出し先は `{project_dir=カレントディレクトリ}/docs/crystallize/output/eval-<YYYYMMDD-HHMMSS>-mock-evaluator.json` (ディレクトリが無ければ作成)。書く前に、同ディレクトリの既存の `eval-*.json` を削除する (後から読む処理のない使い捨ての出力なので、最新の 1 回分だけを残す)。Markdown フィードバックは stdout に出し、末尾に同 schema の eval JSON を添付する。パスが存在しない場合は `undecidable: true` で終了する。

`undecidable: true` で終了するときは、`score` と breakdown を 0、`goals`・`form_diffs`・`walks`・`findings` を空配列とし、理由を `feedback` に書く。

## 手順

### 1. 辿り方の決定

**モックは静的である**。キットのモックは、押しても画面が移らないのが普通で、画面の移り変わりは「同じ案の中に並んだ枠 (`.cz-frame`。上のラベルが画面名)」と「状態 (`data-state`)」で描かれる。そこで 1 手は次のように判定する: 押すものが画面にあり、押した結果に当たる枠か状態が同じ案の中に描かれていれば、その手は辿れたとする。押しても表示が変わらないこと自体は指摘しない。結果に当たる枠も状態も描かれていなければ「描かれていない」と記録する。

モックをブラウザで開いて操作できる手段 (ページの操作と表示の読み取りができるツール) がこの環境にあるかを確認する。ツールは遅延ロードされている場合があるため、必要なものは **1回の ToolSearch でまとめて**ロードする。特定の製品名は本文書に記述しない (ツール類は利用者側の環境設定に依存するため)。

- **操作して辿る (`mode: "operated"`)**: 手段があるとき。**必ず新しいタブで開き、辿り終えたらそのタブを閉じる** (ユーザーが見るシートは親が試問のあとに 1 回だけ開くため、評価用のタブを残さない)。案の切替は URL のハッシュ `#variant=<id>`、状態と端末の切替は下部のバーで行う。回答パネルとテーマ切替 (◐) には触れない (回答パネルの入力は下書きとして保存され、あとで開いたユーザーに復元されるため)。重なり・切れ・画面外に出た操作部品は、このときだけ判定する
- **読んで辿る (`mode: "traced"`)**: 手段が無いとき、`file://` を開けないとき、開けても操作できないとき。ほかの手段を探して回らず、こちらに切り替える。判定不能にはしない。スロット層 (`<style id="cz-mock-style">`、`.cz-variant` の中身、`<script id="cz-mock-script">`) を Read し、枠ごとに「何が見えるか」「押せるものは何か」「その結果に当たる枠や状態はどれか」を書き出してから辿る。重なりや切れのように描画しないと分からない点は判定せず、判定しなかった旨を feedback に書く

無改変層 (`CZ-KIT:*` で囲まれたブロック) は読まない。キットの切替バー・調整パネル・回答パネルは評価対象ではない。画像の data URI は読み飛ばしてよい。

### 2. 目的の列挙

`task`・`user`・`stated_form` から、使う人がこの画面でやり遂げたいことを 2〜5 個、使う人の言葉で書き出す (例: 「検索した作品を、続きの期と一緒に登録する」)。主な目的 1 つに加えて、次のうちモックに関係するものを入れる。

- 初めて開いたとき・データが 0 件のとき
- 途中でやめる・間違えて戻る
- 件数が多いとき・上限に達したとき
- 失敗したとき (通信できない、対象が見つからない)

ここで書いた目的が以降の採点の単位になる。目的を書かずに画面の感想を並べない (「見やすい」「すっきりしている」は導線の評価にならない)。

### 3. 案ごとに辿る

`variants` (省略時は評価対象の全案) の各案について、目的ごとに最初の画面から 1 手ずつ辿り、`walks` に記録する。1 手ごとに「見えているもの → 押すもの → 結果に当たる枠・状態」を書く。関係する状態があれば切り替えて辿る。調整パネル (`TWEAKS`) は既定値で辿り、値によって手順や最初の表示が変わる項目があれば、その値でも辿って、どの値での観測かを書く。次の点を探す。

| 探すもの | 例 |
|---|---|
| 行き止まり | 戻る・取り消しが無い。目的の途中で、次に当たる枠が描かれていない |
| 次の一手が見えない | 何を押せば進むのかが画面から分からない。主な操作が画面外や他の部品の下にある |
| 手数 | 同じ目的に対して他の案や現状より明らかに手数が多い。件数が増えると手数が比例して増える |
| 結果が見えない | 押した結果に当たる枠や状態に、何が変わったのか・成功したのかが描かれていない |
| 見かけの食い違い | 同じ見た目の部品が、枠によって違う役割で使われている。押せるものと押せないものが見分けられない |
| 状態で切れる | 0 件・上限・失敗のとき、その先へ進む手段や抜ける手段が無い |
| 取り返しのつかない操作 | 削除や上書きに、確認や取り消しに当たる枠・状態が無い |
| 文言 | ボタンや見出しが、押すと何が起きるかを言っていない |

描かれていない画面を「実装ではこう動くはず」と補って完了扱いにしない。

### 4. 案の幅を検査する

`structure_shown` が `true` のとき、または `stated_form` が無いときは、この手順を行わない (`pattern_breadth` は N/A)。

`stated_form` を読み、評価対象の全案 (`variants` で絞られていても全案) について「この案は口にされた形のどこを変えているか」を 1 文ずつ `form_diffs` に書く。問いそのものが置き場所を尋ねるラウンドでも同じ基準で見る (その問いの外にある形を 1 つ見せることが目的である)。`data-rejected` の付いた案は辿らないが、その案が崩した前提は「ユーザーが見て退けたもの」として数え、同じ崩し方を再び提案しない。

- すべての案が、口にされた形の中での配置違い (同じ手順・同じ情報を、置き場所だけ変えたもの) であれば、**口にされた形を崩した案を最低 2 つ自力で組み立ててみる**。崩し方の手がかり: その手順ごと無くす (聞かずに決めて後から直せるようにする) / 順番を変える (先に済ませる、後回しにする) / 入口を変える (別の画面から始める) / まとめる・分ける (1 回で済ませる、1 件ずつにする) / 最初に見せる情報を減らす
- 組み立てた案のうち、手順 3 で見つけた問題を 1 つ以上解消するものを 1 つだけ `missing_pattern` として挙げる (最も多く解消するもの)。**どの問題も解消する案が組めなければ `missing_pattern` は挙げず**、`pattern_breadth` を下げて、組み立てて捨てた案を feedback に 1 行ずつ残す (違うだけの案を足すと、ユーザーに好みを聞くことになる)
- `suggestion` は作成役がそのまま描ける細かさで書く: どの枠に何が出て、何を押すとどの枠に移り、どの目的の何手目が変わるか

`data-variant-name` が「(提案)」で始まる案は、作成役が頼まれずに足した案である。この案が口にされた形を実際に崩しているかも同じ基準で見る。崩せていなければ、その案を名指しして `missing_pattern` を挙げる (親はこの案を描き直させる)。

### 5. 口にされた形そのものを辿る

`stated_form` があるとき、手順 3 で見つけた問題のうち、**`stated_form` の文言に由来すると示せるもの**を `premise_doubt` として分けて報告する。全案に共通していても、口にされた形とは関係のない描き漏れ (どの案にも次の枠が無いなど) は `variant_issue` のままとする。評価対象が 2 案以上あるときは、全案に共通する問題であることも条件とする (1 案だけの問題は、その案の出来である)。

- `stated_form` の該当箇所を原文で引用し、どの目的の何手目で何が起きたかを書く
- 「希望が間違っている」とは書かない。「この形のとおりに辿ると、N 件のときに M 手かかる」「途中でやめる手段が描かれていない」のように観測を書く
- 口にされた形のどこを緩めると問題が消えるかが分かれば `suggestion` に書く。これは親エージェントがユーザーに問いとして出すための材料であり、評価者の決定ではない

### 6. フィードバックと eval JSON

指摘を `findings` に並べ、重さを付ける。

- `high`: 主な目的を最後まで辿れない / 主な目的の経路に行き止まりがある / `missing_pattern` (手順 4 の条件を満たして挙げたもの) / 口にされた形のとおりに辿ると主な目的を辿れない、または使う人が気づかないまま意図と違う結果を確定できる
- `medium`: 主な目的以外の目的で辿れない・行き止まり / 手数や結果の見えなさが目的の達成を遅らせる
- `low`: 文言・小さな食い違い

`feedback` はそれらを畳み込んだ 1 段落のサマリとする。

## eval JSON schema

```json
{
  "score": <quality.overall と同値の 0-100>,
  "plan_implementation": {"overall": 100, "notes": "モック評価では実装計画との突き合わせは対象外"},
  "quality": {
    "overall": <eval-schema.json の weight による breakdown の加重平均 0-100>,
    "breakdown": {
      "flow_completion": <辿った案 × 目的のうち、最後まで辿れた割合 0-100>,
      "friction": <辿れた経路に、手数・結果の見えなさ・食い違いの指摘が少ないか 0-100>,
      "pattern_breadth": <案が口にされた形の配置違いに留まっていないか 0-100。N/A は 100>,
      "evidence_grounding": <全指摘に、辿った手順と観測が付いているか 0-100>
    }
  },
  "mode": "operated|traced",
  "goals": ["<手順 2 で書いた目的>"],
  "form_diffs": [{"variant": "<data-variant>", "changes": "<口にされた形のどこを変えているか 1 文。手順 4 を行わないときは空配列>"}],
  "walks": [
    {"variant": "<data-variant>", "goal": "<目的>", "completed": <bool>, "steps": ["<見えているもの → 押すもの → 結果に当たる枠・状態>"]}
  ],
  "findings": [
    {"kind": "variant_issue|missing_pattern|premise_doubt", "severity": "high|medium|low", "variant": "<data-variant。複数の案に共通する指摘と、案に属さない指摘は JSON の null>", "goal": "<目的>", "observation": "<辿った手順と観測。premise_doubt は stated_form の原文引用を含める>", "suggestion": "<直す案。missing_pattern は作成役が描ける細かさで>"}
  ],
  "feedback": "<high → medium → low を畳み込んだ string サマリ>",
  "feedback_structured": {
    "high":   [{"kind": "...", "variant": "...", "message": "..."}],
    "medium": [{"kind": "...", "variant": "...", "message": "..."}],
    "low":    [{"kind": "...", "variant": "...", "message": "..."}]
  },
  "undecidable": <bool>,
  "passed": <bool>,
  "evaluator_skill": "mock-evaluator"
}
```

**passed の判定**: `high` が 0 件かつ `undecidable` でなければ `passed: true`。`passed: false` はシートを見せることを止める判定ではない — 呼び出し元 (`spec`) は `high` の指摘を、直すか、案として足すか、ユーザーへの問いとしてシートに載せるかのいずれかで処理してからシートを見せる。`score` は参考値であり合否には使わない。

## 採点観点の定義

| breakdown キー | 評価内容 | 根拠 |
|---------------|---------|------|
| `flow_completion` | 辿った各案で、手順 2 の目的を最初の画面から最後まで辿れるか。描かれていない枠で止まった経路は未完了とする | 手順 3 |
| `friction` | 辿れた経路に、手数の多さ・結果の見えなさ・見かけの食い違い・状態で切れる箇所がどれだけあるか | 手順 3 の表 |
| `pattern_breadth` | 案が、口にされた形の配置違いに留まっていないか。`structure_shown` が `true` のとき、`stated_form` が無いときは N/A (満点扱い) | `spec` SKILL.md「Step 3: モック」の提案の案 |
| `evidence_grounding` | 各指摘に、辿った手順と観測が記録されているか。観測の無い指摘は減点する | 手順 3・5 |

## Gotchas

- **辿らずに感想を書かない** — 「情報が多い」「分かりにくい」だけの指摘は作成側が直せない。「目的 X の 3 手目で、候補が 12 件あるとき [登録する] が一覧の下にあり、最後まで送らないと見えない」のように、目的・何手目・見えたものを書く
- **見た目の好みを採点しない** — 配色や余白の好みはユーザーが調整パネルで決める。本スキルが見るのは、目的をやり遂げられるかと、そこまでのつまずきである。`traced` のときは重なりや切れも判定しない
- **違うだけの案を足さない** — `missing_pattern` は、辿って見つけた問題を解消する案に限る。問題を解消しない案を足すと、ユーザーに好みを聞くだけの比較が増える
- **口にされた形を黙って上書きしない** — `premise_doubt` は観測の報告であり、取り下げる決定ではない。`suggestion` は親エージェントが問いにするための材料に留める
- **押しても動かないことを指摘しない** — モックは静的で、移り変わりは枠と状態で描かれる。指摘するのは、結果に当たる枠や状態が描かれていないことである
