# diff-review — 例外ビューア（人間レビューの最後のゲート）

本スキルは、fork された環境で差分のレビュー画面を生成する役割を持ちます。人間による確認作業は、以下の 3 つの観点に分かれます。

1. **意図どおりか**（挙動確認） — 上流のワークフロー（`plan-implement` の「挙動ゲート」等）が担当します。本スキルは、この確認が完了した後に呼び出される前提です。
2. **正しいか**（テスト + AI レビュー） — 人間による判断は不要です。Step 2 で結果を集計して提示するのみです。
3. **危なくないか**（`plan-implement` でいう「例外ゲート」）— **本スキルの担当範囲です**。昇格条件に該当する hunk のみを人間に提示します。

**この画面で人間が行う作業は、昇格条件に該当する変更点のリスクを受け入れるかどうかの承認判断のみであり、コードの実装が正しいかどうかの判定ではありません。** 実装の正しさ（2 の観点）はテストと AI レビューによって検証済みです。人間がコードの詳細を再判定しようとしても確認作業が形式化しやすいため、判断に必要な情報のみを整理して提示します。承認判断に不可欠なのは「何が起きうるか・元に戻せるか・誰に影響するか」であり、差分コードの詳細を読み解くことではありません。そのため、昇格した hunk は**利用者にとって同じ悪影響を及ぼすもの同士でリスクごとに集約し**、そのリスク 1 件につき決裁カード（`references/components.md` 部品7）を 1 枚出力します。カードは利用者の視点で記述された見出し 1 文と平易な説明文 4 項目を最初に提示し、コードや判断根拠は初期状態で折りたたんだまま承認判断ができる構成にします。

すべての hunk をそのまま提示する構成では、確認すべき箇所が埋もれてしまい、見落としや不十分な確認の原因となります。本スキルは、すべての差分を順に読ませるのではなく、**リスクのある変更箇所を強調し、その他の変更箇所を折りたたんで整理する画面**として機能します。すべての hunk が確認対象に含まれていることを保証する検算は維持します。折りたたむ目的は、情報の除外ではなく表示の整理です。

## 呼び出し前提

**動作確認が完了したあとに呼び出します。** 動作確認の完了前に呼び出すと、レビュー画面の生成後に動作確認を行って修正が入り、生成した差分が古くなって再レビューが行われないままコミットされるという問題が生じます。

主な起動経路は、`plan-implement` のフェーズ5（例外ゲート）から Skill ツールで `skill: diff-review, args: plan: <plan のパス>` として起動される形式です（挙動確認を行うフェーズ4が完了した後にのみ呼び出される取り決めです）。ユーザーが「diffレビュー」「レビュー画面」と直接指示して実行する従来の方法もそのまま利用できます。

HTML 生成の共通規約（単一ファイルで完結・外部 CDN の使用禁止・チャットへの本文直接出力の禁止・保存先と `open` コマンドによる表示・style.css の適用）は、派生元である同一プラグインの `html-report` スキル本文を Read して従ってください。本スキルは、その共通規約に diff レビュー固有のルールを追加して適用します。

## Input / Output

- **Input**: `$ARGUMENTS` = 比較の基点 (省略時は `git diff HEAD` + 未追跡ファイル)。`plan: docs/crystallize/plans/<slug>.md` が指定されている場合は、意図解説や昇格判定の根拠として使用する。指定がない場合でも `docs/crystallize/plans/` 直下に関連する plan があれば Read する。候補が複数ある場合は自動で選択せずユーザーに確認する。分割された plan は `covers:` の対象範囲が異なるため、選択を誤ると別の plan の受け入れ基準を確認済み記録として表示することになる。**plan の先頭に `spec: docs/crystallize/specs/<slug>.md` の行がある場合は spec も Read し (パスはリポジトリルート (`git rev-parse --show-toplevel`) 基準で解決する)、受け入れ基準の表示は spec の「受け入れ基準 (テストケース表)」から取得する**。要件の正式な定義は spec 側にあり、plan は実装手順のみを持つためである。`spec:` 行がない旧形式の plan (受け入れ基準を plan 内に保持しているもの) は、従来どおり plan から取得する。
- **Output**: 昇格 hunk が 1 件以上ある場合 — `<projroot>/docs/crystallize/reports/YYYY-MM-DD-diff-review-<slug>.html` を生成して `open` で開く。最終応答は「決裁カード数 (昇格 hunk 数) / 全 hunk 数 + 各カードの見出し文をそのまま (カードが 4 枚を超える場合は、①および②のカードの見出しのみを並べ、残りは件数のみを記載) + ファイルパス」のみとする (見出しを再要約しない。応答と画面で文言が変わると、どのカードを指しているか特定できなくなるため)。**昇格 hunk が 0 件の場合 — HTML は生成せず、最終応答は Step 3 のスキップ規則の 1 行のみとする。**

## 最重要ルール (理由つき)

- **hunk 数の検算（合計の一致確認）を必ず完了させる** — 昇格 hunk 数 + 非昇格 hunk 数の合計が、差分全体の hunk 数と一致するまでレポートを公開しない。分類に迷う hunk は「未分類」グループに配置する (見落としを防ぐため。未分類の hunk は条件⑥として自動的に昇格対象となる)。
- **各 hunk は 01 (昇格) または 02 (非昇格) のどちらか一方に一度だけ配置する** — 昇格した hunk を元のグループ側にも重複して残すと、合計数の整合性が崩れて検算ができなくなる。
- **diff 本文は必ず HTML エスケープ処理を行う** — コードには `<div>` や `&&` などの文字列が含まれる。エスケープ処理を怠ると、表示崩れにとどまらず差分が画面上に表示されなくなる問題が発生する。
- **解説文には参照資料にある事実のみを記載する** — plan、コード、diff から確認できる事実のみを記述し、推測による記述には「推測:」と明記する。
- **昇格判定に迷った場合は昇格対象とする** — 確認対象が増える負担よりも、不可逆な操作などの重大なリスクを見逃す被害の方がはるかに大きいためである。

## Step 1: 差分の収集

```bash
PROJROOT=$(git rev-parse --show-toplevel)
git -C "$PROJROOT" diff <基点> --stat   # 規模の把握
git -C "$PROJROOT" status --porcelain   # 未追跡ファイルの検出
```

- 基点の指定を省略した場合は、`git diff HEAD` (ステージ済みおよび未ステージの変更) に加え、未追跡ファイルを「新規ファイル全体の追加」として差分に含める。
- 総ファイル数、総 hunk 数、総追加・削除行数をここで確定し、検算の基準値として記録する。**`M` は「除外後の判定対象 hunk 数」**とする。レビュー対象外のファイル (生成済みレポート `docs/crystallize/reports/`、plan `docs/crystallize/plans/`。Gotchas 参照) の hunk は `M` に含めず、その除外件数を別途記録する (昇格 0 件のときの出力行に記載するため)。
- 差分の規模が大きい場合 (数百 hunk) は一度に読み込まず、ファイル単位に分割して Read する。
- plan がある場合は同じタイミングで Read し、実装計画および `## Deviations` 見出し (存在する場合) の内容を記録しておく。plan の先頭に `spec:` 行がある場合は該当する spec も Read し、要件と受け入れ基準の表を記録する。`spec:` 行がない旧形式の plan は、plan 内の確定事項や受け入れ基準を同じ用途で使用する (いずれも Step 3 と Step 4 で使用する)。

## Step 2: 論理グループ化と解説

hunk を **ファイル単位ではなく変更意図の単位** でグループ化する (同一ファイルの hunk が別グループに分かれてもよい)。plan がある場合は、plan の実装計画項目とグループを対応づける。各グループに記載する項目は以下のとおりとする。

| 項目 | 内容 |
|---|---|
| グループ名 | 変更の意図を表す短い名詞句 |
| タグ | feat / refactor / fix / docs / config / test |
| リスク | 低リスク (挙動の変化なし・局所的変更) / 注意 (共通基盤への影響・広範囲に波及) / 要注意 (データ変更・削除・セキュリティ関連) |
| 意図 | 変更理由と影響範囲を 2〜3 文の平易な完全な文で記述 |
| 指摘 | diff を確認して気づいた問題点 (ある場合)。詳細な検証は /code-review の役割であるため、確認時に明らかな点のみを記載 |

この「指摘」欄の内容は、Step 3 の昇格判定④の入力情報となる。plan の実装計画項目に対応しないグループは「未分類」として残す (Step 3 の⑥により昇格対象となる)。グループごとの hunk 数は、**昇格した hunk も含めた総数** を集計する (Step 4 のヘッダ表示で「うち昇格 n 件」として表示するため)。

## Step 3: 昇格判定 — 例外ビューアの核

hunk 1 件ごとに、以下の 6 条件のいずれかに該当するか判定する。該当する場合は「昇格」、該当しない場合は「非昇格」とする。

| # | 昇格理由 | 判定材料 | 目安 |
|---|---|---|---|
| ① | データ削除・移行・不可逆操作 | diff 本文・ファイルパス | `DROP`/`DELETE`/`TRUNCATE`/`rm`/`migrations/` 配下/スキーマ変更 (`ALTER TABLE` 等) |
| ② | 対外境界 | ファイルパス・diff 本文 | 公開 API ルーティング・認証・課金・秘密情報 (`.env`/secrets/key)・外部送信の新規呼び出し・CORS/権限設定 |
| ③ | 依存の追加・更新 | ファイルパス | `package.json`/`pubspec.yaml`/`requirements.txt`/`Gemfile`/`go.mod`/`Cargo.toml` 等のマニフェスト |
| ④ | AI レビューの指摘・不一致 | Step 2 の「指摘」欄 | 指摘が載っている hunk |
| ⑤ | plan の Deviations | plan の `## Deviations` 見出し | 確定事項からの逸脱に対応する hunk。plan がない場合や該当見出しがない場合は判定対象外として扱う (エラーとはしない) |
| ⑥ | plan にない予想外の変更 | Step 2 のグループ分類 | どの実装計画項目・意図にも紐づかない hunk (= 「未分類」グループ) |

1 つの hunk が複数の条件に該当する場合がある。その際は該当したすべての番号を記録する (Step 4 でバッジとしてすべて表示する)。判定に迷う hunk は昇格対象とする (最重要ルール参照)。

### スキップ規則 — 昇格 0 件なら画面を作らない

昇格した hunk が 1 件もない場合は、**HTML を生成せず Step 4 をスキップする**。最終応答は以下の 1 行のみとする (`M`・`N`・`a`・`d`・`X` は Step 1 で確定した実際の数値):

```
全 M hunk 中、昇格 0 件 (①〜⑥該当なし)。N files +a -d (レビュー対象外 X hunk: reports/plans を除外)。go / no-go を
```

除外が 0 件の場合は後ろの括弧全体を省略する (不要な情報を表示しないため)。

単一の形式的な確認のためだけにブラウザを開かせることは避ける。軽微な変更でも毎回画面を生成すると確認作業の形式化を招くためである。**スキップするのは Step 4 のみであり、Step 1〜3 の処理および Step 5 の検算は通常どおり実行する。**

### リスクへの束ね — 決裁の単位は hunk ではなくリスク

昇格した hunk を、**利用者にとって同じ悪影響を及ぼすもの同士**でまとめる。まとまり 1 つが決裁カード (Step 4) 1 枚に対応する。判定自体は hunk 単位で行い、まとめるのは表示上の整理であり判定の基準単位ではない。

- まとめる基準は「利用者から見た悪影響が同一であるか」のみとする。同一ファイルにあること、昇格理由が同じであること、Step 2 の論理グループが同じであることは基準としない。確認者が判断するのは結果としてのリスクを受け入れるか否かであり、ファイルやコードの区切りは承認の単位ではないためである。
- **1 カード 1 ファイルに縛らない**。1 つのリスクが複数ファイルにまたがる場合は、そのカード内に全ファイルの hunk を並べて配置する。
- 他とまとめられない hunk は 1 件単独で 1 枚のカードにする。無理にまとめないこと。異なる影響を 1 枚に混在させると、的確な見出し 1 文が作成できなくなる。見出しを端的に表現できない場合は、別々の影響が混在している証拠であるため分割する。
- **1 つの hunk は 1 枚のカードにのみ配置する**。2 つの悪影響に関与する hunk は、影響がより重大な側のカードに配置し、もう一方のカードの根拠欄に「この変更は <相手の見出し> のカードにある」と 1 行記載する (複数のカードに配置すると、昇格 hunk 数とカード内の合計が一致しなくなり、検算が成立しなくなるため)。
- 検算 (Step 5) は hunk 単位で実施する。カード数を検算の母数としないこと。カード数はまとめ方によって増減するため、母数にすると hunk の確認漏れを検知できなくなる。
- まとめた結果のカード数を記録する。ヘッダの要約行および承認進捗の分母 (Step 4-1)、承認チェックボックスの総数 (Step 4-5) にこの数値を使用する。

## Step 4: HTML の構成 (昇格が 1 件以上のときだけ)

HTML の基本骨格、タブ、diff コンポーネント (行番号2列・hunk ヘッダ・sticky ファイルヘッダ・右側ファイルナビ) は、派生元である html-report の `../html-report/references/templates.md` の**構造をそのまま使用する**。ただし、**`<main>` は `class="report report-numbered"` と指定し、`markdown-body` は付与しない**。`markdown-body` の子孫セレクタ (詳細度 (0,1,1)) が components.md の固有部品の単一 class (0,1,0) を上書きし、レイアウト崩れが発生するのを防ぐためである。diff-review 固有の部品 (昇格理由バッジ・ヘッダ集計・決裁カード・承認チェック・状態バッジ・保存用 JavaScript) の定義は `references/components.md` を正本とする。CSS および JavaScript のブロックは変更せずに配置し、マークアップは該当ファイルで定義されているスロット規約 (`{…}` プレースホルダと繰り返しコメント) の範囲のみを差し替える。**事前の定義にない部品の追加や独自 CSS の作成は行わない**。不足している部品は components.md への追記として対応する (自由な記述による都度生成は、レポートごとの外観の不一致を招くためである)。以下 1〜6 に、各部品に設定する内容を定義する。

1. **ヘッダ**: タイトル (タスク名 + 差分レビュー)、`N files / M hunks +追加 -削除`、**「人間が決裁する箇所 <カード数> 件 (昇格 <昇格 hunk 数> hunk) / 全 <判定対象 hunk 数> hunk」の要約行** (承認判断の単位と検算の単位が異なるため両方を表示する。カード数のみでは全 hunk が判定を通過したことが確認できず、hunk 数のみでは必要な承認件数が把握できないため)。グループ別リスク・指摘の集計 (Step 2 の表をそのまま縮小表示し、各行に「うち昇格 n 件」を付記する。AI レビューが実施済みである根拠として配置する)。承認進捗「確認 0/N」(N = 承認チェックの数 = 決裁カード数。部品6 の JavaScript がこの N を実際のチェック数で上書きするため、昇格 hunk 数を記述すると表示上の整合性が取れなくなる)。レビュー対象から除外した hunk (reports/plans) がある場合は、その件数と理由を除外注記 (部品 1 の `review-note`) に記載する。0 件なら行ごと省略する。
2. **受け入れ基準** (spec に記載がある場合。spec がない旧形式なら plan の該当セクションから取得): 動作確認チェックリストとしてヘッダ付近に配置する。spec のテストケース表は 1 行 1 項目として要約する (`<seam> — <ケース> → <期待結果>`)。plan に `covers:` 行がある場合は、そこに列挙された受け入れ基準 (AC) の行のみを掲載する (他の plan の担当分はこの差分の確認実績にならないため)。spec の「UI・見た目など TDD 対象外で挙動ゲート (実機確認) に委ねる基準」も同一リストに続けて記載する。`covers:` に `実機:` の項目がある場合は、実機確認に委ねる基準とモック確定の要件のうち、そこに記載されたもののみを掲載する。「テスト対象外と決定した項目」は確認完了の記録ではないため掲載しない。この画面上で操作者にチェックさせるのではなく、挙動ゲートを通過済みであることの記録として表示する。spec にも plan にも受け入れ基準の記載がない場合は、このセクション全体を省略する。
3. **01 昇格** (先頭): Step 3 でまとめたリスク 1 件につき決裁カード (部品7) を 1 枚、`01 昇格` 見出しの直下に並べる。**ファイル単位の `<details class="file">` で囲まない**。1 枚のカードが複数ファイルにまたがる場合があるためである。カードの内容は上から順に以下のとおりとする。
   - **見出し 1 文** (`.decision-headline`。80 字以内): 「<いつ・どの操作で>、<利用者に何が起きうるか>。<取り消せるか>」。**この見出しを読むだけで承認判断ができる記述**を基準とする。確認者は事前の動作確認でアプリケーションを操作した人物であるため、プログラムコードの用語で記述すると判断に必要な情報が伝わらない。
   - 利用者に及ぶ悪影響が特定できない昇格 (③依存関係の追加・⑥未分類で発生しやすい) については、「<何が変更・追加されたか>。利用者への影響は<推測: …/ 入力情報からは読み取れない>。」という形式で記述する。**根拠のない悪影響を創作して記述しない**。入力情報にない事実を追加しないルールを見出しにも適用する。確認者が判断するのは「影響範囲が不明確なまま進行してよいか」であり、推測を交えない客観的な判断材料を提供する。
   - **4 項目** (各 1 文・60 字程度): **何が起きうるか** (利用者視点での悪影響。見出しの単なる言い換えとせず、**どのような状況で発生するか、またはどの程度の範囲で発生するか**の情報を補足する) / **元に戻せるか** (可逆か不可逆かの区分と復旧手順の要約) / **影響範囲** (対象ユーザー・対象データ・発生タイミング) / **AI レビューの判定** (「指摘なし」「N 件の指摘はすべて解消済み」「未解消 N 件: <概要>」のいずれかを記載。指摘番号は記載しない)。これら 4 つの項目名と順序は固定とし、表現を変更しないこと。毎回異なる言葉で記述すると、確認者が情報を探す負担が増えるためである。
   - **根拠は折りたたむ** (`<details class="decision-basis">`「根拠を見る」、初期状態は closed): 動作の仕組みの説明・code-review の指摘との対応・Deviations との対応・該当する hunk の一覧を記載する。識別子を記載できるのはこの折りたたみ内以降に限定する。該当する内容がない項目は削除せず「該当なし」と記載する。
   - **hunk ごとの diff** (初期状態は closed): まとめた hunk を templates.md の `<details class="file">` を用いて 1 件ずつ配置する (同一ファイル内の hunk が 2 件ある場合はブロックも 2 つ配置する。ファイルナビゲーション上は同一ファイルが出現順に重複して表示されてよい)。承認判断に必要なのは見出しと上記 4 項目であり、コードの詳細ではない。確認が必要な場合に展開できるため、初期状態で折りたたむことは情報の除外ではない。
   - 昇格理由バッジ (①〜⑥、複数可) と元のグループ名はカード上部にまとめる (まとめた hunk の内容を合算し、重複するバッジは 1 つにまとめる)。バッジを折りたたみの内部 (`hunk-head`) に配置しないこと。展開するまで昇格理由が確認できなくなるためである。
   - **記載できるのは入力情報に含まれる事実のみとする** (最重要ルール参照)。「AI レビューの判定」の情報源は Step 2 の「指摘」欄および plan の `## Deviations` に限定し、いずれにも記載がない場合は「指摘なし」と記載する (レビュー結果を推測で作成しない)。可逆性や影響範囲のうち diff・plan・spec から読み取れない部分には「推測:」を付記する (根拠欄の記述にも同一ルールを適用する)。
4. **02 非昇格グループ**: Step 2 のグループ単位で、そのグループに残った非昇格の hunk のみをファイル別の `<details class="file">` (初期状態は `closed`) に配置する。意図の解説はグループ単位で 1 つ記載する。非昇格の hunk が 0 件になったグループは、このセクション自体を省略してよい (ヘッダの集計表に件数が残るため)。
5. **承認チェック — 置き場所はカードの末尾**: 決裁カード 1 枚につき 1 個、カードの**内部の末尾** (最後の diff の直後) に配置する。確認者がリスクの内容を確認し終えた位置で承認判断を行う導線とするため、ヘッダやカードの冒頭には配置しない。ラベルは「このリスクを受け入れる」とする。確認者に求めているのはリスクの受容であり、diff の確認完了報告やコードの正確性の判定ではないためである。チェックボックスの総数 = カードの総数 = ヘッダの「確認 0/N」の N とする (ファイル単位のチェックに戻さないこと。1 枚のカードが複数ファイルにまたがる場合、ファイル単位のチェックでは「該当リスクを受け入れたか」を記録できないため)。
6. **チェック状態の可視化と保存**: components.md に定義された承認用 JavaScript が担当する。カードへの `.approved` クラスの付与・削除、カード上部の状態バッジおよびファイルナビへの反映、ヘッダの「確認 n/N」の更新、localStorage への保存および画面復元時の再適用を実行する。保存キーにはカードの見出し文を使用する。動作の詳細は components.md 部品6 に定義されているため、ここでは再定義しない。(**見出し文を修正したカードは未承認状態に戻る**。内容が変更された場合は、別のリスクとして承認判断をやり直す必要があるためである)。

### 見出しと 4 項目の語彙 — 素材の語彙を持ち込まない

使用できる語彙は、**用語集および spec の要件セクションにある語、ならびに一般的な日常語のみ**とする。用語集は `docs/crystallize/CONTEXT.md` (リポジトリ直下の `CONTEXT.md` に `## 用語` または `## Language` があればそちらが正本)、どちらもなければ spec の「用語」セクションを使用する。コードや plan の専門用語をそのまま記載すると、確認者 (事前の動作確認でアプリケーションを操作した人物) にとって内容が理解しにくくなり、判断材料として機能しなくなるためである。

**記載してはならない表現**: 関数名・変数名・クラス名・provider 名などの識別子、ファイル名・パス・拡張子、行番号、hunk 番号、code-review の指摘番号、Deviations の項目番号、`()` 付きの呼び出し表記。これらの情報は除外するのではなく、「根拠を見る」の折りたたみ内および diff の中に配置する。

- 悪い例: 「build() がアプリ起動のたびに _reconcileAbandoned() を走らせる (起動時の帳簿整理)。この provider を最初に読んだ時点で、猶予切れの active セッションファイルが書き換わる。」
- 良い例: 「アプリを起動するたびに、中断中の復習フライトが自動で破棄扱いになることがある。判定を誤ると続けられたはずのフライトが消え、元に戻せない。」

**出力前に語彙と形式の検証を行う** — 見出しと 4 項目のテキストのみをファイルに抽出する (**バッジの文言は含めない。dt と dd の間、バッジと本文の間には半角空白を 1 つ挿入する**。空白を入れないと単語の境界が失われ、2) の照合をすり抜けるため)。抽出したファイルに対して以下の 3 つの検証コマンドを実行する。

```bash
# 1) 明示的な禁止形 — ヒットが 0 であること
grep -nE '[a-z][A-Z]|[a-z0-9]_[a-z]|\(\)|\.[a-z]{1,5}\b|hunk ?[0-9]|指摘 ?[0-9]|項目 ?[0-9]|L[0-9]+|[0-9]+ ?行目' <抜き出したファイル>
# 2) ラテン文字の語をすべて列挙 — 1 語ずつ、用語集か spec の要件節にあるか確かめる
grep -oE '[A-Za-z]{2,}' <抜き出したファイル> | sort -u
# 3) 字数 — 見出しは 80 字、4 項目の説明文は各 60 字を超えないこと
while IFS= read -r line; do [ ${#line} -gt 80 ] && echo "${#line} 字: $line"; done < <抜き出したファイル>
```

- 1) は該当件数が 0 件であることが条件である。該当した場合は、正規表現を変更するのではなく文側を書き直す (該当があることは、コード固有の表現が混入していることを示しているため)。
- 2) は 0 件である必要はないが、**列挙された英単語が用語集または spec の要件セクションに含まれているかを 1 語ずつ照合する**。含まれていなければ一般的な日本語に言い換える。`provider` や `build` のような単一語の識別子は 1) のパターンで検知されないため、この照合によって識別子の混入を防止する。`API` や `JSON` のような略語も同様に扱い、用語集に記載がなければ言い換える (例外を個別判断にすると、確認基準が曖昧になるため)。
- 3) の 60 字制限は説明文のみを対象としてカウントする (見出し語「何が起きうるか」などは含めない)。
- 件数を記述する際は数値を先に配置する (例:「2 件の指摘はすべて解消済み」)。「指摘 2 件」という順序で記述すると、指摘番号の「指摘 2」と機械的に区別がつかず、1) の検証で誤検知されるためである。

## Step 5: 検算と表示

- 昇格 hunk 数 + 非昇格 hunk 数の合計が、Step 1 で確定した判定対象 hunk 数 `M` と一致することを確認する。**さらに、Σ(各カードの hunk 数) = 昇格 hunk 数 = Σ(グループ表の「うち昇格 n」) の 3 つの数値が一致することを確認する** (カードへの重複登録や登録漏れがある場合、この 3 つの数値の不一致として検出される)。一致しない場合は、未割り当ての hunk を「未分類」グループ (⑥) に割り当ててから公開する。
- **この検算は、昇格 0 件でスキップした場合も同様に実行し、集計した数値をスキップ規則の 1 行に記載する**。画面を生成しない場合でも、すべての hunk を判定した客観的な証拠は数値のみであるため、この検算を省略してはならない。
- 保存先、`open` コマンドによる表示、レポート一覧 (report-index) への登録、gitignore に関する注意点は、派生元の Step 5 の規定に従う (昇格 0 件のときはファイルを生成しないため、この一連の手順は不要となる)。

## Gotchas

- 未追跡ファイルは `git diff` の出力に含まれない。`git status --porcelain` で `??` と表示されるファイルを収集しないと、新規ファイルがレビュー対象から漏れる原因となる。
- 承認チェックボックスは「このリスクを受け入れる」という承認判断の記録であり、動作確認の証拠やコードの正当性を保証するものではない。動作確認は上流ワークフローで担保し、コードの正しさはテストと AI レビューで担保する。チェック状態を根拠に「動作確認済み」「レビュー完了」として上位プロセスや履歴に報告してはならない。承認はユーザーが行う判断であり、スキルの実行によって自動的に保証される成果物ではない。
- 昇格 0 件時のスキップは**工程の省略ではなく出力形式の短縮**である。差分の収集、グループ化、6 条件に基づく判定、検算はすべて実行した上で、出力形式のみを HTML から 1 行のテキストに変更している。判定手順を省略すると検算用の数値が得られないため、1 行に M、N、追加・削除行数を必ず記載する (数値を提示できない状態は、判定が実行されていないことを示す)。
- 本スキルで生成した HTML 自体 (`docs/crystallize/reports/`) や plan (`docs/crystallize/plans/`) が差分に含まれることがある。これらはレビュー対象から除外し、その旨と件数を画面上に注記として記載する。
- spec (`docs/crystallize/specs/`) の hunk は除外しない。spec は保存される成果物であり、コミット対象に含まれるためである。ただし、実装計画のどの項目にも紐づかないため、そのまま処理すると「未分類」 (条件⑥) として昇格してしまう。spec の改訂履歴に追加された行を変更意図とし、「仕様改訂」グループに対応づける。ユーザー自身が挙動ゲートで決定した仕様改訂を「plan にない想定外の変更」として昇格させると、昇格 0 件時のスキップ規則が適切に機能しなくなるためである。
- plan に `## Deviations` 見出しが存在しない場合、spec が見つからない場合、あるいは受け入れ基準のセクションが存在しない場合でも処理を中断しない。条件⑤の判定や受け入れ基準の表示は「該当なし」として省略し、その他の判定は通常どおり進める。
- 非昇格グループの出力を完全に削除してはならない。初期状態で折りたたむのであり、出力から除外するのではない。検算の対象から外れると、確認漏れを防ぐ原則が機能しなくなるためである。
