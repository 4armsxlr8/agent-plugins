# Levels: 難度設計と適応制御

`references/learning-science.md` のエビデンスに基づき、難度は **直近正答率 70-85% の窓**（Bjork の desirable difficulties）を維持する。Bloom 階層は出題タイプの **分布モニタ用途** に限定する（階層性の経験的根拠は弱いため、ロック構造には使わない）。

## 主軸: 5段階レベル

| Level | Label | 目安 |
|---|---|---|
| 1 | 初級 | 用語と基本概念を「知っている」状態。定義の暗唱と典型例の識別ができる |
| 2 | 中の下 | 単純な使用ができる。テンプレ的な使い方なら自力で再現できるが応用は不安 |
| 3 | 中 | 標準的なケースを自力で実装・解決できる。よくある落とし穴も把握している |
| 4 | 中の上 | 非自明なケースで適切な選択肢を判断できる。複数手法のトレードオフを語れる |
| 5 | 上級 | 抽象化・設計・最適化が可能。新しい問題を既知のパターンに還元できる |

Level は **カリキュラムの Stage 配分** と **Worked Example の fading レベル** に直結する:

| Level | Stage | Worked Example |
|---|---|---|
| 1 | Foundation | full（完全な解答ステップ + 解説） |
| 2 | Foundation 後半 | full → faded への移行期 |
| 3 | Practical | faded（途中まで埋まっている） |
| 4 | Design | open（自力 / 設計問題） |
| 5 | Design | open + 拡張 / 教える側に立つ課題 |

⚠️ **Expertise Reversal Effect**: Level 4-5 の学習者に worked example を与えると逆効果（負荷増）。Stage 3 では使わない。

## 副軸: Bloom 階層（モニタ指標）

Bloom は **出題タイプの認知レベル分布をバランス監視** するための指標。「下位階層がクリアされないと上位に進めない」というロック構造には使わない（学習科学的に弱い根拠）。

- **Remember (記憶)**: 用語・定義・記法を再生
- **Understand (理解)**: 概念を自分の言葉で説明、例を識別
- **Apply (応用)**: 既知の手順を新しい場面で実行
- **Analyze (分析)**: 構成要素に分解し関係を読み解く
- **Evaluate (評価)**: 複数の選択肢から判断・正当化
- **Create (創造)**: 制約下で新しい解を構築

### 出題分布の目安（Stage 別）

| Stage | Remember | Understand | Apply | Analyze | Evaluate | Create |
|---|---|---|---|---|---|---|
| 1 (Foundation) | 30% | 40% | 30% | 0% | 0% | 0% |
| 2 (Practical) | 10% | 20% | 40% | 20% | 10% | 0% |
| 3 (Design) | 0% | 10% | 20% | 30% | 25% | 15% |

これは厳密なノルマではなく、**直近 5問が同じ階層に固まっていないか** をチェックするための分布感覚。

## 診断フェーズ

**診断は通常学習と必ず分離する**（ユーザーのフィードバック反映）。診断専用ディレクトリ `.study/<topic>/diagnostic/` に問題ファイルを置く。

### 診断問題の構成

Bloom 階層の異なる **4問** を出題:

1. **Remember 寄り**（Level 1-2 判定）: 「○○とは何か説明してください」
2. **Apply 寄り**（Level 2-3 判定）: 「このケースで○○を使って実装してください」
3. **Analyze 寄り**（Level 3-4 判定）: 「このコードの問題点を指摘してください」
4. **Evaluate / Create 寄り**（Level 4-5 判定）: 「A と B のどちらを選び、なぜか」

### 診断中の解説プロトコル

通常学習と異なり、診断は **レベル測定** が目的。ただしユーザーが「わからない」「空欄」で投了した場合も、

- **必ず模範回答 + 解説を提示する**（次の問題に進む前に）
- 「これは難度の高い問題でした」と難度文脈を添える
- スコアを付けて次の診断問題に進む

診断問題ファイルは通常学習と同じテンプレートを使うが、ヘッダーで `Type: diagnostic` を明示する。

### 推定レベルの算出

各問のスコア（0.0-1.0）から推定レベルを決める:

| 条件 | 推定 Level |
|---|---|
| 全 4 問が 0.7+ | 5 候補（追加で Create 1問で確定） |
| 上位 2-3 問が 0.7+ | 4 |
| 中位 2 問前後が 0.7+ | 3 |
| 下位 2 問のみ 0.7+ | 2 |
| 第1問のみ 0.7+ | 1 |
| 全問 0.4 未満 | 1（基礎から、概念導入を優先） |

`Confidence` は推定レベル付近のスコア安定度から:

- 全 4 問が判定通り（綺麗な階段状）→ 0.9
- 1問だけ予想外れ → 0.7
- 2問以上ばらつき → 0.5（追加 1-2問で再診断推奨）

診断後、`diagnostic/summary.md` に結果を書き出し、ユーザーにレビューしてもらってから本ループへ。

## 適応制御（Sliding Window）

学習中の難度調整は **直近 5問の正答率移動平均** を主指標にする（旧仕様の連続2問 streak より安定）。

### Difficulty Window: 70-85%

`references/learning-science.md` の desirable difficulties に基づき、直近 5問の平均スコアが:

| 直近 5問平均 | 動作 |
|---|---|
| **0.85+** | 難度上げ。Level +1 か、同 Level 内で 1段階上の Bloom / 課題タイプへ |
| **0.70-0.85** | 維持。これが学習が最も進む窓 |
| **0.50-0.70** | 維持＋ヒント強化、worked example を 1段階手前に戻す |
| **0.50 未満** | 難度下げ。Level -1 か、Stage を一段戻して基礎強化 |

最低5問の履歴がない場合は、直近の全問の平均で代用する（最低3問は集めてから判定）。

### 主観フィードバックは参考程度

ユーザーが「簡単すぎる」「効いてない感じ」と訴えても、**スコアが 0.85 未満なら難度を上げない**（Bjork の fluency 錯覚）。一方、「難しすぎてつらい」と訴えた場合は休憩や Stage 戻しを優先（精神的負荷は学習効率を破壊する）。

### Level 変化時の動作

Level が変化したら:

1. `README.md` の `Current level` を更新
2. ユーザーに明示する: 「Level 3 → 4。直近の正答率が安定して 0.85 を超えたので難度を上げます」
3. カリキュラムの未着手項目を Level に合わせて再配分（必要なら）

## 例外: ユーザーの調子を考慮する

3問連続でヒント要求が続く場合、知識ではなく **集中・疲労の問題** の可能性がある。即座に Level を下げず:

1. 「少し休憩しますか？」と一度問う
2. 同レベルで別タイプの問題に切り替える（例: code-write → predict-output）
3. それでも続けば Stage を一段戻す（Level -1 ではなく原則的に Stage で戻す）

逆に、明らかに易しすぎて全問即答 + 0.95+ が続く場合は、診断信頼度を下げて再診断モードを提案する。

## 学習効率の窓を狙う

繰り返しになるが Study Loop の難度設計は **常に 70-85% の正答率窓** を狙う。これは:

- 100% 正答 → 学習が止まっている、新しい概念に進むべき
- 50% 以下 → 認知負荷オーバー、基礎が足りない、Stage を戻すべき
- 70-85% → desirable difficulty、長期保持が最大化される

「効率の良い学習は心地よくない」というのは Bjork の核心メッセージである。Study Loop はこの不快さを **意図的に維持する** よう設計する。
