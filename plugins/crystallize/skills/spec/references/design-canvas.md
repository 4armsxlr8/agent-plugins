# デザインキャンバス — 絵を置く場所の使い方

画面のあるタスクの案 (モック) は、プロジェクトに 1 つの**デザインキャンバス** (claude.ai の Design 型 Artifact。アートボードを並べる面) に描く。問いはラウンドレポート (`docs/crystallize/specs/<slug>/round-<n>.html`) に置き、キャンバスには絵だけを置く。ここに書く名前 (`project/`・`.dc.html`・`canvas.json`・`support.js`・プロトタイプリンク・`{{…}}`・`<sc-for>`・`<dc-import>`) は 2026-10-18 に Design 型の指示で確認したもの。アートボードのファイルの書き方そのものはここに書かず、キャンバス作成時 (または `type_url` の `read`) に Design 型が返す指示に従う。**型の指示が変わっていたら型の指示が勝つ**。

## 1 プロジェクト 1 キャンバス

- `docs/crystallize/design-canvas.md` に URL・Design 型の `type_url`・題・使ったデザインシステム (無ければ「なし」)・作成日を書く。全 spec・全ラウンドで同じキャンバスを使い、新しい案はアートボードとして足す。キャンバスを spec ごと・ラウンドごとに作らない (絵の置き場が増えるほど、前に決めた画面との見比べができなくなる)
- 無ければ親が作る。Artifact ツールの `action: "quickstart"`, `intent: "design"` で Design 型の `type_url` とデザインシステムの一覧を得る → プロジェクトのデザインシステムが一覧にあればそれを使う → `type_url` と題 (`<プロジェクト名> design`) で publish → 返ってきた Design 型の指示 (ファイルの形、公開の仕方、先に読むページ) を読み、URL と `type_url` を `design-canvas.md` に記録する
- **セッションの最初に 2 回 `read` する**。(1) `action: "read"` + `url` = キャンバス: そのセッションで read も publish もしていない Artifact への publish は拒否されるため。これはページしか返さない。(2) `action: "read"` + `type_url` (url は渡さない): Design 型の指示が返る。後のセッションはこれでしか指示を取り戻せない

## ラウンドの行

- **絵の要る問い 1 つ = キャンバスの 1 行**。行頭に `title1` の付箋「R<round> Q<n> <題>」を置き、右に選択肢ごとのアートボードを 1 枚ずつ並べる
- アートボードの名前は `R<round>-Q<n>-<選択肢 id>` (ファイルは `project/R5-Q1-A.dc.html`)。1 案が複数画面なら `R5-Q1-A-2` と続ける。ユーザーがそのラウンドを見る前の描き直しは同じ名前に上書きし、見たあとに描き直す案は新しい名前にする (レポート・ledger・spec が指した名前の中身を変えない)
- 同じ問いの案は同じ場面 (同じ画面・同じダミーデータ) で描き、問いで比べる差だけを変える
- 提案の案 (spec Step 3) は、アートボードの題 (`.dc.html` の `<title>`) の先頭に「(提案)」を置く。名前の規則は他の案と同じ
- 画面の移り変わりは、アートボード間のプロトタイプリンク (`<a href="R5-Q1-A-2.dc.html">`) で描く。`mock-evaluator` はこのリンクと行の並びで導線を辿る
- 見ながら動かさないと決められない値 (余白・件数など) は、アートボードに `data-props` の調整を付け、同じ値の `doc-ask` をレポートにも置く (spec Step 2)。値はレポートの返信で受け取る
- 既定のページには現在のラウンドの行だけを置く。決まった画面は「決まっていること」ページへ、落ちた案は「不採用」ページへ移す (`pages`)。名前や題に「(確定)」「(不採用)」の印は付けない — どのページにあるかが状態である

## 作成と公開

- アートボードの HTML を書くのはサブエージェント (spec Step 3 の委任)。書き出し先は `docs/crystallize/specs/<slug>/design/round-<n>/`。親はこのファイルと Design 型が返した指示、名前と寸法、場面、前のラウンドの読み戻し (`design/round-<m>/project/`) の場所を渡す (写しは spec の終了時にしか作られないので、途中のラウンドで既存の絵を見せるには前のラウンドの読み戻しを渡す)。サブエージェントはキャンバスに触らない
- 公開は親が行う (Artifact ツール、`url` = キャンバス)。行の付箋・ページの配置も親が宣言する。どのファイルをどのパスで publish するかは Design 型の指示に従う
- 描き直しも同じ手順 (サブエージェントがファイルを直す → 親が再公開 → 再読み戻し → スクリーンショットの取り直し)

## 読み戻しとスクリーンショット

- 公開後、各アートボードと `canvas.json` を `action: "read"` + `paths: ["project/<名前>.dc.html", …, "project/canvas.json"]` + **`out_dir` = `docs/crystallize/specs/<slug>/design/round-<n>` の絶対パス**で読み戻す。`out_dir` を省くと scratchpad に落ちる。ファイルは `<out_dir>/project/<名前>.dc.html` に入る。ディスクの中身がキャンバスの中身と同じになり、`mock-evaluator` と試問はこのディレクトリを読む
- スクリーンショットは読み戻した HTML から作る。`<script src="./support.js"></script>` の行を除いた写しを作り、headless Chrome でアートボードの寸法どおりに描いて PNG にする。例: playwright の `chromium.launch({ channel: 'chrome' })`、`deviceScaleFactor: 2`、viewport をアートボードの寸法に合わせて `page.screenshot`。playwright が無ければ Chrome 単体でよい: `chrome --headless=new --screenshot=<png> --window-size=<w>,<h> file://<写し>` (依存を足さない)。PNG は `design/round-<n>/project/<名前>.png` に置き、絶対パスをラウンドレポートの素材に書く (data URI への埋め込みは `html-report` が行う)
- デザインシステムの部品、`{{holes}}`、`<sc-for>`、`<dc-import>` を使うアートボードはローカルでは正しく描けない。その案はスクリーンショットを付けず、キャンバスへのリンクだけにし、レポートにその旨を 1 行書く

## 終了時

- 確定したアートボードを「決まっていること」ページへ、落ちた案を「不採用」ページへ移す
- 確定したアートボードを `action: "read"` + `paths` + `out_dir` = `docs/crystallize/specs/<slug>/design` の絶対パスで読み戻し、`design/project/<名前>.dc.html` を写しとして保存する (読み戻したファイルをそのまま置く。手で直さない)。実装者 (`code-generator`) はこの写しを読む。キャンバスと写しが食い違ったらキャンバスが正本で、写しを読み戻し直す
- 改訂 (挙動ゲートでの外観変更) では、サブエージェントがアートボードの HTML を直し、親が `read` (url) でキャンバスを開いてから再公開し、写しを読み戻す。写しだけを直さない

## Gotchas

- **案をレポートに描かない** — レポートに載せるのはスクリーンショットとリンクだけ。絵の正本はキャンバス 1 つ
- **問いをキャンバスに置かない** — 答えはレポートの返信で受ける。キャンバスのコメントは補助で、設計を変える指摘はレポートのコメントか次のラウンドの問いに移す
- **読み戻しを省かない** — ローカルのファイルを直接スクリーンショットにすると、公開に失敗した案や古い版を見せることがある。ディスクの中身は常にキャンバスから読み戻したもの
