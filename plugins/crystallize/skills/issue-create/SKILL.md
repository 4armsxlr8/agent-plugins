# issue-create

会話の文脈や雑なメモを、構造の整った GitHub issue へ変換して起票する。リポジトリに issue テンプレートやラベルの運用があればそれに従い、無ければ持ち込まない — 起票先の家風が正で、本スキルは何も設置しない。fork しない — 素材が会話の中にあるため、メイン会話で動く。

## Input / Output

- **Input**: `$ARGUMENTS` = issue にしたい内容のメモ。省略時は直前の会話から対象を推定し、一行で確認を取る
- **Output**: GitHub issue (作成された URL を報告)。リポジトリの状態は変更しない (テンプレやラベルを作らない)

## 最重要ルール

1. **起票は対外的な操作 — 承認フェーズ (手順6) を飛ばして `gh issue create` しない**。承認前に作られた issue は削除しても通知や履歴が相手側に残り、取り消せない
2. **会話・メモに無い事実を補わない** — 推測で埋める箇所は「推測:」と明示する。必須といえる項目 (バグなら再現手順) が埋まらなければ、起票せずその項目だけ質問する
3. Web フォームと違い `gh issue create` はテンプレートの required を強制しない — **必須項目の担保はこのスキルの仕事**

## 手順

1. 対象リポジトリを確定する (cwd の git root。曖昧なら確認)
2. リポジトリの流儀を調べる — `.github/ISSUE_TEMPLATE/` のテンプレート (`*.yml` / `*.md`) と `gh label list` の実在ラベルを確認する
3. 種別を判定する (バグ報告 / 機能要望 / 雑務)。内容から自明でなければ、技術の言葉ではなく挙動の言葉で確認する
4. 本文を組み立てる:
   - **テンプレートがあれば**その項目立てどおりに書く。必須項目 (required) が会話の素材で埋まらなければ、その項目だけ質問する
   - **無ければ**種別に応じた見出し付きの構造で書く — バグ: 再現手順 / 期待した挙動と実際の挙動 / 環境。機能要望: 背景・困りごと / 欲しい挙動 / 受け入れ基準。雑務: やること / 完了条件
   - 機能要望の**受け入れ基準は観測可能な挙動レベル**で書く (テンプレートに欄が無くても見出しとして含める — 後段の find-unknowns / plan がそのまま流用する)
5. 重複を確認する: `gh issue list --search` で似た issue を探し、あればリンクを提示して起票するかを仰ぐ
6. **承認フェーズ**: 投稿される内容をそのまま提示する — タイトル / 本文の全文 (要約にしない。要約と実物の差分に指摘漏れが生まれる) / ラベル (付ける場合) / 起票先リポジトリ。AskUserQuestion で「起票する / 修正する」を確認し、修正の指摘があれば本文を直してこの手順を繰り返す。**明示的な承認が出るまで起票しない**
7. 承認を得てから `gh issue create` を実行する。`--label` は**手順2で確認した実在ラベルから内容に合うものがあるときだけ**付ける — 一覧に無いラベルは指定しない (作らない)。合うものが無ければラベルなしで起票する
8. URL を報告し、次の一手を1行だけ案内する (着手するなら新セッションで `/find-unknowns` に issue の URL か要約を渡す)

## Gotchas

- **issue を plan にしない** — issue は受け皿であって計画書ではない。背景・欲しい挙動・受け入れ基準まで書けたら止める。深掘り (blindspot 探索・モック・質問監査) は find-unknowns の仕事で、起票段階で盛ると二重管理になる
- **無いラベルを `--label` に渡すと起票ごと失敗する** — 「あった方がよさそうなラベル」を発明しない。ラベル体系の整備はリポジトリ所有者の仕事で、本スキルは実在するものから選ぶだけ
- **テンプレートの必須項目は起票後には強制されない** — Web フォームと違い CLI 経由は素通りする。required 相当が埋まらないまま承認フェーズへ進めない
